# C6 결과 — 실제 웹사이트에서

측정일 2026-09-18 · Chrome **152.0.7977.83** (headless=new, GPU 가속)
**엄격 격리 + 순서 섞기** ([C4d](../c4-raster-threshold/RESULTS.md#610-26배는-chromium-이-아니라-내-측정-절차였다)) · 설정마다 3회
대상: `en.wikipedia.org/wiki/List_of_Unicode_characters` — **DOM 47,925 노드 · 문서 152,571px · 블록 698개**
사전 등록: [PREDICTION.md](PREDICTION.md) · 측정 [measure.mjs](measure.mjs) · 집계 [analyze.mjs](analyze.mjs)

> 공개 페이지를 **읽기만** 했다. 총 18회 로드(사전 조사 6회 포함 24회). 로그인·폼·쓰기 없음.

## 결론 먼저 — 내 합성 하네스는 **양쪽으로** 틀렸다

| | 성능 | 정확성 |
|---|---|---|
| **합성이 말한 것** | cv 는 조건에 따라 **손해**(항목 스타일만에서 4.5배) | `contain-intrinsic-size` 73px 하나로 **오차 1.3%** |
| **실제** | cv 가 **훨씬 유리**(폭 변경에서 **11.3배**), 최악도 **무승부** | 81px 하나로 **오차 89.3%** — 스크롤바가 깨진다 |

**성능은 내가 과소평가했고, 정확성 문제는 내가 과소평가했다.** 방향이 반대다.

## 1. 성능 — 실제 페이지가 합성보다 cv 에 훨씬 유리하다

무효화 1회당 ms (3회 평균).

| 무효화 | 모드 | Style | Layout | PrePaint | Paint | 합계 | `plain` 대비 |
|---|---|---:|---:|---:|---:|---:|---|
| 컨테이너 폭만 | `plain` | 77.0 | 90.5 | 88.9 | 5.8 | 262.2 | — |
| | `cv-auto` | **8.5** | **5.3** | 5.3 | 4.0 | **23.2** | **11.30배 이득** |
| 항목 스타일만 | `plain` | 36.9 | 0.0 | 0.7 | 5.7 | 43.2 | — |
| | `cv-auto` | 35.0 | 0.0 | 2.4 | 5.2 | 42.7 | 1.01배 (**무승부**) |
| `:root` 변수 | `plain` | **500.8** | 9.3 | 11.9 | 7.3 | 529.2 | — |
| | `cv-auto` | **85.4** | 0.2 | 2.5 | 6.5 | 94.6 | 5.59배 이득 |

### 합성(C5)과 나란히 놓으면

| 무효화 | 합성 C5 | **실제 C6** | 방향 |
|---|---:|---:|---|
| 컨테이너 폭만 | 2.73배 이득 | **11.30배 이득** | 같음 (**4배 더 유리**) |
| 항목 스타일만 | **0.22배 = 4.5배 손해** | **1.01배 = 무승부** | ⚠ **다름** |
| `:root` 변수 | 1.32배 이득 | **5.59배 이득** | 같음 (4배 더 유리) |

**[C5 에서 "항목 스타일만 바뀌면 4.5배 손해"](../c5-realistic-invalidation/RESULTS.md#2-무효화-범위별-전체-표-n4000--무효화-1회당-ms)라고
경고했는데, 실제 페이지에서는 손해가 아니었다.**

### 왜 실제가 더 유리한가

합성 리스트에서 `plain` 의 컨테이너 폭 변경 Style 은 **0.41ms** 였다.
실제 페이지에서는 **77ms** — **188배**다.

실제 페이지에는 내 하네스에 없던 게 있다. 복잡한 선택자, 수천 개의 규칙, 47,925개 노드.
**건너뛸 일이 실제로 많으니 `content-visibility` 가 절감할 것도 많다.**
내 합성 리스트는 너무 단순해서 **cv 가 아낄 것이 애초에 없었다.**

> [C5 에서 "건너뛸 스타일 작업이 없으면 절감할 것도 없다"](../c5-realistic-invalidation/RESULTS.md#1-왜-c2-의-조건이-문제였나)고 썼다.
> 맞는 말이었는데, **내 하네스가 바로 그 "작업이 없는" 쪽**이었다.

## 2. 정확성 — 여기서 실제가 훨씬 나쁘다

| | 문서 높이 |
|---|---:|
| 원본 (`plain`) | **152,571 px** |
| `cv-auto` (`contain-intrinsic-size: auto 81px`) | **16,303 px** |
| **오차** | **−89.3%** |

**문서가 원래의 10.7% 로 쪼그라든다.** 스크롤바가 완전히 깨진다.

[C1 에서 합성 리스트는 73px 하나로 오차 1.3% 였다](../c1-initial-load/RESULTS.md#4-contain-intrinsic-size-의-값이-맞는지-다시-확인됐다).
차이는 **블록 크기의 균일성**이다.

| | 블록 수 | 높이 중앙값 | 최소~최대 | **변동계수** |
|---|---:|---:|---|---:|
| 내 합성 리스트 | 4,000 | 109px | 109~109px | **≈ 0** |
| **실제 Wikipedia** | 698 | 81px | **26 ~ 43,220px** | **3.72** |

**한 값으로 맞출 수가 없다.** 26px 짜리와 43,220px 짜리에 같은 추정치를 줘야 한다.

`auto` 키워드가 렌더된 크기를 기억하지만, 대부분의 블록은 화면 밖이라 **한 번도 렌더된 적이 없다.**
그래서 기억할 것이 없고 81px 추정치가 그대로 쓰인다.

> **이게 실제 페이지에 `content-visibility` 를 적용할 때의 진짜 장벽이다.**
> 성능이 아니라 **문서 높이**다. 내 합성 하네스는 이 문제를 완전히 숨기고 있었다.

## 3. 애초에 걸 곳을 찾는 것부터 문제였다

사전 조사에서 공개 문서 사이트 4곳을 훑었다.

| 걸림돌 | 내용 |
|---|---|
| **테이블** | 반복 단위가 대부분 `<tr>` 인데 **`contain: size` 는 테이블 내부 요소에 적용되지 않는다** |
| **입자가 너무 굵다** | 권장대로 본문 직계 자식에 걸면 Wikipedia 19개 · MDN 3개 · WHATWG 3개뿐 |
| **크기가 제각각** | 한 단계 내려가 698개를 찾았지만 변동계수 3.72 |

| 사이트 | 쓸 수 있나 |
|---|---|
| Wikipedia (Unicode 목록) | ✅ `.mw-parser-output section > *` 698개 |
| MDN CSS Reference | ❌ 본문 직계 자식 3개 |
| WHATWG HTML Standard | ❌ 3개 |
| Wikipedia (HTTP 상태 코드) | ❌ 문서가 17,865px 로 작다 |

**4곳 중 1곳만 쓸 수 있었다.** 합성 하네스에서는 당연히 겪지 않는 문제다.

## 4. 사전 등록 주장 판정

| # | 주장 | 판정 | 실측 |
|---|---|---|---|
| **Q1** | 81px 하나로는 `scrollHeight` 오차 **30% 이상** | ✅ **채택** (그 이상) | **89.3%** |
| **Q2** | 폭 변경에서 cv 이득. 다만 **배율은 C5보다 작다** | ⚠️ **절반 반증** | 이득은 맞지만 **4배 더 크다**(2.73 → 11.30배) |
| **Q3** | 항목 스타일만 바뀌면 cv 가 **손해** | ❌ **반증** | **무승부**(1.01배) |
| **Q4** | `plain` Style 이 무효화 방식에 따라 크게 다르다 | ✅ **채택** | 36.9 ~ 500.8ms (**14배**) |
| **Q5** | 전체 결론의 **방향**이 C5 와 같다 | ⚠️ **부분** | 둘은 같고 하나는 다르다 |

**5개 중 1개 반증, 2개 부분.**
특히 **Q2·Q3 를 틀린 방향이 일관된다** — 나는 실제 페이지가 합성보다 **cv 에 불리할 것**이라 봤는데
전부 **유리한 쪽**으로 틀렸다.

## 5. 그래서 이 저장소의 결론을 어떻게 고쳐야 하나

| 기존 문장 | 고쳐야 할 것 |
|---|---|
| [C5] "항목 스타일만 바뀌면 cv 가 4.5배 손해" | **합성 한정.** 실제 페이지에서는 무승부였다 |
| [C1] "`contain-intrinsic-size` 는 정확히 줄 수 있다 (오차 1.3%)" | **내가 균일하게 만들었기 때문.** 실제로는 89% 틀린다 |
| [C2/C5] "이득은 조건에 따라 없거나 손해" | 실제 페이지에서는 **세 조건 모두 이득** (11.3 / 1.01 / 5.59배) |

**실무자에게 할 말은 이렇게 바뀐다:**

> `content-visibility` 는 실제 페이지에서 **성능상 거의 항상 이득**이다 (내 합성 측정보다 훨씬).
> 진짜 문제는 **문서 높이**다 — 블록 크기가 제각각이면 `contain-intrinsic-size` 를
> 한 값으로 줄 수 없고, 스크롤바가 깨진다. **적용 전에 블록 높이의 분포부터 보라.**

## 6. 한계

- **사이트 한 곳**이다. Wikipedia 한 페이지로 "실제 웹" 을 대표할 수 없다
- 무효화 세 가지는 [C5 와 맞추려고](../c5-realistic-invalidation/PREDICTION.md) 고른 것이고, 실제 사용자 상호작용(스크롤·클릭)은 안 봤다
- **초기 로드는 안 쟀다.** 네트워크 변동이 커서 별도 설계가 필요하다 ([C1](../c1-initial-load/RESULTS.md) 의 실제판)
- 페이지가 바뀌면 숫자도 바뀐다. 측정일을 기록해뒀다
- headless · GPU 가속 · Chrome 152 단일 엔진

## 7. 자가 평가

**통과**

- **16개 실험의 공통 전제를 처음으로 밖에서 검증했다.** 그리고 **양쪽으로 틀렸다는 게 나왔다** —
  성능은 과소평가, 정확성 문제는 과소평가. 한 방향으로만 틀렸으면 "합성은 낙관적" 같은
  간단한 보정으로 끝났을 텐데, 방향이 갈려서 **그런 보정이 불가능하다는 것**까지 드러났다
- **측정 전 조사에 세 단계를 쓴 게 맞았다.** 바로 측정했으면 `<tr>` 에 `content-visibility` 를 걸고
  (테이블 내부에는 size 컨테인먼트가 안 붙는다) 엉뚱한 숫자를 냈을 것이다
- **Q2·Q3 를 틀린 방향이 일관됐다.** 내가 실제 페이지를 "더 나쁠 것" 으로 가정하고 있었다는 뜻이고,
  사전 등록이 없었으면 그 편향을 못 봤을 것이다
- 공개 페이지를 읽기만 하고 로드 수를 제한했다

**부족**

- 사이트 한 곳으로 끝냈다. 최소 3곳은 봐야 "실제 웹" 이라 말할 수 있다
- 초기 로드(C1 의 실제판)를 안 쟀다. 이게 `content-visibility` 의 주 홍보 지점인데 빠졌다
