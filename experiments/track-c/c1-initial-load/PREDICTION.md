# C1 사전 등록 예측 — 초기 로드 비용

> **측정 전에 작성.** 2026-09-18.
> [A4 §7](../../track-a/a4-content-visibility/RESULTS.md#7-한계) 에서 *"이 기능의 주요 홍보 지점인데 빠졌다"* 고 적은 항목을 채운다.

## 왜 이걸 따로 재야 하나

Track A 전체가 **정상 상태와 리레이아웃**만 쟀다. **첫 페인트를 잰 실험이 하나도 없다.**
그런데 `content-visibility` 가 가장 많이 홍보되는 지점은 초기 로드다.

A4 의 리레이아웃 측정과 결정적으로 다른 점:

| | A4 (리레이아웃) | C1 (초기 로드) |
|---|---|---|
| DOM 생성 | 트레이스 **밖**에서 미리 | 트레이스 **안** — 파싱부터 포함 |
| 측정 구간 | 강제 리레이아웃 8회 | 내비게이션 → LCP |
| 항목 삽입 | JS 로 `appendChild` | **HTML 에 미리 박아둔다** |

항목을 JS 로 만들면 파싱 비용이 빠진다. 그래서 이번엔 **N개 항목이 들어간 정적 HTML 파일을 미리 생성**해서,
브라우저가 진짜 문서를 파싱·레이아웃·페인트하는 전 과정을 잰다.

## 측정

| 항목 | 값 |
|---|---|
| N | 200 / 1,000 / 4,000 항목 |
| 모드 | `plain` · `cv-auto`(정확한 intrinsic-size) · `cv-nosize` |
| 구간 | `Page.navigate` 직전부터 LCP 이후까지 트레이싱 |
| 1차 지표 | `ParseHTML` · `UpdateLayoutTree` · `Layout` · `PrePaint` · `Paint` · `RasterTask` 의 횟수·시간 |
| 2차 지표 | FCP · LCP (트레이스의 `firstContentfulPaint` / `largestContentfulPaint::Candidate`) |
| 격리 | 설정마다 Chrome 새로 기동 · 3회 반복 · 캐시 무효화 |

## 예측

| # | 주장 | 근거 |
|---|---|---|
| **G1** | `ParseHTML` 은 세 모드가 **거의 같다** | HTML 바이트가 동일하다. CSS 한 줄 차이뿐 |
| **G2** | 초기 `Layout` 시간이 `cv-auto` 에서 **70% 이상** 줄어든다 | A4 리레이아웃에서 87% 줄었다. 초기 로드도 비슷할 것 |
| **G3** | 초기 `Layout` 이 **여전히 N에 비례**한다 (N 20배 → 8배 이상 증가) | A4 결론: 상자 자체는 레이아웃된다 |
| **G4** | **LCP 는 세 모드가 비슷하다** | LCP 요소는 화면 맨 위 항목이고, 그건 어느 모드든 렌더된다 |
| **G5** | `cv-nosize` 의 초기 Layout 은 `cv-auto` 와 비슷하다 | A4 에서 CPU 비용이 사실상 같았다 (10.00 vs 10.88ms) |

### 가장 불확실한 것

**G4 다.** 두 갈래가 가능하다.

- (a) LCP 요소가 화면 위쪽이라 모드와 무관 → 비슷하다
- (b) `plain` 은 4,000개를 전부 레이아웃하느라 첫 페인트가 밀린다 → `cv-auto` 가 확실히 빠르다

통용되는 홍보 문구는 (b)를 주장한다. 나는 **(a)에 가깝되 N=4,000 에서는 (b)가 조금 보일 것**으로 본다 —
레이아웃이 끝나야 첫 페인트가 나오므로, 레이아웃이 78ms 걸리면 그만큼 밀릴 수밖에 없다.

→ **LCP 차이를 N별로 본다.** N이 작으면 차이 없고, N이 크면 벌어질 것으로 예측한다.

## 판정

- G1·G2·G3 성립 → 통과
- G2 실패 (`cv-auto` 가 초기 로드에서는 별 도움 안 됨) → **리레이아웃과 초기 로드가 다르다**는 뜻. 그 자체가 중요한 발견
- G4 가 (b)로 크게 갈림 → 통용 문구가 맞다는 뜻. 내 예측 수정
