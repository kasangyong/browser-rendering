# C4d 사전 등록 예측 — `RasterTask.dur` 이 왜 실행마다 26배 널뛰나

> **측정 전에 작성.** 2026-09-18.
> [C4 §6.9](RESULTS.md#69-겹침-10배도-잡음이었다--그리고-왜-계속-이랬는지-알아냈다) 에서 열어둔 마지막 항목.

## 먼저 좁힌 것 — 꼬리가 아니라 실행 전체가 움직인다

평균만 흔들리면 **긴 꼬리 몇 개** 때문이다. 그런데 **중앙값도 같이** 움직인다.

| 설정 (동일) | 반복별 평균 µs | 반복별 **p50** µs | 평균 배율 | **p50 배율** |
|---|---|---|---:|---:|
| GPU 켬 · cols=1 | 60 · 111 · 579 · 1577 | 39 · 48 · 151 · **963** | 26.3배 | **24.7배** |
| GPU 켬 · cols=2 | 121 · 246 · 1227 · 1497 | 48 · 50 · 893 · **1168** | 12.4배 | **24.3배** |
| GPU 끔 · cols=1 | 1202 · 1473 · 1514 · 1707 | 484 · 493 · **1278** · **1368** | 1.4배 | 2.8배 |

평균/p50 비는 2.0~4.7 로 **일정하다.** 분포 모양은 그대로인데 **통째로 위아래로 움직인다.**

게다가 값이 **두 무리**로 갈린다 — 빠른 실행(39~50µs)과 느린 실행(890~1170µs).
중간이 드물다. 실행 단위로 **뭔가가 켜지고 꺼진다.**

## 가설

실행마다 Chrome 을 새로 띄우므로 후보는 **실행 단위 상태**다.

| # | 가설 | 내용 |
|---|---|---|
| **J1** | **이전 실행의 잔여 프로세스** | `SIGKILL` 후 0.5초만 쉬고 다음을 띄운다. GPU 프로세스 정리는 더 걸릴 수 있고, 겹치면 새 실행이 느려진다 |
| **J2** | **GPU 워밍업** | 프로세스가 갓 떴을 때 셰이더 컴파일·텍스처 할당이 겹친다. 빌드 직후 바로 재면 그 구간을 잡는다 |
| **J3** | 머신 상태 (열·주파수) | 내 통제 밖 |
| **J4** | 측정 구간이 다른 것을 잡는다 | 실행마다 래스터가 창의 어디에 걸리는지 달라진다 |

**J1 이 제일 의심스럽다.** 지금까지 모든 프로브가 `kill → 500ms → 다음 실행` 이었다.

## 측정 설계

**같은 설정만 반복한다.** 레이어 600 · 100×100 · cols=1 · GPU 래스터 켬 · **10회씩.**
조건 사이의 차이가 아니라 **흩어짐 자체**가 측정 대상이다.

| 조건 | 무엇이 다른가 |
|---|---|
| **A** | 현행 — `kill` 후 0.5초 |
| **B** | **엄격 격리** — headless Chrome 이 **0개**가 될 때까지 기다리고 +3초 |
| **C** | B + **빌드 전 5초 워밍업** (페이지 띄워놓고 대기) |

같이 기록: 측정 시작 시점의 **살아 있는 chrome 프로세스 수**(J1 의 직접 증거).

**판정**

| 결과 | 결론 |
|---|---|
| B 에서 흩어짐이 크게 줄면 | **J1 채택** — 잔여 프로세스 경합 |
| B 는 그대로인데 C 에서 줄면 | **J2 채택** — GPU 워밍업 |
| 셋 다 그대로면 | J1·J2 기각. J3 쪽이고 **이 환경에서는 못 잡는다** |
| 느린 실행에서 chrome 프로세스 수가 많으면 | J1 의 직접 증거 |
