# C4 사전 등록 예측 — Raster 가 켜지는 임계점

> **측정 전에 작성.** 2026-09-18.
> [C3 §4](../c3-layer-cliff/RESULTS.md#4-덤으로--c2-가-못-닫은--이-닫혔다) 에서 열어둔 것:
> *"Raster 가 1,000 → 1,500 에서 110배 뛰는 기전. 미확인."*

## 무엇을 쫓는가

C3 의 원자료를 **반복별로** 풀어보니 110배는 평균이 만든 착시였다.

| 레이어 | rep0 | rep1 | rep2 | |
|---:|---:|---:|---:|---|
| 500 | 0.04 | 0.05 | 0.06 | 전부 꺼짐 |
| 1,000 | 1.00 | 0.07 | 0.05 | 전부 꺼짐 |
| **1,500** | **61.69** | **60.37** | **0.03** | **2/3 켜짐** |
| 2,000 | 39.52 | 67.61 | 50.40 | 전부 켜짐 |
| 2,500 | 30.34 | 65.68 | 37.50 | 전부 켜짐 |
| 3,000 | 72.30 | 93.58 | 90.89 | 전부 켜짐 |

**중간값이 없다.** 0.03~1.00ms 아니면 30~94ms. 연속적으로 커지는 게 아니라 **이진 상태**다.
그리고 1,500 은 경계라 **같은 설정에서도 켜지기도 하고 안 켜지기도 한다.**

> [C3 의 "절벽"](../c3-layer-cliff/RESULTS.md#2-절벽은-없다)은 잡음이었지만,
> **이건 잡음이 아니다.** 0.05 와 60 사이가 비어 있다.

## 왜 애초에 Raster 가 0 이어야 하는가

하네스는 `will-change:transform` 으로 승격된 레이어의 **transform 만** 바꾼다.
타일은 이미 래스터돼 있으므로 **다시 그릴 이유가 없다.** 500·1,000 에서 0.05ms 인 게 정상이다.

그러니 질문은 *"왜 1,500 부터 다시 그리기 시작하는가"* 다.
가장 자연스러운 설명은 **타일이 버려지고(eviction) 매 프레임 다시 만들어진다**는 것이다.

## 가설

| # | 가설 | 내용 |
|---|---|---|
| **E1** | **타일 리소스 *개수* 상한** | cc 의 `ManagedMemoryPolicy` 에는 바이트 상한과 **별도로** 리소스 개수 상한이 있다. 1,000~1,500 사이에서 이걸 넘는다 |
| **E2** | 타일 *바이트* 상한 | 어떤 메모리 예산을 넘겨 축출이 시작된다 |
| **E3** | GPU 메모리 압박 | 타일 예산이 아니라 GPU 쪽에서 밀려난다 |
| **E4** | 임계점이 아니라 포화 | 한 프레임에 래스터를 못 끝내 backlog 가 쌓이는 것뿐 |

### E2 는 이미 의심스럽다

C3 에서 잰 타일 메모리는 **1,500 레이어에서 27.7MB**, [A2 가 소스에서 확인한 예산 512MB](../../track-a/a2-gpu-memory/RESULTS-source.md) 의 **5.4%** 다.
바이트 상한이라면 한참 남았다. (C3 에서 같은 산수로 한 번 틀린 적 있으니 이번엔 **실측으로도** 확인한다.)

## 측정 설계

### A. 임계점 정밀 탐색 — 켜질 확률을 잰다

레이어 **800 / 1,000 / 1,100 / 1,200 / 1,300 / 1,400 / 1,500 / 1,750 / 2,000**,
각 **6회 반복**. 경계가 확률적이므로 평균이 아니라 **켜진 비율**을 본다.

기록: `RasterTask` 시간·횟수 · 타일 메모리 · GPU 메모리 · 합성 레이어 수 ·
그리고 축출의 직접 증거가 될 이벤트(`TileManager`·`EvictTiles` 계열)가 트레이스에 있는지.

**판정**
- 켜진 비율이 어떤 레이어 수에서 0 → 1 로 급격히 바뀌면 → **진짜 임계점**
- 비율이 완만하게 오르면 → 임계점이 아니라 **확률적 포화**(E4)

### B. 결정적 판별 — 개수인가 바이트인가

[C3 의 박스 크기 판별](../c3-layer-cliff/RESULTS.md#3-타일-메모리는-원인이-아니다--실측으로도)을 그대로 쓴다.
레이어 **개수는 그대로** 두고 **타일 1장의 바이트만** 4배로 만든다.

| 박스 | 타일 ([`kTileRoundUp=64`](../../track-a/a2-gpu-memory/RESULTS-source.md)) | 타일 1장 |
|---|---|---:|
| 38×15 | 64×64 | 16 KB |
| **100×100** | **128×128** | **64 KB** |

**판정** — 임계점이 어디로 움직이는가

| 결과 | 결론 |
|---|---|
| 큰 박스에서 임계 레이어 수가 **1/4 로 내려온다** | **E2 채택** — 바이트가 기준 |
| 임계 레이어 수가 **그대로** | **E1 채택** — 개수가 기준 |
| 큰 박스에서 아예 안 켜진다 | 둘 다 아님. 다시 설계 |

### C. 소스 확인

A~B 로 방향이 잡히면 [A2 때와 같이](../../track-a/a2-gpu-memory/RESULTS-source.md)
Chromium 소스에서 해당 상한값을 찾아 **실측값과 대조**한다.

## 예측 요약

| # | 내 예측 |
|---|---|
| **A** | 임계점이 **뚜렷하다.** 1,100~1,300 어딘가에서 켜진 비율이 0 → 1 로 뛴다 |
| **B** | **E1 채택** — 큰 박스로 바이트를 4배 늘려도 **임계 레이어 수는 거의 그대로**일 것이다 |
| **E2** | 기각 — 1,500 에서 27.7MB 는 512MB 예산의 5.4% 다 |

**근거**: 상태가 이진이고 경계가 좁다는 건 **세는 값**(개수)에 걸린 상한처럼 보인다.
바이트 압박이라면 더 완만하게 나빠졌을 것이다.

**틀릴 수 있는 지점**: C3 에서 "타일 메모리 예산" 가설이 산수로 죽었다고 좋아했는데,
그때는 *바이트* 예산만 봤다. **개수 상한을 확인해본 적이 없다** — 그래서 이번엔 소스까지 간다.
