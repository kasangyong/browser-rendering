## 1. ① `auto` 키워드는 범인이 아니었다

### 설계 — 두 축을 직교시켰다

A4 는 **모드**(`plain`/`cv-auto`)와 **무효화 방법**(폭 변경)이 묶여 있어서 어느 쪽이 원인인지 못 가린다.
모드 3 × 무효화 3 × N 2 의 완전 격자로 다시 쟀다.

| 무효화 | 무엇을 바꾸나 | 의도 |
|---|---|---|
| `width` | `#list` 폭 760↔720px | **A4 가 쓴 방법** |
| `offset` | `#list` 의 `padding-top` 0↔40px | 폭은 그대로, **위치만** 민다 |
| `color` | 항목 배경색 | 레이아웃과 무관한 **대조군** |

### 결과 (N=4,000 · 무효화 8회 총합 ms)

| 무효화 | 모드 | **Layout 패스** | Style | **Layout** | PrePaint | Paint | 합계 | `plain` 대비 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| `width` | `plain` | 8회 | 222.4 | 265.9 | 135.0 | 13.1 | 636.3 | — |
| | `cv-auto` | 9회 | 54.3 | **32.4** | 35.0 | 10.1 | 131.7 | **4.83배 이득** |
| | `cv-fixed` | 9회 | 55.6 | **33.5** | 38.0 | 10.6 | 137.7 | 4.62배 이득 |
| `offset` | `plain` | 8회 | 226.4 | **23.4** | 119.1 | 10.2 | 379.1 | — |
| | `cv-auto` | **17회** | 65.5 | **45.0** | 53.7 | 10.0 | 174.1 | 2.18배 이득 |
| | `cv-fixed` | **17회** | 57.6 | **42.1** | 50.8 | 9.3 | 159.8 | 2.37배 이득 |
| `color` | `plain` | **0회** | 221.9 | **0.0** | 10.1 | 12.8 | 244.8 | — |
| | `cv-auto` | **9회** | 58.3 | **34.8** | 38.9 | 8.1 | 140.1 | 1.75배 이득 |
| | `cv-fixed` | **9회** | 62.7 | **37.7** | 44.8 | 9.2 | 154.3 | 1.59배 이득 |

### H1 반증 — `auto` 를 빼도 똑같다

| 무효화 | `cv-auto` (`auto 73px`) | `cv-fixed` (`73px`) | 차이 |
|---|---:|---:|---:|
| `width` | 32.4ms | 33.5ms | 3% |
| `offset` | 45.0ms | 42.1ms | 6% |
| `color` | 34.8ms | 37.7ms | 8% |

**전부 반복 간 편차(±20%)보다 작다.** 두 번 독립 실행해도 같았다
(1차: 4.13 / 4.09 · 2차: 4.05 / 4.19 ms/회).

> `auto` 키워드가 "렌더된 크기를 기억한다"는 건 맞지만, **그 기억이 O(N) 을 만드는 게 아니다.**
> C1 에서 세운 가설([C1 §6](../c1-initial-load/RESULTS.md#6-그래서-a4-와-왜-다른가--가설))은 틀렸다.

### H1′ 도 반증 — 폭 변경만의 문제가 아니다

폭을 전혀 건드리지 않는 `offset` 에서도 `cv` 는 N 에 비례해서 커진다.

| 무효화 | 모드 | N=500→4,000 (8배) | 스케일링 지수 |
|---|---|---:|---:|
| `width` | `plain` | 6.16배 | 0.87 |
| | `cv-auto` | 3.61배 | **0.62** |
| `offset` | `plain` | 5.78배 | 0.84 |
| | `cv-auto` | 5.32배 | **0.80** ← 거의 안 줄었다 |

`width` 에서는 지수가 0.87 → 0.62 로 떨어지지만, `offset` 에서는 0.84 → 0.80 으로 **사실상 그대로**다.

## 2. 예측 못 한 것 — Layout 패스 횟수가 늘어난다

표에서 제일 눈에 띄는 건 시간이 아니라 **횟수**다.

| 무효화 | `plain` | `cv-auto` | |
|---|---:|---:|---|
| `width` | 8회 | 9회 | 같다 |
| `offset` | 8회 | **17회** | **2배** |
| `color` | **0회** | **9회** | **없던 게 생겼다** |

- **세로로 밀기만 해도** `content-visibility` 는 레이아웃을 **두 번** 돈다.
  한 번 배치한 뒤, 어떤 항목이 뷰포트에 가까워졌는지 다시 판정하고, 그 결과로 또 배치한다.
- **색만 바꿔도** 레이아웃이 9번 생긴다. `plain` 은 **0번**이다 — 페인트만 하면 되는 변경이다.

그래서 `offset` 에서 Layout 은 `plain` 23.4ms → `cv` 45.0ms 로 **1.9배 비싸진다.**

### 그런데 전체로는 여전히 `cv` 가 이긴다

Layout 만 보면 손해인데 파이프라인 **전체 합계**는 세 경우 모두 `cv` 가 싸다 (4.83 / 2.18 / 1.75배).

**이득이 Layout 이 아니라 Style 에서 나오기 때문이다.**

| 무효화 | Style `plain` → `cv` | Layout `plain` → `cv` |
|---|---|---|
| `width` | 222.4 → 54.3 (**−76%**) | 265.9 → 32.4 (−88%) |
| `offset` | 226.4 → 65.5 (**−71%**) | 23.4 → 45.0 (**+92%**) |
| `color` | 221.9 → 58.3 (**−74%**) | 0.0 → 34.8 (**+∞**) |

**Style 절감은 무효화 종류와 무관하게 일정하다(−71~76%). 흔들리는 건 Layout 쪽이다.**

A4 에서 나는 *"Layout 87% 절감"* 을 앞세웠는데, 그건 **폭 변경이라는 한 가지 무효화에서만** 성립한다.
무효화 종류를 바꾸면 Layout 절감은 사라지거나 역전되고, **끝까지 남는 건 Style 절감**이다.

> ⚠️ **한계** — 세 무효화 모두 `:root` 의 **CSS 커스텀 프로퍼티**를 바꾼다. 커스텀 프로퍼티는 상속되므로
> 트리 전체의 스타일을 무효화하는 **최악의 경우**다. 그래서 `plain` 의 Style 220ms 는 절대값으로는 과장돼 있다.
> 다만 세 무효화가 **같은 방식**을 쓰므로 무효화끼리의 비교는 그대로 유효하다.
> `#list.style.width` 를 직접 건드리는 방식으로 다시 재면 Style 절대값은 훨씬 작아질 것이다. (미측정)

## 3. ② 점프형 스크롤 — 기전은 맞았고, 현상이 재현되지 않았다

### 판별 방법

추정값만 다르게 두고(`auto` 키워드는 양쪽 유지), **실제로 렌더 상태가 된 항목 수**를
`contentvisibilityautostatechange` 이벤트로 **브라우저에게 직접 물어봤다.** 추정하지 않았다.

| N | 추정값 | 패턴 | Layout ms | Paint회 | Raster회 | **렌더된 항목** |
|---:|---|---|---:|---:|---:|---:|
| 4,000 | 118px (41% 과대) | 점프형 | 442.4 | 99 | 664 | 1,041 |
| | **73px (정확)** | 점프형 | **381.9** | 107 | 703 | **1,227** |
| | 118px (41% 과대) | 연속형 | 701.4 | 122 | 110 | 181 |
| | **73px (정확)** | 연속형 | 732.3 | 82 | 136 | 181 |
| 8,000 | 118px (41% 과대) | 점프형 | 1,958.1 | 99 | 689 | 1,088 |
| | **73px (정확)** | 점프형 | **1,384.6** | 99 | 703 | **1,227** |
| | 118px (41% 과대) | 연속형 | 2,069.2 | 122 | 80 | 181 |
| | **73px (정확)** | 연속형 | **1,770.6** | 82 | 98 | 181 |

### H2 의 기전은 맞았다

정확한 값이 **더 많은 항목을 실제로 렌더한다.**

| N | 118px 과대 | 73px 정확 | |
|---:|---:|---:|---|
| 4,000 | 1,041개 | 1,227개 | **+18%** |
| 8,000 | 1,088개 | 1,227개 | **+13%** |

추정 높이를 41% 부풀리면 한 번의 점프가 **가상의 거리**를 더 많이 건너뛰므로,
같은 40단계라도 **실제 화면을 통과하는 항목이 적다.** 예측한 대로였다.
(연속형은 이동 거리가 18,000px 로 고정이라 양쪽 다 **181개**로 정확히 같다 — 설계대로 작동했다는 확인이다.)

### 그런데 H2 의 전제가 무너졌다

H2 는 *"정확한 값이 **느렸던** 건 일을 더 해서다"* 라는 주장이었다.
그런데 **정확한 값이 느리지 않다.** 네 조건 중 세 개에서 오히려 **빠르다.**

| N | 패턴 | 118px → 73px |
|---:|---|---|
| 4,000 | 점프형 | 442.4 → 381.9 ms (**1.16배 빠름**) |
| 8,000 | 점프형 | 1,958.1 → 1,384.6 ms (**1.41배 빠름**) |
| 8,000 | 연속형 | 2,069.2 → 1,770.6 ms (1.17배 빠름) |
| 4,000 | 연속형 | 701.4 → 732.3 ms (1.04배 느림 — 노이즈 범위) |

**13~18% 더 많이 렌더하면서도 더 빠르다.**

이유는 `auto` 의 기억값에 있다. 과대 추정하면 `scrollHeight` 가 계속 **틀린 채로 갱신된다** —
N=8,000 에서 진짜 높이는 872,328px 인데 118px 모드는 점프 후 **1,184,725px**, 연속 스크롤 후
**1,224,264px** 로 값이 계속 움직인다. 항목이 렌더될 때마다 기억값을 고쳐 쓰고,
그때마다 문서 높이가 바뀌어 다시 레이아웃이 걸린다.
정확한 값(73px)은 873,864px 로 **처음부터 맞아서 고칠 게 없다.**

> ⚠️ 이 표만 보면 *"정확한 값이 점프형에서도 빠르다"* 고 말하고 싶어진다. **그렇게 결론내지 않는다** —
> [§5](#5-a4b-와의-충돌을-좁혔다--재현되는-건-paint-뿐이다) 에서 같은 비교를 네 번 해보니
> 과대 추정 쪽 측정값이 **5.3배 범위로 흩어진다.** 점프형에서 두 값의 우열은 **측정할 수 없다.**
> **연속형에서는** 정확한 값이 일관되게 낫다 (A4b 1.78배 · C2 1.17배).

### A4b 와 정면으로 충돌한다

같은 N=8,000, 같은 40단계 점프, **바이트 단위로 같은 스크롤 함수**인데 결과가 반대다.

| N=8,000 · 점프형 | [A4b](../../track-a/a4-content-visibility/RESULTS-scroll.md) | **C2 (이번)** |
|---|---:|---:|
| 118px 과대 · Layout | 611.9 ms | 1,958.1 ms |
| **73px 정확** · Layout | **1,132.1 ms** | **1,384.6 ms** |
| 73px 정확 · **Paint 회수** | **1,315회** | **99회** |
| 결론 | 정확한 값이 **1.85배 나쁨** | 정확한 값이 **1.41배 좋음** |

A4b 쪽도 노이즈가 아니다 — 3회 반복에서 Paint 가 1316 / 1314 / 1316 으로 **거의 완전히 재현**된다.
양쪽 다 재현성 있는 측정인데 결론이 반대다. 둘 중 하나에 **숨은 변수**가 있다는 뜻이다.

**→ 하네스를 교차시켜 변수를 좁혔다. [§5](#5-a4b-와의-충돌을-좁혔다--재현되는-건-paint-뿐이다)**

## 4. ③ commit 선형성 — 판정 보류. 대신 측정법이 틀렸다는 걸 찾았다

### 먼저 나온 것: 이 디스플레이는 120Hz 다

레이어 수를 바꿔가며 rAF 프레임 간격을 직접 쟀다 ([probe-layers.mjs](probe-layers.mjs)).

| 요청 | 실제 박스 | **합성 레이어** | 평균 FPS | 프레임 간격 중앙값 / p95 |
|---:|---:|---:|---:|---:|
| 500 | 500 | 504 | 120.0 | **8.3** / 9 ms |
| 750 | 750 | 754 | 118.6 | **8.4** / 10 ms |
| 1,000 | 1,000 | 1,004 | 61.1 | **16.3** / 25.4 ms |
| 1,500 | 1,500 | 1,504 | 19.4 | **39.9** / 134.1 ms |
| 2,000 | 2,000 | 2,004 | 27.5 | 36.9 / 53.4 ms |

두 가지가 동시에 확인된다.

1. **레이어 = 박스 + 4.** 2,000개까지 승격 거부가 없다 — [A1b 의 "승격 한계 없음"](../../track-a/a1-pipeline-skip/RESULTS-b.md)이 다시 확인됐다.
2. **프레임 간격이 8.3ms 의 배수로 떨어진다** (8.3 → 16.3 → 39.9). 이 화면은 **120Hz** 이고
   메인 스레드 rAF 는 **vsync 에 묶여 있다.**

### 그래서 A1b 의 "commit 7.0배"는 못 쓰는 숫자다

A1b 는 프레임당 비용을 `Commit 총합 ÷ 프레임 수` 로 구했다.
그런데 프레임 수가 vsync 배수로 **양자화**되므로, 이 값은 레이어 수가 아니라 **양자화 계단**을 잰다.

실제로 같은 방식으로 다시 재니 **1,500 에서 값이 거꾸로 꺾였다**(1,000 의 1.128ms → 1,500 의 0.671ms).
프레임 수가 107 → 154 로 **늘어난** 탓이다. 레이어가 늘었는데 프레임이 늘 수는 없다.

### 세 가지 방법으로 재봤지만 전부 선형에 못 미친다

`Commit` 개별 이벤트의 지속시간 분포를 직접 보고, vsync 까지 꺼봤다.

| 측정 방법 | R² (중앙값 적합) |
|---|---:|
| 프레임당 비용 (`총합 ÷ 프레임수`) | 0.735 |
| 개별 이벤트 중앙값 | **0.155** |
| 개별 이벤트 중앙값 · **vsync 끔** | **0.640** |

vsync 를 끈 쪽이 확실히 안정적이다 — `Commit` 이 3초에 1,362회 찍히고(=454/s, 120Hz 를 한참 넘는다)
평균과 중앙값이 거의 붙는다(0.094 vs 0.082). 그런데도 선형은 아니다.

| 레이어 | Commit 수 | 중앙값 ms | **레이어당 µs** |
|---:|---:|---:|---:|
| 100 | 1,362 | 0.082 | 0.82 |
| 250 | 885 | 0.108 | 0.43 |
| 500 | 270 | 0.296 | 0.59 |
| 750 | 181 | 0.391 | 0.52 |
| 1,000 | 209 | 0.335 | 0.33 |
| 1,500 | 141 | 0.539 | 0.36 |
| **2,000** | **49** | **3.700** | **1.85** |

**250~1,500 구간은 레이어당 0.33~0.59µs 로 거의 일정하다** — 이 구간만 적합하면 R² = 0.845,
기울기 0.299µs/레이어. 여기까지는 선형에 가깝다.

**2,000 에서 무너진다.** 레이어당 비용이 5배로 뛰고, 3초 동안 commit 이 **49회**밖에 안 찍힌다.
이 지점은 렌더러가 포화돼서 **측정 자체가 못 믿을 상태**다.

### 판정

| | |
|---|---|
| **H3** (선형, R² ≥ 0.95) | ❌ **미달** — 세 방법 모두 0.95 에 못 미친다 |
| **H3′** (임계점이 있다) | ⚠️ **확정 못 함** — 2,000 에서 꺾이지만 그게 실제 임계점인지 측정 포화인지 못 가린다 |

**판정 보류.** 다만 이번 라운드에서 확실해진 게 두 개 있다.

- **A1b 의 7.0배는 인용하면 안 된다.** vsync 양자화가 섞인 값이다.
  "레이어가 늘면 commit 이 비싸진다"는 방향은 맞지만 배율은 못 믿는다.
- **2,000 레이어 근처에 뭔가 있다.** [A2 에서 확인한 타일 메모리 예산 512MB](../../track-a/a2-gpu-memory/RESULTS-source.md)
  와 관련이 있을 수 있다 — 2,004개 레이어의 타일이 예산을 넘겨 축출이 시작되는 지점일지도. **미검증 가설이다.**

> 제대로 답하려면 프레임 수에 기대지 않는 설계가 필요하다 —
> 예를 들어 레이어 수를 고정한 채 **commit 을 N번 강제**하고 그 N번의 분포만 보는 식.

## 5. A4b 와의 충돌을 좁혔다 — 재현되는 건 Paint 뿐이다

두 하네스의 스크롤 함수가 **바이트 단위로 같은데** 결론이 반대였다. 변수를 하나씩 없앴다.

### 1단계 — 런치 인자를 의심했다 (기각)

유일하게 다른 인자는 `--hide-scrollbars` 였다. A4 의 측정 스크립트엔 없고 C2 엔 있다.
하네스 × 스크롤바로 교차시켰다 (N=8,000, 73px, 점프형).

| 하네스 | 스크롤바 | `innerW`/`clientW` | Layout ms | **Paint회** | Raster회 |
|---|---|---|---:|---:|---:|
| A4 | 보임 | 1254 / 1239 | 1,512.5 | **1,315** | 697 |
| A4 | 숨김 | 1254 / 1254 | 1,000.6 | **1,290** | 697 |
| C2 | 보임 | 1254 / 1239 | 1,029.2 | **99** | 703 |
| C2 | 숨김 | 1254 / 1254 | 874.8 | **99** | 703 |

**스크롤바는 원인이 아니다.** A4 하네스는 스크롤바를 숨겨도 Paint 가 1,290회 나온다.
원인은 **하네스 쪽**이다.

### 2단계 — 그런데 Raster 는 같다

Paint 이벤트가 13배 차이 나는데 **RasterTask 는 697 vs 703 으로 사실상 같다.**
같은 픽셀을 만들면서 Paint 이벤트만 잘게 쪼개져 기록된다는 뜻이다.
**`Paint` 이벤트 횟수는 작업량의 대리 지표가 아니다.**

A4b 가 *"`Paint` 가 13배 뛰는 게 단서"* 라고 적은 그 단서는, **일이 13배 늘었다는 뜻이 아니었다.**

### 3단계 — 같은 실행 안에서 두 값을 맞붙였다

A4b 의 비교를 **한 번의 실행 안에서** 두 하네스 각각에 대해 다시 했다
(N=8,000, 점프형, 스크롤바 숨김, [probe-harness.mjs](probe-harness.mjs)).

| 하네스 | 추정값 | Layout ms | Style ms | Paint회 | Raster회 | 118px → 73px |
|---|---|---:|---:|---:|---:|---|
| **A4** | 118px 과대 | 3,254.5 | 327.4 | 97 | 690 | — |
| **A4** | **73px 정확** | **1,244.6** | 201.6 | 1,290 | 697 | **2.61배 빠름** |
| **C2** | 118px 과대 | 1,695.3 | 157.6 | 99 | 690 | — |
| **C2** | **73px 정확** | 1,765.7 | 165.8 | 99 | 703 | 0.96배 (무승부) |

A4 자기 하네스에서는 **정확한 값이 2.6배 빠르다.** C2 하네스에서는 **무승부**(4% 차, 노이즈 범위).
어느 쪽도 A4b 의 *"정확한 값이 1.85배 나쁘다"* 를 재현하지 않는다.

### 무엇이 재현되고 무엇이 안 되는가

| 지표 | A4b 원자료 | 이번 재측정 | 재현? |
|---|---:|---:|---|
| 118px · Paint회 | 97 | 97 | ✅ 완전 일치 |
| 118px · Raster회 | 692 | 690 | ✅ |
| 73px · Paint회 | 1,315 | 1,290 | ✅ |
| 73px · Raster회 | 697 | 697 | ✅ 완전 일치 |
| 73px · **Layout ms** | 1,132.1 | 1,244.6 | ✅ 10% 이내 |
| **118px · Layout ms** | **611.9** | **3,254.5** | ❌ **5.3배** |

**딱 하나가 재현되지 않는다 — 과대 추정(118px) 설정의 Layout 시간.**
나머지 다섯 지표는 전부 맞는다. A4b 안에서도 3회 반복이 570/586/596ms 로 촘촘했으니
**세션 안에서는 안정적이고 세션을 바꾸면 흔들리는** 값이다.

네 번의 독립 측정에서 118px 의 Layout 은 **5.3배 범위**로 흩어진다. 73px 은 1.6배 안에 모인다.

| 측정 | 118px 과대 | 73px 정확 | 비 |
|---|---:|---:|---|
| A4b 원본 | **611.9** | 1,132.1 | 1.85배 나쁨 |
| C2 §3 (N=8,000) | 1,958.1 | 1,384.6 | 1.41배 좋음 |
| 2×2 · A4 하네스 | **3,254.5** | 1,244.6 | 2.61배 좋음 |
| 2×2 · C2 하네스 | 1,695.3 | 1,765.7 | 무승부 |
| **흩어진 범위** | **611.9 ~ 3,254.5 (5.3배)** | **1,132 ~ 1,766 (1.6배)** | |

**넷 중 셋이 "정확한 값이 좋거나 비긴다" 쪽이고, 흔들리는 축은 과대 추정 쪽이다.**

### 왜 과대 추정만 불안정한가

`auto` 는 렌더된 항목의 실제 크기를 기억하고 추정을 **계속 고쳐 쓴다.**
과대 추정이면 고칠 게 많아서 `scrollHeight` 가 측정 내내 움직인다 —
N=8,000 에서 진짜 872,328px 인데 점프 후 **1,184,725px**, 연속 스크롤 후 **1,224,264px**.

문서 높이가 움직이면 `scrollTop = max × (i/40)` 가 매번 **다른 지점**을 가리킨다.
같은 스크립트가 실행할 때마다 다른 일을 하는 것이다.
정확한 값(73px)은 873,864px 로 처음부터 맞아서 고칠 게 없고, 그래서 **재현된다.**

> **결론** — A4b 의 *"점프형에서 정확한 값이 1.85배 나쁘다"* 는 **채택하지 않는다.**
> 그 비교의 기준이던 118px 측정값이 세션 간 **5.3배로 흔들리기 때문**이고,
> 네 번의 독립 측정 중 A4b 만 그 방향이다.
>
> 다만 **"정확한 값이 점프형에서 빠르다"고 뒤집어 주장하지도 않는다** — 2×2 의 C2 하네스는 무승부였다.
> 정직한 서술은 이것이다: **점프형 스크롤에서 두 값의 우열은 측정할 수 없다.**
> 과대 추정 설정 자체가 재현 가능한 측정 대상이 아니기 때문이다.
>
> A4b 의 *"연속형이 현실에 맞는 조건"* 이라는 방법론 결론은 그대로 유효하고,
> **연속형에서는 정확한 값이 일관되게 낫다** (A4b 1.78배 · C2 1.17배).

## 6. 사전 등록 주장 판정

| # | 주장 | 판정 | 실측 |
|---|---|---|---|
| **H1** | `auto` 키워드가 A4 의 O(N) 원인 | ❌ **반증** | `auto 73px` vs `73px` 차이 **3~8%** — 반복 편차 이하 |
| **H1′** | 폭 변경 자체가 원인 | ❌ **반증** | 폭을 안 바꾸는 `offset` 에서도 지수 0.80 (plain 0.84) |
| **H2** | 정확한 값이 통과 항목 **1.5배 이상** 많다 | ⚠️ **방향만** | +13~18% (1.5배 미달) |
| **H2 전제** | 정확한 값이 점프형에서 **느리다** | ❌ **반증** | 4번 재봐서 A4b 만 그 방향. 다만 우열 자체가 **측정 불가**(과대 추정 쪽이 5.3배 산포) |
| **H3** | commit 은 선형, R² ≥ 0.95 | ❌ **미달** | 세 방법 모두 < 0.95 (0.735 / 0.155 / 0.640) |
| **H3′** | 임계점이 있다 | ⚠️ **확정 못 함** | 2,000 에서 꺾이나 측정 포화와 구분 불가 |

**사전 등록한 것 중 맞은 게 하나도 없다.** 예측할 때 *"세 개 다 단순한 설명이 맞다는 쪽에 걸었다.
하나라도 빗나가면 그게 더 흥미로운 결과다"* 라고 적었는데, 셋 다 빗나갔다.

그 대신 **예측하지 않았던 것 세 개**를 얻었다.

1. `content-visibility` 의 이득은 **Layout 이 아니라 Style** 에서 나온다 (§2)
2. 무효화 종류에 따라 **레이아웃 패스 횟수가 2배로 늘거나 없던 게 생긴다** (§2)
3. 이 환경은 **120Hz** 이고, 그 탓에 [A1b 의 "commit 7.0배"](../../track-a/a1-pipeline-skip/RESULTS-b.md)가 못 쓰는 숫자다 (§4)

## 7. 한계

- **`:root` 커스텀 프로퍼티로 무효화했다.** 상속되므로 트리 전체 스타일을 무효화하는 **최악의 경우**다.
  무효화끼리의 비교는 유효하지만 `plain` 의 Style 220ms 는 절대값으로 과장돼 있다
- **N 을 500 과 4,000 두 점만 썼다.** 스케일링 지수는 두 점 기울기라 신뢰구간이 넓다
- **③ 은 프레임 수에 의존하는 설계였다.** 프레임 수 자체가 측정 대상의 함수라 순환이 생겼다
- 항목 구조가 한 종류다. 실제 웹사이트가 아니라 합성 리스트다
- headless · GPU 가속 켜짐 · Ganesh 백엔드 · Chrome 152 단일 엔진

## 8. 자가 평가

**통과**

- **가설 세 개를 전부 틀렸는데, 그게 이번 라운드의 값어치다.** `auto` 키워드를 의심한 건
  C1 에서 세운 그럴듯한 이야기였고, 직교 격자로 재보니 **아무 차이도 없었다.**
  모드와 무효화를 묶어둔 채로는 영영 몰랐을 것이다
- **`color` 를 대조군으로 넣은 게 결정적이었다.** 처음엔 "폭을 안 바꾸는 무효화 = 색 변경" 으로
  잡았다가, 색은 레이아웃을 **아예 안 일으켜서** 아무것도 판별 못 한다는 걸 깨닫고 `offset` 을 추가했다.
  그리고 정작 그 `color` 대조군이 **`plain` 0회 → `cv` 9회**라는 제일 놀라운 숫자를 내놨다
- **③ 을 못 풀었다고 적는 게 맞다.** R² 0.64 를 "비선형 확인" 으로 포장할 수 있었지만,
  1,000 레이어에서 값이 꺼지는 걸 설명 못 하는 채로 결론을 내면 A1b 의 실수를 반복하는 것이다.
  대신 **A1b 의 숫자가 왜 못 믿을 값인지**는 확실히 보였다
- **A4b 와 정면으로 충돌하는 결과를 덮지 않았다.** 하네스를 교차시켜 원인까지 좁혔다 (§5)

**부족**

- N 두 점은 인색했다. 네 점이었으면 지수를 제대로 말할 수 있었다
- ③ 을 위한 올바른 설계(프레임 수에 안 기대는 방식)를 끝내 못 만들었다
