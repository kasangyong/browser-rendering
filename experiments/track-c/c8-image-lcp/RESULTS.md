## 한 줄

**예측이 틀렸다.** `content-visibility` 는 이미지 LCP 도 12~38% 앞당겼다.
그런데 **다운로드가 빨라진 게 아니라 요청이 일찍 나갔다** — 그리고 그건 LCP 이미지가 `loading="lazy"` 였기 때문이다.

## 1. 연기 테스트가 설계 결함을 잡았다

[C7 의 "캐시를 데운 뒤 잰다"](../c7-real-initial-load/PREDICTION.md) 를 그대로 가져왔더니 **FCP = LCP 가 또 나왔다.**
LCP 요소는 제대로 `<img>` 인데도.

```
cv-auto   FCP 684.3  LCP 684.3  이미지<img>  Layout  52.28
plain     FCP 595.3  LCP 595.3  이미지<img>  Layout 198.42
```

캐시가 따뜻하면 **이미지도 캐시돼 있어서** 첫 컨텐츠 프레임에 같이 그려진다.

> 문서 사이트에서 네트워크는 **잡음**이었다. 이미지 LCP 에서는 **현상 그 자체**다.
> 다운로드를 지워버리면 재려던 걸 지우는 것이다.

데이터 수집 **전에** 캐시 상태를 축으로 올렸다 — `warm`(C7 동일) / `cold`(빈 프로필 첫 로드).
[PREDICTION.md 부칙](PREDICTION.md#부칙--측정-전-설계-변경-2026-09-18-본-측정-시작-전) 에 그 경위를 남겼다.

## 4. 왜 빨라졌나 — 다운로드가 빨라진 게 아니다

LCP 이미지의 리소스 타이밍을 직접 봤다. ms · 중앙값

| 사이트 | 캐시 | 모드 | 요청 시작 | 응답 끝 | 전송 시간 | 바이트 | LCP |
|---|---|---|---:|---:|---:|---:|---:|
| Grand Canyon | cold | plain | 1835 | 2111 | 276 | 38,064 | 2224 |
| | | cv-auto | **1256** | 1376 | 120 | 38,064 | **1597** |
| Milky Way | cold | plain | 2094 | 2221 | 127 | 19,938 | 2349 |
| | | cv-auto | **1560** | 1674 | 114 | 19,938 | **1935** |
| Mount Everest | cold | plain | 2114 | 2226 | 112 | 28,194 | 2346 |
| | | cv-auto | **1699** | 1827 | 127 | 28,194 | **2064** |

**바이트가 같다. 전송 시간도 사실상 같다.** 달라진 건 **요청 시작 시각**뿐이다 — 400~580ms 앞당겨졌다.

`content-visibility` 는 네트워크를 건드리지 않는다. 그런데 요청이 일찍 나갔다.

### 이미지 요청이 왜 1.8초나 뒤에 나가나

프리로드 스캐너가 있으면 훨씬 일찍 나갔어야 한다. [probe-why.mjs](probe-why.mjs) 로 봤다.

| 관측 | plain | cv-auto |
|---|---|---|
| LCP 이미지의 `loading` | **`lazy`** (세 곳 전부) | **`lazy`** |
| 요청된 이미지 수 / 전체 (lazy) | 10/69(63) · 6/46(43) · 18/233(226) | **완전히 동일** |
| 요청된 이미지 바이트 | 110KB · 81KB · 87KB | **완전히 동일** |
| LCP 이미지 위치 | top 369·340·465px (뷰포트 844px 안) | 동일 |

**"cv 가 화면 밖 이미지 요청을 줄여 경쟁이 완화된다" 가설은 틀렸다.** 요청 수도 바이트도 똑같다.

남는 설명은 하나다:

> `loading="lazy"` 이미지는 **"뷰포트 안인가"** 를 알아야 요청이 나간다.
> 그건 **레이아웃을 해야 안다.** 레이아웃이 요청의 선행 조건이다.
> cv 가 레이아웃을 52~74% 줄이면 그 판정이 앞당겨지고, 요청이 먼저 나가고, LCP 가 빨라진다.

이게 맞다면 **`content-visibility` 는 이미지 LCP 를 직접 빠르게 하지 않는다.**
lazy 이미지의 **요청 발사 시점을 앞당겨** 간접적으로 빠르게 하는 것이다.

이 설명은 추측으로 두면 안 된다. → [5. 반증 테스트](#5-반증-테스트--lazy-를-끄면-효과가-사라지는가)

## 5. 반증 테스트 — lazy 를 끄면 효과가 사라지는가

> 측정 [measure-lazy.mjs](measure-lazy.mjs) · 집계 [analyze-lazy.mjs](analyze-lazy.mjs) · 60회 (3곳 × 2모드 × lazy/eager × 5회), 콜드 캐시, 실패 0건

HTML 을 가로챌 때 `loading="lazy"` 를 `loading="eager"` 로 전부 바꿨다 (`lazy남음 0/69`·`0/46`·`0/233` 으로 확인).
가설이 맞으면 **eager 에서 cv 의 LCP 개선이 사라져야 한다.**

### LCP 로 보면 2 대 1 로 갈린다

| 사이트 | lazy | eager | |
|---|---:|---:|---|
| Grand Canyon | −13% | **+5%** | 개선이 사라졌다 |
| Mount Everest | −23% | **−9%** | 개선이 사라졌다 |
| Milky Way | −5% | −21% | 반대로 나왔다 |

Milky Way 는 **lazy 팔에서부터 개선이 안 나왔다(−5%).** 그 사이트에서는 대조 자체가 성립하지 않았다.
이 실행의 LCP 흩어짐은 1.3~1.6배이고 효과 크기가 그와 비슷하다 — **LCP 만으로는 판정이 안 된다.**

### 요청 시작으로 보면 3 대 0 이다

LCP 가 아니라 **가설이 직접 예측하는 양**(요청 시작 시각)을 보면 깨끗하다.

| 실행 | 사이트 | 이미지 | Layout 절감 | 요청 앞당김 |
|---|---|---|---:|---:|
| C8 본측정 | Grand Canyon | lazy | 354ms | **+579ms** |
| C8 본측정 | Milky Way | lazy | 402ms | **+534ms** |
| C8 본측정 | Mount Everest | lazy | 332ms | **+414ms** |
| C8b 반증 | Grand Canyon | lazy | 57ms | **+149ms** |
| C8b 반증 | Milky Way | lazy | 104ms | **+73ms** |
| C8b 반증 | Mount Everest | lazy | 98ms | **+59ms** |
| C8b 반증 | Grand Canyon | **eager** | 65ms | **−106ms** |
| C8b 반증 | Milky Way | **eager** | 134ms | **+47ms** |
| C8b 반증 | Mount Everest | **eager** | 118ms | **−98ms** |

- **lazy 6점은 전부 양수.** Layout 을 많이 아낄수록 요청이 많이 앞당겨진다 (r = 0.95)
- **eager 3점은 평균 −52ms.** Layout 절감은 lazy 쪽(57~104ms)과 비슷한데도 요청이 안 앞당겨진다

> **같은 레이아웃 절감이어도, 요청이 앞당겨지는 건 이미지가 `lazy` 일 때뿐이다.**

r = 0.95 는 6점이 두 덩어리(본측정 / 반증실행)로 갈려 있어 그 사이 간격이 만든 값이다.
덩어리 안에서는 그만큼 깨끗하지 않다. 방향과 자릿수만 읽어야 한다.
**진짜 증거는 상관이 아니라 lazy/eager 대조**다 — 같은 실행, 섞인 순서, 부호가 뒤집힌다.

### 곁가지 — eager 는 공짜가 아니다

`eager` 는 요청을 확실히 앞당긴다(plain 기준 1026→728, 1233→856, 1271→884ms).
그런데 LCP 는 그만큼 안 줄었다(−8%, −2%, −23%). 전송이 길어졌기 때문이다:

| | 요청 시작 | 응답 끝 | 전송 |
|---|---:|---:|---:|
| Grand Canyon plain lazy | 1026 | 1149 | 123ms |
| Grand Canyon plain eager | 728 | 1031 | **303ms** |

lazy 를 끄면 화면 밖 이미지 60여 개가 한꺼번에 경쟁한다. 먼저 나가도 늦게 끝난다.

### Layout 절감은 이미지 정책과 무관했다

| 사이트 | lazy | eager |
|---|---:|---:|
| Milky Way | −66% | −72% |
| Grand Canyon | −59% | −61% |
| Mount Everest | −61% | −64% |

**S10 성립.** `content-visibility` 가 아끼는 레이아웃 일 자체는 이미지 로딩 정책과 상관없다.
달라지는 건 **그 절감이 LCP 로 이어지는 경로**다.

### 판정

| # | 주장 | 판정 |
|---|---|---|
| S8 | eager 에서 cv 의 LCP 개선이 사라진다 | **부분 성립** — LCP 로는 2/3, 요청 시작으로는 3/3 |
| S9 | eager 가 plain 의 LCP 를 크게 앞당긴다 | **부분 성립** — 요청은 300~400ms 앞당기나 전송이 길어져 LCP 는 2~23% |
| S10 | eager 에서도 Layout 절감은 그대로 | **성립** — 59~66% vs 61~72% |

### 두 실행을 가로질러 비교하면 안 된다

같은 `cold·plain` 조건인데 Layout 이 본측정 478~643ms, 반증실행 97~161ms 로 **4배 차이**가 났다.
LCP 도 2.2~2.3초에서 1.2~1.8초로 내려갔다. 그 사이 네트워크가 달라졌다.

로드 중 Layout 은 고정 비용이 아니다 — **리소스가 도착할 때마다 다시 도는 양**이라
네트워크가 빠르면 그 횟수 자체가 줄어든다. 위 표에서 실행을 나눠 적은 이유다.

`cold` 는 네트워크가 통째로 들어오므로 흩어짐이 크다. 반복별 LCP (ms, 정렬):

## 9. 남은 것

- **동적 페이지.** 여기 세 곳은 여전히 위키다. 커머스·SNS 는 스크립트가 지배할 것이다
- **cv-auto 의 cold Layout 절감(52~65%)이 warm(82~90%)보다 작은 이유.** 이미지 도착마다 리레이아웃이 도는 것으로 보이는데 계수하지 않았다
- **다른 브라우저.** Safari 는 `content-visibility` 를 17.4 에서 넣었고 lazy 정책도 다르다
