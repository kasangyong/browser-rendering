# C8 — LCP 가 이미지일 때

> 사전 등록 → [PREDICTION.md](PREDICTION.md) · 측정 [measure.mjs](measure.mjs) · 집계 [analyze.mjs](analyze.mjs)
> **결과 파일에 남은 측정 759행** (`*.json` 전수 합계 · warm 조건은 행마다 로드 2회).
> 본측정 72 · 반증 60 · eager 실제판 60 · 비싼 eager 36 · **A 정밀 80** · **warm 80** ·
> FCP 비용 40 · auto 대조 60 · **용량-반응 80** · **DCL 기준 80** · 다운로드 24 · 순서 14 · 그 외 사전 조사·분해 73.
> 덮어쓴 사전 조사 스윕과 실패한 실행은 안 셌다. 2026-09-18 ~ 20.

## 한 줄

**예측이 틀렸다.** `content-visibility` 는 이미지 LCP 도 12~38% 앞당겼다.
그런데 **다운로드가 빨라진 게 아니라 요청이 일찍 나갔다** — 그리고 그건 LCP 이미지가 `loading="lazy"` 였기 때문이다.

`eager` 가 실제인 사이트(Wikivoyage 3곳)에서 다시 재보니 **기전은 확인됐지만 이득은 없었다.**
요청이 첫 레이아웃 **전에** 나가고(14/14), 레이아웃 예산도 30~70ms 뿐이라 앞당길 게 없다.

> `content-visibility` 가 이미지 LCP 를 앞당기려면 **둘 다** 필요하다 —
> ① LCP 이미지가 `lazy` ② 레이아웃 비용이 수백 ms.

②만 만족하는 페이지(Turku · Layout 876ms)도 찾아서 쟀다. **레이아웃을 424ms 아꼈는데 요청이 38ms 밀렸다.**
같은 규모를 아낀 lazy 페이지에서는 579ms 앞당겨졌다. 네 칸을 다 채웠고, 효과는 한 칸에만 있다.

그다음 "왜 LCP 가 안 움직이나" 를 트레이스 바닥까지 팠다. 결론은 한 문장이다:

> **`content-visibility` 는 렌더링 대기를 확실히 줄인다(−320~−506ms, 신뢰구간이 0 제외).
> 그런데 그게 절대 LCP 로는 안 나타난다** — 콜드에서는 네트워크 변동(±600ms)에 묻히고,
> warm 에서는 **cv 자신이 첫 페인트를 160~248ms 늦춰서** 상쇄된다.

## 1. 연기 테스트가 설계 결함을 잡았다

[C7 의 "캐시를 데운 뒤 잰다"](../c7-real-initial-load/PREDICTION.md) 를 그대로 가져왔더니 **FCP = LCP 가 또 나왔다.**
LCP 요소는 제대로 `<img>` 인데도.

```
cv-auto   FCP 684.3  LCP 684.3  이미지<img>  Layout  52.28
plain     FCP 595.3  LCP 595.3  이미지<img>  Layout 198.42
```

캐시가 따뜻하면 **이미지도 캐시돼 있어서** 첫 컨텐츠 프레임에 같이 그려진다.

> 문서 사이트에서 네트워크는 **잡음**이었다. 이미지 LCP 에서는 **현상 그 자체**다.
> 다운로드를 지워버리면 재려던 걸 지우는 것이다.

데이터 수집 **전에** 캐시 상태를 축으로 올렸다 — `warm`(C7 동일) / `cold`(빈 프로필 첫 로드).
[PREDICTION.md 부칙](PREDICTION.md#부칙--측정-전-설계-변경-2026-09-18-본-측정-시작-전) 에 그 경위를 남겼다.

## 4. 왜 빨라졌나 — 다운로드가 빨라진 게 아니다

LCP 이미지의 리소스 타이밍을 직접 봤다. ms · 중앙값

| 사이트 | 캐시 | 모드 | 요청 시작 | 응답 끝 | 전송 시간 | 바이트 | LCP |
|---|---|---|---:|---:|---:|---:|---:|
| Grand Canyon | cold | plain | 1835 | 2111 | 276 | 38,064 | 2224 |
| | | cv-auto | **1256** | 1376 | 120 | 38,064 | **1597** |
| Milky Way | cold | plain | 2094 | 2221 | 127 | 19,938 | 2349 |
| | | cv-auto | **1560** | 1674 | 114 | 19,938 | **1935** |
| Mount Everest | cold | plain | 2114 | 2226 | 112 | 28,194 | 2346 |
| | | cv-auto | **1699** | 1827 | 127 | 28,194 | **2064** |

**바이트가 같다. 전송 시간도 사실상 같다.** 달라진 건 **요청 시작 시각**뿐이다 — 400~580ms 앞당겨졌다.

`content-visibility` 는 네트워크를 건드리지 않는다. 그런데 요청이 일찍 나갔다.

### 이미지 요청이 왜 1.8초나 뒤에 나가나

프리로드 스캐너가 있으면 훨씬 일찍 나갔어야 한다. [probe-why.mjs](probe-why.mjs) 로 봤다.

| 관측 | plain | cv-auto |
|---|---|---|
| LCP 이미지의 `loading` | **`lazy`** (세 곳 전부) | **`lazy`** |
| 요청된 이미지 수 / 전체 (lazy) | 10/69(63) · 6/46(43) · 18/233(226) | **완전히 동일** |
| 요청된 이미지 바이트 | 110KB · 81KB · 87KB | **완전히 동일** |
| LCP 이미지 위치 | top 369·340·465px (뷰포트 844px 안) | 동일 |

**"cv 가 화면 밖 이미지 요청을 줄여 경쟁이 완화된다" 가설은 틀렸다.** 요청 수도 바이트도 똑같다.

남는 설명은 하나다:

> `loading="lazy"` 이미지는 **"뷰포트 안인가"** 를 알아야 요청이 나간다.
> 그건 **레이아웃을 해야 안다.** 레이아웃이 요청의 선행 조건이다.
> cv 가 레이아웃을 52~74% 줄이면 그 판정이 앞당겨지고, 요청이 먼저 나가고, LCP 가 빨라진다.

이게 맞다면 **`content-visibility` 는 이미지 LCP 를 직접 빠르게 하지 않는다.**
lazy 이미지의 **요청 발사 시점을 앞당겨** 간접적으로 빠르게 하는 것이다.

이 설명은 추측으로 두면 안 된다. → [5. 반증 테스트](#5-반증-테스트--lazy-를-끄면-효과가-사라지는가)

## 5. 반증 테스트 — lazy 를 끄면 효과가 사라지는가

> 측정 [measure-lazy.mjs](measure-lazy.mjs) · 집계 [analyze-lazy.mjs](analyze-lazy.mjs) · 60회 (3곳 × 2모드 × lazy/eager × 5회), 콜드 캐시, 실패 0건

HTML 을 가로챌 때 `loading="lazy"` 를 `loading="eager"` 로 전부 바꿨다 (`lazy남음 0/69`·`0/46`·`0/233` 으로 확인).
가설이 맞으면 **eager 에서 cv 의 LCP 개선이 사라져야 한다.**

### LCP 로 보면 2 대 1 로 갈린다

| 사이트 | lazy | eager | |
|---|---:|---:|---|
| Grand Canyon | −13% | **+5%** | 개선이 사라졌다 |
| Mount Everest | −23% | **−9%** | 개선이 사라졌다 |
| Milky Way | −5% | −21% | 반대로 나왔다 |

Milky Way 는 **lazy 팔에서부터 개선이 안 나왔다(−5%).** 그 사이트에서는 대조 자체가 성립하지 않았다.
이 실행의 LCP 흩어짐은 1.3~1.6배이고 효과 크기가 그와 비슷하다 — **LCP 만으로는 판정이 안 된다.**

### 요청 시작으로 보면 3 대 0 이다

LCP 가 아니라 **가설이 직접 예측하는 양**(요청 시작 시각)을 보면 깨끗하다.

| 실행 | 사이트 | 이미지 | Layout 절감 | 요청 앞당김 |
|---|---|---|---:|---:|
| C8 본측정 | Grand Canyon | lazy | 354ms | **+579ms** |
| C8 본측정 | Milky Way | lazy | 402ms | **+534ms** |
| C8 본측정 | Mount Everest | lazy | 332ms | **+414ms** |
| C8b 반증 | Grand Canyon | lazy | 57ms | **+149ms** |
| C8b 반증 | Milky Way | lazy | 104ms | **+73ms** |
| C8b 반증 | Mount Everest | lazy | 98ms | **+59ms** |
| C8b 반증 | Grand Canyon | **eager** | 65ms | **−106ms** |
| C8b 반증 | Milky Way | **eager** | 134ms | **+47ms** |
| C8b 반증 | Mount Everest | **eager** | 118ms | **−98ms** |

- **lazy 6점은 전부 양수.** Layout 을 많이 아낄수록 요청이 많이 앞당겨진다 (r = 0.95)
- **eager 3점은 평균 −52ms.** Layout 절감은 lazy 쪽(57~104ms)과 비슷한데도 요청이 안 앞당겨진다

> **같은 레이아웃 절감이어도, 요청이 앞당겨지는 건 이미지가 `lazy` 일 때뿐이다.**

r = 0.95 는 6점이 두 덩어리(본측정 / 반증실행)로 갈려 있어 그 사이 간격이 만든 값이다.
덩어리 안에서는 그만큼 깨끗하지 않다. 방향과 자릿수만 읽어야 한다.
**진짜 증거는 상관이 아니라 lazy/eager 대조**다 — 같은 실행, 섞인 순서, 부호가 뒤집힌다.

### 곁가지 — eager 는 공짜가 아니다

`eager` 는 요청을 확실히 앞당긴다(plain 기준 1026→728, 1233→856, 1271→884ms).
그런데 LCP 는 그만큼 안 줄었다(−8%, −2%, −23%). 전송이 길어졌기 때문이다:

| | 요청 시작 | 응답 끝 | 전송 |
|---|---:|---:|---:|
| Grand Canyon plain lazy | 1026 | 1149 | 123ms |
| Grand Canyon plain eager | 728 | 1031 | **303ms** |

lazy 를 끄면 화면 밖 이미지 60여 개가 한꺼번에 경쟁한다. 먼저 나가도 늦게 끝난다.

### Layout 절감은 이미지 정책과 무관했다

| 사이트 | lazy | eager |
|---|---:|---:|
| Milky Way | −66% | −72% |
| Grand Canyon | −59% | −61% |
| Mount Everest | −61% | −64% |

**S10 성립.** `content-visibility` 가 아끼는 레이아웃 일 자체는 이미지 로딩 정책과 상관없다.
달라지는 건 **그 절감이 LCP 로 이어지는 경로**다.

### 판정

| # | 주장 | 판정 |
|---|---|---|
| S8 | eager 에서 cv 의 LCP 개선이 사라진다 | **부분 성립** — LCP 로는 2/3, 요청 시작으로는 3/3 |
| S9 | eager 가 plain 의 LCP 를 크게 앞당긴다 | **부분 성립** — 요청은 300~400ms 앞당기나 전송이 길어져 LCP 는 2~23% |
| S10 | eager 에서도 Layout 절감은 그대로 | **성립** — 59~66% vs 61~72% |

### 두 실행을 가로질러 비교하면 안 된다

같은 `cold·plain` 조건인데 Layout 이 본측정 478~643ms, 반증실행 97~161ms 로 **4배 차이**가 났다.
LCP 도 2.2~2.3초에서 1.2~1.8초로 내려갔다. 그 사이 네트워크가 달라졌다.

로드 중 Layout 은 고정 비용이 아니다 — **리소스가 도착할 때마다 다시 도는 양**이라
네트워크가 빠르면 그 횟수 자체가 줄어든다. 위 표에서 실행을 나눠 적은 이유다.

## 6. C8c — `eager` 가 '실제'인 사이트에서 다시

> 사전 등록 [부칙 3](PREDICTION.md#부칙-3--c8c-eager-가-실제인-사이트-2026-09-19-측정-전) · 측정 [measure-eager.mjs](measure-eager.mjs) · [probe-order.mjs](probe-order.mjs) · 60회 + 14회

[C8b 의 `eager` 는 내가 만든 조건이었다.](#5-반증-테스트--lazy-를-끄면-효과가-사라지는가)
모든 이미지를 한꺼번에 eager 로 만들어 전송이 123 → 303ms 로 길어지는 부작용이 있었다.

### 대상 — 18곳 중 4곳, 전부 Wikivoyage

| 시도 | 결과 |
|---|---|
| 뉴스·문서·매거진 10곳 | 8곳 탈락 — 텍스트 LCP 이거나 문서가 2~14k px |
| 위키 밖 (seriouseats · dpreview · nps) | **봇 차단** — 문서 744~1,837px, DOM 33~280 |
| Wikivoyage 5곳 | **4곳 통과.** Tokyo 만 LCP 이미지가 lazy |

**Wikivoyage 는 Wikipedia 와 같은 MediaWiki 이고 선택자도 같은데**(`.mw-parser-output section > *`)
히어로 배너에만 `lazy` 가 안 붙는다. 나머지는 대부분 lazy 다 — **요즘 권장되는 패턴 그대로**다.
같은 엔진에서 Tokyo 만 다른 것도 기록해 둔다. 엔진이 아니라 **페이지별**이다.

| 사이트 | 문서 높이 | LCP 이미지 | 블록 | 이미지(lazy) |
|---|---:|---|---:|---|
| Paris | 82,189px | `loading` 없음 | 461 | 246 (179) |
| Rome | 66,411px | `loading` 없음 | 414 | 121 (86) |
| London | 124,619px | `loading` 없음 | 746 | 689 (658) |

> 결과적으로 조작이 **히어로에 거의 국한**됐다 — C8b 보다 깨끗한 조건이 됐다.

이건 네트워크가 빠르든 느리든 부호가 안 바뀐다. 30ms 를 잡을 필요가 없다.

## 7. C8d — 레이아웃이 비싼데 `eager` 인 페이지

> 사전 등록 [부칙 4](PREDICTION.md#부칙-4--c8d-레이아웃이-비싼데-lcp-이미지가-eager-2026-09-19-측정-전) · [probe-heavy.mjs](probe-heavy.mjs) · [measure-heavy.mjs](measure-heavy.mjs) · 36회

[C8c 는 ①도 ②도 아닌 페이지](#6-c8c--eager-가-실제인-사이트에서-다시)였다. 두 조건을 분리하려면 **②만** 만족하는 페이지가 필요하다.

### 찾는 법 — 도시 이름을 찍지 않는다

`Special:LongPages` 로 Wikivoyage 최장 문서부터 훑고, 판정은 프록시가 아니라 **실측 Layout ms** 로 했다.
[C8c 에서 London(124,619px · DOM 15,415)이 135ms 밖에 안 나왔다](#lcp-로는-판정이-안-된다) — 문서 높이·DOM 은 못 믿는다.

| 문서 | 문서 높이 | DOM | **Layout** | 블록 | LCP |
|---|---:|---:|---:|---:|---|
| Turku | 124,362px | 15,064 | **1,143ms** | 506 | 이미지 · `eager` |
| United Kingdom | 138,175px | 6,605 | **361ms** | 865 | 이미지 · `eager` |
| Philippines | 132,372px | 6,711 | **377ms** | 822 | 이미지 · `eager` |

안정성 확인 9/9, 본 측정 36/36 전부 이미지 LCP · `loading` 없음.

> 상위 14개 중 이미지 LCP 는 **5개뿐**이었다. 나머지는 `<p>` 였다.
> **긴 문서일수록 텍스트가 LCP 가 되기 쉽다** — 조건 ①과 ②가 같이 성립하기 어려운 구조적 이유다.

### 결과 — 레이아웃을 424ms 아껴도 LCP 가 안 움직인다

| 사이트 | Layout | FCP | LCP | 요청 앞당김 | 응답끝→LCP 대기 |
|---|---|---|---|---:|---|
| Turku | 876 → 452ms (**−48%**) | 1417 → 1333 | 2267 → 2208 (−3%) | **−38ms** | 1047 → 946ms |
| United Kingdom | 304 → 145ms (**−52%**) | 1298 → 1204 | 2007 → 1762 (−12%) | **+185ms** | 742 → 684ms |
| Philippines | 331 → 181ms (**−45%**) | 1200 → 1320 | 1959 → 1972 (+1%) | **−161ms** | 791 → 752ms |

**U1 성립** (45~52% 절감) · **U2 성립** (요청 앞당김 −38·+185·−161 — 부호가 제각각, 즉 안 움직인다)
**U3 반증** · **U4 반증** (대기가 5~10% 밖에 안 줄었다)

### 결정적인 한 줄

| | Layout 절감 | **요청 앞당김** |
|---|---:|---:|
| Grand Canyon <sub>lazy</sub> | 354ms | **+579ms** |
| **Turku** <sub>eager</sub> | **424ms** | **−38ms** |

**Turku 는 Canyon 보다 레이아웃을 더 많이 아꼈다. 그런데 요청은 안 움직였다.**
[기전이 lazy 를 거친다는 것](#4-왜-빨라졌나--다운로드가-빨라진-게-아니다)의 가장 깨끗한 증거다.

### 네 칸이 다 찼다

| | 레이아웃 **쌈** | 레이아웃 **비쌈** |
|---|---|---|
| **`eager`** | C8c `asis` — 절감 48~67ms · 앞당김 **−1~+97ms** | **C8d** — 절감 150~424ms · 앞당김 **−161~+185ms** |
| **`lazy`** | C8b·C8c `forced` — 절감 30~104ms · 앞당김 **+28~+149ms** | **C8 본측정** — 절감 332~402ms · 앞당김 **+414~+579ms** |

**앞당김이 크고 일관된 칸은 오른쪽 아래 하나뿐이다.**
`eager` 두 칸은 부호가 섞이고(잡음), `lazy`·쌈 은 작다. [C8c 의 "둘 다 필요하다" 가 그대로 선다.](#그래서-조건이-두-개로-좁혀진다)

### 그런데 대기 735ms 는 뭔가

세 곳 모두 **이미지가 다 내려온 뒤 LCP 까지 742~1,047ms** 를 더 기다린다(전체 중앙값 735ms).
응답 끝은 오히려 FCP 보다 **69ms 빠르다** — 이미지는 첫 페인트 즈음에 이미 손에 있다.

36행 전체로는 `Layout` 과 대기의 상관이 r = 0.72 지만,
**통제된 대조**(같은 사이트, 섞인 순서, plain vs cv)에서는 Layout 을 절반으로 줄여도 대기가 **5~10%** 밖에 안 준다.

> 행을 가로지르는 상관은 "느린 실행은 전부 느리다" 는 공통 요인이 만든 것이다.
> [방법론 17조](../../README.md#방법론-22조)가 또 걸렸다 — 조건 차이를 말하기 전에 통제된 대조부터 본다.

이 735ms 가 무엇인지는 **닫지 못했다.**

## 8. C8e — 그 735ms 를 쪼갰다

> [probe-wait.mjs](probe-wait.mjs) · [probe-banner.mjs](probe-banner.mjs) · 21회 로드

[C8d 가 남긴 것](#그런데-대기-735ms-는-뭔가): 이미지가 다 내려온 뒤 LCP 까지 742~1,047ms 를 더 기다리는데,
`Layout` 을 절반으로 줄여도 그 대기가 5~10% 밖에 안 줄었다.

### 먼저 갈림길 하나 — 메인 스레드는 바쁜가

창(응답끝 → LCP) 안에서 메인 스레드 점유를 쟀다. **40~100%.** 한쪽으로 안 갈렸다.
창 안 메인 스레드 상위는 `Layout` 158~173ms · `FunctionCall` 93~189ms — 어느 것도 창을 못 채운다.

> 여기서 한 번 틀렸다. 메인 스레드를 `RunTask` 총량이 제일 큰 스레드로 골랐더니
> 엉뚱한 스레드를 집어 **분해가 통째로 비어서** 나왔다.
> 렌더러 메인 스레드는 `ParseHTML`·`Layout` 이 도는 스레드로 골라야 한다.

### 뜻밖의 것 — LCP 후보가 갈아치워진다

| 시각 | 요소 | 크기 |
|---:|---|---:|
| 956ms | `<img>` 위키보이지 워드마크 | 3,000px² |
| 1,092ms | **`<p>`** | 83,190px² |
| 1,448ms | `<img>` 페이지 배너 ← 최종 LCP | 85,801px² |

**최종 LCP 는 그 전에 이미 그려진 `<p>` 를 3.1% 차이로 이긴 것이다.** Philippines 에서는 **1.3%** 차이다
(84,783 → 85,920px²). 한 요소가 늦게 그려지는 게 아니라, **누가 제일 큰지가 늦게 결정된다.**

### 그래서 세 구간으로 쪼갰다

매 프레임 배너의 `getBoundingClientRect()` 와 `complete` 를 찍었다. 6회 · ms

| | 응답끝 | 최종 크기 | `complete` | LCP | ① | ② | ③ |
|---|---:|---:|---:|---:|---:|---:|---:|
| Turku #0 | 1224 | 1346 | 1346 | 1772 | 122 | 0 | **426** |
| Turku #1 | 1521 | 1625 | 1625 | 2136 | 104 | 0 | **511** |
| UK #0 | 1299 | 1373 | 1504 | 2088 | 75 | 130 | **584** |
| UK #1 | 966 | 1098 | 1098 | 1436 | 133 | 0 | **338** |
| Philippines #0 | 1137 | 1278 | 1278 | 1596 | 141 | 0 | **318** |
| Philippines #1 | 1302 | 1364 | 1458 | 1720 | 62 | 95 | **262** |
| **중앙값** | | | | | **122** | **0** | **426** |

① 응답끝 → 배너가 478×180 으로 레이아웃되는 시각 (ResourceLoader 스타일 + 레이아웃)
② 그 시점 → `complete=true`
③ **준비 완료 → LCP 가 보고하는 `renderTime`**

| 구간 | 중앙값 | 비중 |
|---|---:|---:|
| ① 레이아웃으로 크기가 정해지기까지 | 122ms | **22%** |
| ② 로드 완료까지 | 0ms | 0% |
| ③ **준비된 뒤 실제로 그려지기까지** | 426ms | **78%** |

### 교차 검증이 맞는다

레이아웃 몫이 **22%** 뿐이다. `content-visibility` 가 `Layout` 을 절반으로 줄여도
대기는 **최대 11%** 밖에 못 줄인다. [C8d 가 실측한 값은 5~10% 였다.](#결과--레이아웃을-424ms-아껴도-lcp-가-안-움직인다)

**따로 잰 두 값이 맞아떨어진다.** 이게 "왜 Layout 을 아껴도 이 대기가 안 줄었나" 의 답이다.

### ③ 은 절반만 닫았다

준비된 뒤 262~584ms 동안 **프레임은 계속 나온다** — 그 창에 9~14 프레임, 최대 공백 57~84ms.
멈춘 게 아니라 **느리다**(12~17fps). 같은 창에서 메인 스레드 밖 스레드풀이 359~726ms 바쁘다
(`ThreadPool_RunTask`·`v8.parseOnBackground`) — 래스터·디코드 쪽 혼잡과 맞는다.

**그래도 합성 파이프라인의 어느 단계인지는 못 갈랐다.** 거기까지 가려면
[paint chunk 계수](../../README.md#닫지-못한-것)처럼 소스 빌드가 필요하다.

### 닫은 것 / 못 닫은 것

| | |
|---|---|
| ✅ 다운로드가 아니다 | 응답끝은 FCP 보다 이르거나 비슷하다 |
| ✅ 디코드가 먼저가 아니다 | 크기가 정해질 때 이미 `complete=true` 인 경우가 4/6 |
| ✅ **레이아웃이 주범이 아니다** | 22% 뿐. 그래서 Layout 을 반으로 줄여도 5~10% |
| ✅ 후보 경합이 실재한다 | 최종 LCP 가 앞선 `<p>` 를 **1.3~3.1%** 차이로 이긴다 |
| ❌ ③의 426ms 가 파이프라인 어디인가 | 프레임은 나오지만 느리다. 단계는 못 갈랐다 |

## 9. C8f — 그 426ms 를 다시 쪼갰다

> [probe-pipeline.mjs](probe-pipeline.mjs) · 21회 로드 (plain 9 · plain/cv 대조 12)

[C8e 의 ③](#8-c8e--그-735ms-를-쪼갰다) — 배너가 준비된 뒤 LCP 까지의 426ms.

### 방법 — 배너를 언급하는 이벤트를 전부 뽑는다

단계 이름을 추측하지 않았다. LCP 이미지의 **파일명 토큰**(`Stonehenge_banner_distant_`)으로
트레이스 10만 개의 `args` 를 통째로 훑으면, 그 배너에 일어난 일이 시간순으로 줄지어 나온다.

```
uk #0      1653ms  ResourceSendRequest
         1827.8ms  ResourceReceiveResponse
         2373.6ms  (내 rAF 추적: 최종 크기 + complete)
         2762.1ms  PaintImage                 0.25ms
         2762.2ms  PaintTimingVisualizer::LayoutObjectPainted
           2891ms  LargestImagePaint::Candidate   ← LCP
```

**응답과 페인트 사이 934ms 동안 배너에 관한 이벤트가 하나도 없다.**

### 두 구간으로 갈린다

| | |
|---|---|
| **A** | 준비 → 배너의 `PaintImage` |
| **B** | `PaintImage` → `LargestImagePaint::Candidate` |

12회 측정:

| | 값 |
|---|---|
| **B** | 48 · 78 · 87 · 87 · 87 · **117** · 120 · 136 · 145 · 183 · 251ms |
| **A** | 528 ~ 2,411ms |

**B 는 중앙값 117ms 로 안정적이고, cv 를 걸어도 안 변한다**(uk 136→117 · Philippines 87→87).
페인트가 기록된 뒤 화면에 올라오기까지의 **고정 지연**이다.
**A 가 전부를 좌우한다.**

### 디코드는 범인이 아니다 — 12/12

`Decode Image` · `ImageDecodeTask` 가 `PaintImage` **보다 먼저 온 행이 0/12** 이다.
디코드는 페인트가 **부른 뒤에** 일어난다. 그리기를 막고 있던 게 아니다.

### 왜 A 가 긴가 — 페인트는 드물다

같은 창 안에서 단계별 **횟수**(중앙값):

| 단계 | 횟수 |
|---|---:|
| `Layout` | **50회** |
| `RasterTask` | 55회 |
| `Paint` | **9회** |
| rAF 프레임 | 7회 |

**레이아웃은 50번 도는데 페인트는 9번밖에 안 돈다.**
배너는 준비돼 있어도 **다음 페인트 패스까지 기다린다.**
[방법론 15조 "시간 전에 횟수를 센다"](../../README.md#방법론-22조)가 여기서도 답을 줬다 —
시간 합계로는 `Paint` 가 10~26ms 라 눈에 안 띄지만, **횟수로 보면 5배 차이**다.

### A 가 레이아웃 때문인지는 못 닫았다

같은 실행 안에서 `plain` 과 `cv-auto` 를 섞어 돌렸다. A 가 uk 1,736 → 1,331ms(−23%),
Philippines 955 → 610ms(−36%) 로 줄었다 — 방향은 맞다.

**그런데 이 대조는 믿을 만하지 않다.** 셀당 3회인데 `준비` 가 8,018ms 인 행이 하나,
LCP 후보를 못 받은 행이 하나 있었다. [C8c 에서 한 것과 같은 계산](#lcp-로는-판정이-안-된다)을
하면 이 흩어짐에는 3회로 턱없다.

그리고 [C8d 는 6회로 "LCP 가 안 움직인다"](#결과--레이아웃을-424ms-아껴도-lcp-가-안-움직인다)를 봤다.
둘을 합치면 **A 가 줄어도 전체 LCP 는 안 움직였다**는 뜻인데, 그 둘을 화해시키려면 더 재야 한다.

### 정리

| | |
|---|---|
| ✅ **B = 고정 지연 117ms** | 페인트 기록 → 화면. cv 와 무관 |
| ✅ **디코드는 범인이 아니다** | `PaintImage` 앞에 온 적 0/12 |
| ✅ **페인트가 드물다** | 창 안 `Layout` 50회 vs `Paint` 9회 |
| ❌ A 를 무엇이 밀고 있나 | 방향은 레이아웃 쪽인데 3회로는 못 닫는다 |

## 10. C8g — A 를 셀당 20회로 다시

## 11. C8h — `Layout` 은 왜 `Paint` 보다 3~5배 자주 도는가

> [probe-forced.mjs](probe-forced.mjs) · 24회 (1차 가설 12 · 2차 기준 12)

[C8g 에서 A 구간 안의 횟수가 이랬다](#왜-주는가--페인트-간격이-좁아진다): `Layout` 35회 · `Paint` 10회.
렌더링 수명주기는 Style → Layout → PrePaint → Paint 로 한 번에 도는데, 왜 3~5배 차이가 나나.

### 1차 가설은 반증됐다

*"JS 가 강제로 부르는 동기 레이아웃(강제 리플로)이 많을 것"* 이라고 봤다.
각 `Layout` 을 완전히 감싸는 JS 이벤트가 있는지 셌다.

**12회 전부 정확히 6회**였다. 그리고 전부 `FireIdleCallback` 하나였다.
나머지 20~32회는 JS 밖에서 돈다. **틀렸다.**

### 기준을 바꿨다 — 그 태스크가 페인트까지 갔나

각 `Layout` 을 감싸는 최상위 `RunTask` 를 찾아, 그 태스크가 `Paint` 까지 갔는지로 갈랐다.

| 사이트 | 모드 | `Layout` | 페인트 ○ | **페인트 ✗** | 그 중 `ParseHTML` | `FireIdleCallback` | `Paint` |
|---|---|---:|---:|---:|---:|---:|---:|
| United Kingdom | `plain` | 35 | 16 | **19** | 13 | 6 | 7 |
| | `cv-auto` | 33 | 16 | **17** | 11 | 6 | 9 |
| Philippines | `plain` | 29 | 12 | **17** | 11 | 6 | 5 |
| | `cv-auto` | 31 | 14 | **17** | 11 | 6 | 6 |

> **레이아웃의 절반 이상이 화면에 아무것도 안 남긴다.**
> `ParseHTML` 태스크가 11~13회, `FireIdleCallback` 이 6회.

스트리밍 파서는 HTML 이 도착할 때마다 레이아웃을 돌리지만 **그 태스크는 페인트로 안 간다.**
프레임은 따로 스케줄된다. 그래서 `Layout` 횟수와 `Paint` 횟수가 안 맞는다.

이게 [C8g 의 "cv 가 줄이는 건 레이아웃 횟수가 아니라 한 번의 비용"](#왜-주는가--페인트-간격이-좁아진다)과 맞물린다 —
cv 를 걸어도 `Layout` 횟수(29~35)와 페인트 없는 레이아웃 횟수(17~19)는 **거의 안 변한다.**
파서가 도는 횟수는 문서 구조가 정하는 것이지 `content-visibility` 가 정하는 게 아니다.

### 곁가지 — 긴 태스크가 3분의 1로 준다

| 모드 | 50ms 넘는 태스크 (A 구간 안, 중앙값) |
|---|---:|
| `plain` | **6개** |
| `cv-auto` | **2개** |

`content-visibility` 의 실제 효과가 여기 있다. 총 레이아웃 시간(646→188ms)이 줄면서
**메인 스레드를 오래 잡는 덩어리가 사라진다.** 그래서 페인트 간격이 139~145ms → 86~88ms 로 좁아진다.

## 13. C8j — 캐시를 데워 절대 LCP 를 잰다

> 사전 등록 [부칙 6](PREDICTION.md#부칙-6--c8j-캐시를-데워-절대-lcp-를-잰다-2026-09-20-측정-전) · `measure-paintwait.mjs --warm=1` · **80회, 실패 0건**

[콜드에서는 다운로드 변동(±600ms)이 효과(~350ms)보다 커서 절대 LCP 를 못 잡았다.](#그러면-왜-절대-lcp-가-안-움직였나--검정력이다)
캐시를 데우면 그 변동이 사라진다.

### W3 은 성립 — warm 에서도 FCP 와 LCP 가 갈린다

**80/80 전부 FCP < LCP.** [C8 의 Wikipedia 는 warm 에서 FCP=LCP 가 됐는데](#1-연기-테스트가-설계-결함을-잡았다),
여기는 메인 스레드가 99~100% 차 있어서 이미지가 캐시에 있어도 페인트까지 기다린다. 설계 전제가 맞았다.

### W1 은 반증 — 절대 LCP 는 여전히 안 잡힌다

| 지표 | United Kingdom | Philippines |
|---|---|---|
| **LCP (절대)** | +300 [−56, 480] | −76 [−400, 196] |
| **FCP** | **+280 [72, 388]** ★ | +140 [−8, 376] |
| **LCP − FCP** | −24 [−212, 64] | **−324 [−444, −124]** ★ |
| **A** | +7 [−127, 87] | **−238 [−343, −115]** ★ |
| 배너 응답끝 | **+267 [113, 403]** ★ | +138 [−47, 255] |

### 그런데 뜻밖의 것이 나왔다 — warm 에서 cv 가 FCP 를 늦춘다

**UK 는 FCP 가 280ms 느려졌고 신뢰구간이 0 을 제외한다.** Philippines 도 같은 방향(+140)이다.

네트워크가 빠지니 `content-visibility` **자체의 선행 비용**이 드러난 것으로 보인다.
800개가 넘는 블록에 cv 를 걸면 첫 페인트 전에 치러야 할 일이 생긴다.

그래서 이득(`LCP − FCP` −24 · −324)이 그 비용에 상쇄돼 **절대 LCP 가 안 움직인다.**

> **콜드에서는 네트워크 변동에 묻히고, warm 에서는 cv 자신의 선행 비용에 상쇄된다.**
> 두 경우 다 "렌더링 대기는 확실히 줄지만 절대 LCP 로는 안 나타난다" 로 같은 결론이다.

그 선행 비용이 무엇인지 → [14절](#14-c8k--warm-에서-cv-가-fcp-를-늦추는-값은-어디서-쓰나)

## 14. C8k — warm 에서 cv 가 FCP 를 늦추는 값은 어디서 쓰나

> [probe-fcpcost.mjs](probe-fcpcost.mjs) · warm 40회

[C8j 에서 cv 가 FCP 를 208~284ms 늦췄다.](#그런데-뜻밖의-것이-나왔다--warm-에서-cv-가-fcp-를-늦춘다)
**FCP 이전 구간만** 잘라 단계별로 쟀다.

| 단계 | United Kingdom | Philippines |
|---|---|---|
| **FCP 자체** | 404 → 612 (**+208** [116, 300]) ★ | 396 → 680 (**+284** [148, 684]) ★ |
| `ParseHTML` | 13 → 13 (0) | 14 → 15 (0) |
| **`Layout`** | **1 → 198** (+197 [96, 267]) ★ | **1 → 215** (+214 [192, 296]) ★ |
| `Style` | 10 → 61 (+51 [13, 64]) ★ | 9 → 61 (+52 [28, 67]) ★ |
| `PrePaint` · `Paint` · JS | 변화 없음 | 변화 없음 |
| **`Layout` 횟수** | 5 → 5 | 4 → 7 (0 포함) |

> **같은 양의 HTML 을 파싱했는데 첫 페인트 전 레이아웃만 200배 비싸다.**
> 1ms → 198~215ms. **횟수는 그대로다** — 한 번의 비용이 40배가 된 것이다.

`ParseHTML` 이 13→13ms 로 안 변한 것이 중요하다.
*"FCP 가 늦어져서 그 창에 일이 더 들어간 것뿐"* 이라는 설명을 **배제한다** —
파싱량이 같은데 레이아웃만 늘었다.

### 이게 전부를 설명한다

| | |
|---|---|
| FCP 지연 | +208 · +284ms |
| 그 중 `Layout` | +197 · +214ms |
| 그 중 `Style` | +51 · +52ms |

**설명되지 않는 몫이 거의 없다.**
[C8j 에서 본 "이득이 상쇄된다"](#그런데-뜻밖의-것이-나왔다--warm-에서-cv-가-fcp-를-늦춘다)의 정체가 이것이다.

`content-visibility: auto` 는 화면 밖을 건너뛰는 대신, **첫 페인트 전에 전체 골격을 한 번 세운다.**
그게 이 페이지들(블록 822~865개)에서 200ms다.

## 15. C8l — 그 선행 비용은 `auto` 키워드 탓인가

> [probe-intrinsic.mjs](probe-intrinsic.mjs) · warm 60회 · 세 팔(`plain` · `cv-auto` · `cv-fixed`)

`cv-fixed` 는 `contain-intrinsic-size` 에서 **`auto` 키워드만 뺀 것**이다.
`auto` 는 "마지막으로 기억한 크기" 를 유지해야 해서 따로 장부를 쓴다.

### 먼저 — 중앙값으로 보면 안 된다

`전Layout` 이 **양봉 분포**였다.

```
philippines cv-auto:  208 181 [1] [1] 288 303 [1] 335 [1]
uk          cv-auto:  164 269 319 187 293 297 118
```

cv 의 선행 비용은 **항상 나는 게 아니라 FCP 가 어디에 떨어지느냐에 달려 있다.**
FCP 가 이른 실행에서는 아직 레이아웃할 것이 없다. 그래서 **횟수로 센다** ([15조](../../README.md#방법론-22조)).

### warm FCP — 세 실험을 합치면 (40/셀)

| 사이트 | `plain` | `cv-auto` | 차이 | 95% 신뢰구간 |
|---|---:|---:|---:|---|
| United Kingdom | 372 | 620 | **+248** | [180, 344] ★ |
| Philippines | 384 | 544 | **+160** | [40, 276] ★ |

[C8j 에서 한 곳만 유의했던 것](#w1-은-반증--절대-lcp-는-여전히-안-잡힌다)이 **두 곳 다 유의**해졌다.

### 선행 비용이 나는 비율 — 순열검정

| 조건 | `FCP` 이전 `Layout` > 50ms 인 실행 |
|---|---|
| `plain` | **4/40 (10%)** |
| `cv-auto` | **30/40 (75%)** |
| `cv-fixed` | **9/20 (45%)** |

| 대조 | 차이 | p |
|---|---:|---|
| `plain` vs `cv-auto` | 65%p | **< 0.0001** ★ |
| `cv-auto` vs `cv-fixed` | 30%p | **0.040** ★ |

> **`auto` 키워드가 그 비용의 일부를 만든다.** 빼면 75% → 45% 로 준다.
> 그래도 `plain`(10%)보다는 훨씬 높으니 **나머지는 `content-visibility` 자체**다.

### C2 의 결론이 여기서 갈린다

[C2 는 `auto 73px` 과 `73px` 의 차이가 반복 편차보다 작다(3~8%)고 봤다.](../c2-anomalies/RESULTS.md)
**그건 리레이아웃 이야기였다.** 첫 페인트 전에는 다르다 — 비용이 나는 빈도가 **75% → 45%** 로 갈린다.

p = 0.040 이고 `cv-fixed` 는 20회뿐이다. **약한 증거**로 읽어야 한다.

## 16. C8m — 선행 비용이 cv 요소 개수에 비례하는가

> 사전 등록 [부칙 7](PREDICTION.md#부칙-7--c8m-선행-비용이-cv-요소-개수에-비례하는가-2026-09-20-측정-전) · [probe-dose.mjs](probe-dose.mjs) · warm **80회, 실패 0건**

요소마다 붙는 준비 작업이면 개수에 비례해야 하고, 문서를 한 번 훑는 고정 비용이면 무관해야 한다.

**위쪽만/아래쪽만 이진 비교로는 못 가른다** — 개수도 같이 변해서 위치와 섞인다. 용량-반응으로 갔다.
`nth-of-type` 은 중첩 섹션마다 걸리므로 K 가 곧 개수가 아니다. **실제 매칭 개수를 실행마다 기록**했다.

### X1 은 약하게 성립

**고정 비용은 아니다.** `plain` 1ms → 250~370개 46~66ms → 전체 104~273ms 로 커진다.
그런데 **관계가 약하다** — 행 단위 순위상관이 **rho = 0.24 · 0.31** 이고

### X2 는 반증 — 적게 걸어도 공짜가 아니다

**121~332µs, 2.8배 차이.** "2배 이내" 로 예측했는데 벗어났다.
중첩 섹션 때문에 같은 개수라도 구조가 달라서일 것으로 보지만, **확인하지 않았다.**

### 그래서 처방은 절반만 통한다

> `content-visibility` 를 **적게 걸면 선행 비용이 줄기는 한다**(273 → 66ms).
> 그런데 비례하지 않고, **적게 걸어도 46~66ms 는 낸다.**
> "화면 아래쪽에만 걸면 공짜" 라는 처방은 이 데이터로는 못 세운다.

## 20. 흩어짐

`cold` 는 네트워크가 통째로 들어오므로 흩어짐이 크다. 반복별 LCP (ms, 정렬):

Milky Way      cold  plain     1923  2005  2175  2349  3961  5734   3.0배
Milky Way      cold  cv-auto   1589  1673  1909  1935  1991  2589   1.6배

Mount Everest  cold  plain     1877  1951  2127  2346  2599  4456   2.4배
Mount Everest  cold  cv-auto   1818  1885  1985  2064  2667  3708   2.0배

`plain` 쪽 꼬리(5734ms, 4456ms)가 더 길다. 중앙값으로 읽어야 한다.
`warm` 은 표본이 작은데도 cv-auto 에 6.5배짜리 이상치가 하나 있었다(284~1847ms) — warm 의 −38% 는 그만큼 덜 믿을 만하다.

## 21. 남은 것

- **위키 밖.** 조건 넷을 만족하는 공개 페이지를 위키 밖에서 못 찾았다 — 긴 문서는 텍스트 LCP 고,
  이미지 LCP 는 문서가 짧고, 나머지는 봇 차단이었다(문서 744px · DOM 33). 로그인·스크립트가 있는
  실제 커머스·SNS 는 아예 못 건드렸다
- **T1·T2 를 제대로 잡으려면** 셀당 96회가 필요하다. 사이트 3곳 × 4셀 × 96회 = 1,152회 로드
- ~~`응답끝 → LCP` 사이의 735ms~~ → [8절](#8-c8e--그-735ms-를-쪼갰다)·[9절](#9-c8f--그-426ms-를-다시-쪼갰다)에서 두 번 쪼갰다.
  레이아웃 22% · 준비 뒤 78%, 그 78% 는 다시 **A(다음 페인트 패스까지 기다림) + B(고정 117ms)**
- ~~A 를 무엇이 밀고 있나~~ → [10절](#10-c8g--a-를-셀당-20회로-다시)·[11절](#11-c8h--layout-은-왜-paint-보다-35배-자주-도는가)에서 닫았다.
  메인 스레드가 99~100% 차 있고 `Layout` 이 646~669ms 를 먹는다. cv 가 그걸 줄이면 페인트 간격이 좁아진다
- **절대 LCP 에서 효과를 보려면 몇 회가 필요한가.** 콜드에서 −144ms 를 잡으려면 셀당 약 180회다.
  대신 `LCP − 응답끝` 같은 실행 내 지표를 쓰면 20회로 잡힌다 — 필드 데이터(p75)에서는 어느 쪽이 맞는지 모른다
- ~~cv 의 선행 비용을 피할 수 있나~~ → [17절](#17-c8n--28배는-내-지표가-만든-것이었다).
  **줄어든다.** DCL 기준 요소당 23~58µs 로, 적게 걸면 +25ms → +9ms 로 거의 비례해 준다
- ~~요소당 비용이 왜 2.8배나 흔들리나~~ → **내 지표 탓이었다.** 분자는 FCP 까지, 분모는 끝까지였다
- **cv 가 첫 페인트에 까는 바닥은 무엇이 정하나.** r(기준선 FCP, 지연) = −0.88 까지는 봤지만
  그 바닥값(524~776ms)이 문서 크기·DOM 수 중 무엇을 따라가는지는 2곳으로는 못 본다
- **`lazy` × 싼 레이아웃 칸이 혼재**한다 (C8b −5~−23% vs C8c −0~−5%). 세션이 달라서인지 사이트 차이인지 못 갈랐다
