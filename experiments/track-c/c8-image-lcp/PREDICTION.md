# C8 사전 등록 예측 — LCP 가 이미지일 때

> **측정 전에 작성.** 2026-09-18.
> [C7](../c7-real-initial-load/RESULTS.md) 에서 검증 못 하고 남긴 것.

## 왜 이걸 하나

[C7](../c7-real-initial-load/RESULTS.md) 의 3곳은 전부 문서 사이트라 **FCP = LCP** 였다 —
첫 페인트에 나온 텍스트가 그대로 LCP 요소였다.
그래서 사전 등록한 R3(*"FCP 가 LCP 보다 덜 개선된다"*)을 **측정조차 못 했다.**

실제 웹에서 LCP 는 대개 **이미지**다. 이미지 LCP 는 성질이 다르다 —
**레이아웃이 아니라 이미지 다운로드에 묶여 있다.**
`content-visibility` 가 아끼는 건 레이아웃 시간이므로, 여기서는 효과가 없을 수 있다.

## 대상을 찾는 데만 세 번 걸렸다

| 시도 | 결과 |
|---|---|
| 위키 본문 4곳 (데스크톱 1280px) | **전부 텍스트 LCP.** 썸네일이 작아 문단이 더 크다 |
| 갤러리·포토 4곳 | 이미지 LCP 는 나왔는데 **문서가 1,519~3,076px** — cv 가 의미 없는 크기 |
| **모바일 폭(390×844)** | **뒤집혔다.** 문단 면적이 줄고 이미지가 전체 폭을 차지한다 |

모바일이 억지 조건도 아니다 — 실제 트래픽 대부분이 그 폭이다.

### 확정된 대상 (뷰포트 390×844)

|---|---:|---:|---:|---|---:|---:|---:|
| Grand Canyon | 48,963px | 7,383 | 69 | **`<img>`** | 224 | 208px | 2.83 |
| Milky Way | 71,931px | 11,237 | 46 | **`<img>`** | 225 | 234px | 4.56 |
| Mount Everest | 91,810px | 15,289 | 233 | **`<img>`** | 429 | 200px | 3.83 |

자동 탐색이 찾아준 `#mwBoQ` 같은 건 Parsoid 가 매 렌더마다 새로 만드는 ID라 못 쓴다.

## 측정 방법

[C7 과 동일](../c7-real-initial-load/PREDICTION.md) — 캐시를 데운 뒤 HTML 응답을 가로채
`<style>` 을 심고 두 번째 로드를 잰다. `plain` 도 똑같이 가로채되 빈 스타일을 넣는다.
엄격 격리 + 순서 섞기 + 설정마다 6회.

**추가로 기록**: 각 실행에서 **LCP 요소가 무엇이었는지**(`<img>` 인지 텍스트인지).
cv 가 LCP 요소 자체를 바꿀 수 있기 때문이다.

| **S3** | **FCP 는 빨라진다** → C7 에서 못 본 **FCP/LCP 분리**가 처음 보인다 | ✅ 첫 페인트는 레이아웃에 묶여 있다 |
| **S4** | LCP 요소는 양쪽 모두 `<img>` 로 유지된다 | ✅ LCP 이미지는 화면 위쪽이라 건너뛰지 않는다 |

### 그래서 예상되는 결론

> `content-visibility` 는 **첫 페인트**를 빠르게 하지만 **LCP 는 못 건드린다** —
> LCP 가 이미지라면. C7 에서 본 Wikipedia 의 극적인 개선(24초 → 2.2초)은
> **LCP 가 텍스트였기 때문**일 수 있다.

### 틀릴 수 있는 지점

**S2 가 틀리는 경우**: 레이아웃이 너무 느려서 이미지 디코드·페인트까지 밀리는 경우.
[C7 의 Wikipedia 는 레이아웃에만 22초](../c7-real-initial-load/RESULTS.md)를 썼다.
이번 세 페이지는 그보다 작으므로(48k~92k px) 레이아웃이 그 정도는 아닐 것이다 — 그래도 재봐야 안다.

[C6 에서는 cv 에 불리한 쪽으로, C7 에서는 유리한 쪽으로 편향돼 있었다](../c7-real-initial-load/RESULTS.md#4-사전-등록-주장-판정).
이번엔 **다시 불리한 쪽**(S2: 효과 없음)으로 예측하고 있다. 그 점을 적어둔다.

## 부칙 — 측정 전 설계 변경 (2026-09-18, 본 측정 시작 전)

**연기 테스트 2회**를 돌리고 위 설계가 **질문에 답할 수 없다**는 걸 알았다. 데이터 수집 전에 고친다.

```
cv-auto   FCP 684.3  LCP 684.3  이미지<img>  Layout  52.28
plain     FCP 595.3  LCP 595.3  이미지<img>  Layout 198.42
```

**FCP = LCP 가 또 나왔다.** LCP 요소는 제대로 `<img>` 인데도.
이유: [C7 에서 가져온 "캐시를 데운 뒤 잰다"](../c7-real-initial-load/PREDICTION.md#그래서-캐시를-데운-뒤에-잰다) 설계 때문이다.
캐시가 따뜻하면 **이미지도 캐시돼 있어서** 첫 컨텐츠 프레임에 같이 그려진다.

> 문서 사이트에서 네트워크는 **잡음**이었다. 이미지 LCP 에서는 **현상 그 자체**다.
> 다운로드를 지워버리면 재려던 걸 지우는 것이다.

### 그래서 캐시 상태를 축으로 올린다

| | 절차 |
|---|---|
| **warm** | C7 과 동일 — 1차 로드로 캐시를 데우고 2차 로드를 잰다 |
| **cold** | 빈 프로필에서 **첫 로드를 그대로 잰다.** 실제 첫 방문 |

3곳 × 2모드 × **2캐시** × 6회 = 72회.

### 예측 수정

`cold` 는 새 축이므로 예측을 따로 등록한다. `warm` 예측(S1~S4)은 위 그대로 둔다.

| # | 주장 | 내 예측 |
|---|---|---|
| **S5** | `cold` 에서 **FCP 와 LCP 가 갈라진다** (LCP > FCP) | ✅ 이미지 다운로드가 뒤에 온다 |
| **S6** | `cold` 에서 **LCP 는 cv 로 안 빨라진다** | ✅ 다운로드가 병목이지 레이아웃이 아니다 |
| **S7** | `warm` 에서는 FCP = LCP 가 유지된다 | ✅ 연기 테스트에서 이미 보였다 (n=2, 확증은 본 측정에서) |

연기 테스트에서 **Layout 은 198 → 52ms 로 74% 줄었는데 LCP 는 595 → 684ms 로 늘었다.**
n=1 이라 아직 아무 말도 아니지만, S2 가 맞는 쪽으로 보인다 — 그리고 *느려지는* 쪽까지 갈 수도 있다.

## 부칙 2 — 반증 테스트 사전 등록 (본 측정 후, 반증 실험 전)

본 측정에서 **S2·S6 이 반증됐다.** LCP 가 cv 로 12~38% 빨라졌다.
그런데 다운로드가 빨라진 게 아니었다 — 바이트도 전송시간도 같고 **요청 시작**이 앞당겨졌다.

```
Grand Canyon cold  plain    요청시작 1835  전송 276ms  38,064B → LCP 2224
                   cv-auto  요청시작 1256  전송 120ms  38,064B → LCP 1597
```

`probe-why.mjs` 로 원인을 좁혔다:

| 관측 | 값 |
|---|---|
| LCP 이미지의 `loading` | **세 곳 전부 `lazy`** |
| 요청된 이미지 수 (plain / cv-auto) | 10/10 · 6/6 · 18/18 — **완전히 같다** |
| 요청된 이미지 바이트 | 110KB / 81KB / 87KB — **완전히 같다** |

**"cv 가 화면 밖 이미지 요청을 줄여서 경쟁이 준다" 가설은 틀렸다.** 요청 수가 똑같다.

남은 설명은 하나다:

> `loading="lazy"` 이미지는 **"뷰포트 안인가"** 를 알아야 요청이 나간다.
> 그건 **레이아웃을 해야 안다.** 레이아웃이 요청의 선행 조건이다.
> cv 가 레이아웃을 52~74% 줄이면 그 판정이 앞당겨지고, 요청이 먼저 나가고, LCP 가 빨라진다.

이게 맞다면 **`content-visibility` 는 LCP 를 직접 빠르게 하는 게 아니다.**
lazy 이미지의 요청 발사 시점을 앞당겨서 **간접적으로** 빠르게 하는 것이다.

### 반증 테스트

HTML 을 가로챌 때 `loading="lazy"` 를 `loading="eager"` 로 바꾸고 같은 측정을 한다.
2×2 (plain·cv-auto × lazy·eager), 콜드 캐시만, 3곳 × 5회 = 60회.

| # | 주장 | 내 예측 |
|---|---|---|
| **S8** | `eager` 에서는 **cv 의 LCP 개선이 사라진다** (±10% 안) | ✅ 레이아웃이 더는 요청의 선행 조건이 아니다 |
| **S9** | `eager` 는 `plain` 의 LCP 를 **크게 앞당긴다** | ✅ 요청이 파싱 시점에 바로 나간다 |
| **S10** | `eager` 에서도 **Layout 절감은 그대로다** | ✅ 레이아웃 일 자체는 이미지 정책과 무관 |

S8 이 틀리면(eager 에서도 cv 가 LCP 를 줄이면) 내 설명이 틀린 것이고,
다른 경로가 있다는 뜻이다. 그건 그것대로 결과다.

## 부칙 3 — C8c: eager 가 '실제'인 사이트 (2026-09-19, 측정 전)

[C8b 의 `eager` 는 내가 HTML 을 고쳐 만든 조건](#부칙-2--반증-테스트-사전-등록-본-측정-후-반증-실험-전)이었다.
모든 이미지를 한꺼번에 eager 로 만들었더니 화면 밖 이미지 60여 개가 경쟁해
전송이 123 → 303ms 로 길어지는 부작용이 생겼다. 실제 사이트는 그렇게 안 만든다.

### 대상 찾기 — 18곳 중 4곳

조건 넷을 동시에 만족해야 한다: ① 이미지 LCP ② 그 이미지가 lazy 가 **아님** ③ 문서가 긺 ④ 블록 선택자.

| 시도 | 결과 |
|---|---|
| 1차 10곳 (뉴스·문서·매거진) | 8곳 탈락 — 텍스트 LCP 이거나 문서가 2~14k px |
| 위키 밖 후보 (seriouseats · dpreview · nps) | **봇 차단** — 문서 744~1,837px, DOM 33~280 |
| **Wikivoyage 5곳** | **4곳 통과.** Tokyo 만 LCP 이미지가 lazy |

| 사이트 | 문서 높이 | LCP 이미지 | 블록 | 중앙값 | 변동계수 | 이미지(lazy) |
|---|---:|---|---:|---:|---:|---|
| Paris | 82,189px | `loading` 없음 | 461 | 182px | 2.09 | 246 (179) |
| Rome | 66,411px | `loading` 없음 | 414 | 182px | 1.59 | 121 (86) |
| London | 124,619px | `loading` 없음 | 746 | 182px | 1.97 | 689 (658) |

**Wikivoyage 는 Wikipedia 와 같은 MediaWiki 이고 선택자도 같다**(`.mw-parser-output section > *`).
다른 건 하나다 — 히어로 배너에 `lazy` 가 안 붙는다. 나머지 이미지는 대부분 lazy 다.
**요즘 권장되는 패턴 그대로**이고, C8b 가 만들어낸 "전부 eager" 와는 다르다.

같은 엔진에서 Tokyo 만 LCP 이미지가 lazy 인 것도 기록해 둔다 — 엔진이 아니라 **페이지별**이다.

### 설계 — 같은 실행 안에 대조군을 둔다

[C8 과 C8c 는 세션이 다르므로 가로질러 비교하면 안 된다](RESULTS.md#5-반증-테스트--lazy-를-끄면-효과가-사라지는가) —
C8 과 C8b 사이에서 같은 조건의 Layout 이 4배 갈렸다. 그래서 대조군을 **같은 실행 안에** 넣는다.

| 팔 | HTML |
|---|---|
| `asis` | 손대지 않는다 — 히어로가 실제로 eager |
| `forced` | `loading` 속성이 없는 `<img>` 에 `loading="lazy"` 를 붙인다 |

`forced` 는 Paris 기준 246개 중 67개만 바뀐다(179개는 이미 lazy). C8b 처럼 판을 뒤집지 않는다.

> **측정 후 정정**: 실제로는 **3개**만 바뀌었다. 나머지는 JS 가 만드는 이미지라
> HTML 치환이 닿지 않는다. 조작이 히어로에 거의 국한돼 오히려 깨끗한 조건이 됐다.

3곳 × 2모드 × 2팔 × 5회 = 60회, 콜드 캐시.

### 예측

| # | 주장 | 내 예측 |
|---|---|---|
| **T1** | `asis`(실제 eager) 에서 cv 는 LCP 를 못 줄인다 (±10% 안) | ✅ 레이아웃이 요청의 선행 조건이 아니다 |
| **T2** | `forced`(히어로 lazy) 에서는 cv 가 LCP 를 줄인다 | ✅ 선행 조건이 되살아난다 |
| **T3** | **요청 앞당김**이 `asis` 에서 0 근처, `forced` 에서 양수 | ✅ 이게 기전이 직접 예측하는 양이다 (방법론 21조) |
| **T4** | Layout 절감은 두 팔 모두 비슷하다 | ✅ 이미지 정책과 무관 |

T1 이 틀리면(실제 eager 사이트에서도 cv 가 LCP 를 줄이면) [C8 의 설명이 불완전](RESULTS.md#4-왜-빨라졌나--다운로드가-빨라진-게-아니다)한 것이다.

## 부칙 4 — C8d: 레이아웃이 비싼데 LCP 이미지가 `eager` (2026-09-19, 측정 전)

[C8c 에서 조건이 둘로 좁혀졌다.](RESULTS.md#6-c8c--eager-가-실제인-사이트에서-다시)
그런데 Wikivoyage 3곳은 **①도 ②도 아니어서** 둘을 분리해 볼 수 없었다.
②만 만족하는 페이지 — **비싼데 eager** — 가 있어야 한다.

### 찾았다

`Special:LongPages` 로 Wikivoyage 최장 문서부터 훑었다. 도시 이름을 찍어 맞히지 않았다.
판정은 프록시(문서 높이·DOM)가 아니라 **실측 Layout ms** 로 했다 —
[C8c 에서 London(124,619px · DOM 15,415)이 135ms 밖에 안 나왔다.](RESULTS.md#lcp-로는-판정이-안-된다)

| 문서 | 문서 높이 | DOM | **Layout** | 블록 | 중앙값 | 변동계수 | 이미지(lazy) |
|---|---:|---:|---:|---:|---:|---:|---|
| Turku | 124,362px | 15,064 | **1,143ms** | 506 | 202px | 2.00 | 740 (448) |
| United Kingdom | 138,175px | 6,605 | **361ms** | 865 | 182px | 1.70 | 103 (68) |
| Philippines | 132,372px | 6,711 | **377ms** | 822 | 182px | 1.53 | 74 (70) |

안정성 확인 **9회 전부** 이미지 LCP · `loading` 없음(eager).
Turku 의 Layout 은 [C8 의 Wikipedia(478~643ms)](RESULTS.md#2-렌더링-일--예상대로-크게-준다)보다도 비싸다.

상위 14개 중 이미지 LCP 는 5개뿐이었다. 나머지는 `<p>` — **긴 문서일수록 텍스트가 LCP 가 되기 쉽다.**

### 이번엔 예측이 갈린다

기전만 보면 `eager` 라 요청이 레이아웃을 안 기다리므로 LCP 가 안 빨라져야 한다.
그런데 LCP 는 **다운로드 완료 시점이 아니라 페인트 시점**이다.
레이아웃이 1초 넘게 메인 스레드를 잡고 있으면, 이미지가 일찍 도착해도 **그릴 프레임이 안 나온다.**

| # | 주장 | 내 예측 |
|---|---|---|
| **U1** | Layout 이 크게 준다 | ✅ |
| **U2** | **요청 시작은 안 움직인다** (±50ms) | ✅ eager 니까 파싱 시점에 나간다 |
| **U3** | **그런데도 LCP 는 빨라진다** | ✅ 레이아웃이 페인트를 막고 있다 |
| **U4** | `LCP − 응답끝`(다운로드 후 대기)이 `plain` 에서 크고 `cv-auto` 에서 작다 | ✅ U3 의 직접 증거 |

U2 + U3 이 같이 성립하면 **경로가 둘**이라는 뜻이다 —
[lazy 요청 앞당김](RESULTS.md#4-왜-빨라졌나--다운로드가-빨라진-게-아니다)과 **페인트 해방**.

## 부칙 5 — C8g: A 를 제대로 잰다 (2026-09-20, 측정 전)

### 측정 방식을 두 군데 고친다

**① rAF 폴링을 버리고 트레이스 타임스탬프를 쓴다.**
C8f 의 `준비` 는 매 프레임 `complete` 를 폴링해 잡은 값이다. 그런데 그 창에서 프레임이 7개뿐이라

```
ResourceFinish(배너) → PaintImage(배너) → LargestImagePaint::Candidate
        └────────── A' ──────────┘└──────── B ────────┘
```

**② 시간과 함께 횟수를 센다.**
A 구간 안의 `Paint` 횟수 · `Layout` 횟수 · 메인 스레드 점유 ms 를 같이 기록한다.
[C8f 에서 `Paint` 가 `Layout` 의 1/5 밖에 안 돈다는 걸 횟수로 봐서 알았다.](RESULTS.md#왜-a-가-긴가--페인트는-드물다)

### 규모

`uk` · `philippines` × `plain` · `cv-auto` × **20회** = 80회. 콜드 캐시, 순서 섞음, 엄격 격리.
C8f 의 MAD 로 계산하면 셀당 7회지만 그 MAD 자체가 3회짜리라 못 믿는다. 여유를 크게 준다.

### 예측

## 부칙 7 — C8m: 선행 비용이 cv 요소 개수에 비례하는가 (2026-09-20, 측정 전)

[C8k·C8l 이 밝힌 것](RESULTS.md#14-c8k--warm-에서-cv-가-fcp-를-늦추는-값은-어디서-쓰나):
warm 에서 cv 가 FCP 를 160~248ms 늦추고, 그 값은 **첫 페인트 전 `Layout`**(1ms → 200ms)에서 쓴다.
`auto` 키워드가 일부를 만들지만(75%→45%) 전부는 아니다.

### 남은 갈림길

그 비용이 **cv 요소 하나하나에 붙는 준비 작업**이라면 개수에 비례해야 한다.
문서 전체를 한 번 훑는 고정 비용이라면 개수와 무관해야 한다.

**이진 비교(위쪽만 vs 아래쪽만) 로는 못 가른다** — 위쪽만 걸면 요소 수도 같이 줄어서
"위치 때문인지 개수 때문인지" 가 섞인다. 그래서 **용량-반응**으로 간다.

| 팔 | 선택자 |
|---|---|
| `plain` | 없음 |
| `cv-k2` | `.mw-parser-output section:nth-of-type(-n+2) > *` |
| `cv-k5` | `… :nth-of-type(-n+5) > *` |
| `cv-k10` | `… :nth-of-type(-n+10) > *` |
| `cv-all` | `.mw-parser-output section > *` |

`nth-of-type` 은 중첩 섹션마다 걸리므로 K 가 곧 개수는 아니다.
그래서 **실제로 몇 개가 매칭됐는지 실행마다 기록**하고, x축은 그 실측값으로 잡는다.

| # | 주장 | 내 예측 |
|---|---|---|
| **X1** | 첫 페인트 전 `Layout` 이 cv 요소 **개수에 단조 증가**한다 | ✅ 요소당 준비 작업일 것 |
| **X2** | `cv-k2` 는 `plain` 과 구분이 안 된다 | ✅ 몇 개로는 비용이 안 난다 |
| **X3** | 개수당 비용이 대략 일정하다 (2배 이내) | ⚠️ 자신 없다 — 중첩 때문에 깨질 수 있다 |

X1 이 틀리면(개수와 무관하면) 비용은 **문서 전체를 훑는 고정 작업**이고,
그러면 "cv 를 적게 걸면 된다" 는 처방이 안 통한다.

## 부칙 8 — C8n: 같은 파싱 지점에서 다시 잰다 (2026-09-20, 측정 전)

### 2.8배는 내 지표가 만든 것이었다

[C8m 에서 요소당 비용이 121~332µs 로 2.8배 흔들린다고 썼다.](RESULTS.md#x3-도-반증--요소당-비용이-일정하지-않다)
기존 데이터로 원인을 찾았다.

| | UK | Philippines |
|---|---|---|
| r(FCP, 요소당 비용) | **0.76** | **0.84** |
| r(FCP, `FCP` 이전 `Layout`) | **0.81** | **0.90** |
| 행 단위 요소당 비용 범위 | 1~313µs (**388배**) | 1~488µs (**669배**) |

**분자와 분모의 기준이 다르다.**
분자(`FCP` 이전 `Layout`)는 FCP 까지만 세는데, 분모(cv 요소 수)는 **끝까지 파싱된 뒤**의 값이다.
FCP 가 이른 실행에서는 아직 파싱된 게 없어 분자가 ≈1ms 가 되고, 늦으면 크게 나온다.
**2.8배(중앙값)도, 388~669배(행 단위)도 전부 이 혼입이다.**

### 고정된 파싱 지점에서 다시 잰다

FCP 를 기준선으로 쓰면 안 된다 — FCP 자체가 팔마다 움직인다.
**DOMContentLoaded** 를 쓰면 두 팔 모두 **문서를 끝까지 파싱한 같은 지점**이다.

```
navigationStart ────── DCL(문서 파싱 완료) ────── load
                  └─ 이 구간의 Layout 을 잰다 ─┘
```

요소당 한계비용 = ( `Layout`(cv) − `Layout`(plain) ) ÷ cv 요소 수

`plain` 을 빼서 문서 자체의 레이아웃 비용을 제거한다.

| # | 주장 | 내 예측 |
|---|---|---|
| **Y1** | DCL 기준 요소당 한계비용이 **팔 4개·사이트 2곳에서 2배 이내** | ✅ 혼입을 빼면 안정될 것 |
| **Y2** | DCL 까지의 `ParseHTML` 은 모드와 무관하다 | ✅ 같은 문서를 같은 양만큼 파싱한다 |
| **Y3** | DCL 까지의 `Layout` 은 cv 요소 수에 **단조 증가**한다 | ✅ C8m 보다 깨끗하게 보일 것 |
| **Y4** | FCP 지연이 DCL 지연보다 **작지 않다** | ✅ 첫 페인트가 파싱 완료를 기다린다면 |

Y1 이 틀리면(여전히 2배를 넘으면) 요소당 비용이 정말로 균일하지 않은 것이고,
그때는 **무엇이 다른지**(중첩 깊이·블록 내용)를 따로 봐야 한다.

warm 캐시 · 2곳 × 5팔 × 8회 = 80회.
