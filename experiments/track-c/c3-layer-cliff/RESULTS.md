# C3 결과 — 2,000 레이어 절벽

측정일 2026-09-18 · Chrome **152.0.7977.83** (headless=new, GPU 가속, **vsync 끔**) · 설정마다 Chrome 새로 기동
사전 등록 예측: [PREDICTION.md](PREDICTION.md) · 하네스 [index.html](index.html) · 측정 [measure.mjs](measure.mjs) · 단계 분해 [probe-stages.mjs](probe-stages.mjs)

## 0. 먼저 — 측정 도구부터 새로 만들어야 했다

[C2 §4](../c2-anomalies/RESULTS.md#4--commit-선형성--판정-보류-대신-측정법이-틀렸다는-걸-찾았다) 에서
*"프레임 수에 기대지 않는 설계가 필요하다"* 고 적어놓고 닫았다. 그걸 먼저 만들었다.

### 왜 기존 측정이 답을 못 주는가

| 문제 | 증상 |
|---|---|
| 표본 수가 측정 대상의 함수 | 느릴수록 프레임이 적게 잡힌다. 2,000 레이어에서 3초에 **49개** |
| vsync 양자화 | 프레임 간격이 8.3ms 배수로 떨어져 '프레임당 비용'이 계단이 된다 |
| 트레이스 폭증 | 이벤트가 **레이어 × 프레임**으로 늘어난다. 8초 창에서 **140만 개** → 전송 타임아웃 |

### 그래서 만든 것 — pump 하네스

모든 박스가 **같은 커스텀 프로퍼티 하나**를 transform 에 쓴다.

```css
.box { transform: translateX(var(--tx, 0px)); will-change: transform }
```

`--tx` 를 한 번 바꾸면 레이어 N개가 전부 새 transform 을 받는다.
**k번 토글하면 표본이 정확히 k개** — 프레임이 빠르든 느리든 상관없다.
시간은 페이지 안에서 `performance.now()` 로 재므로 트레이싱도 필요 없다.

### 첫 시도는 틀렸다 — `will-change` 를 빼먹었다

처음 하네스에는 `will-change:transform` 이 없었다. **정적 transform 만으로는 합성 레이어가 생기지 않는다.**

```
요청 500 → 합성 레이어 4개      ← 박스 500개가 레이어 1장에 그려짐
```

레이어 500개의 commit 을 잰다고 생각했지만 실제로는 **박스 500개의 repaint** 를 재고 있었다.
`will-change:transform` 을 넣고 나서야 맞았다.

```
요청   500 → 합성 레이어   504
요청 2,000 → 합성 레이어 2,004
```

> 매 측정마다 `LayerTree` 로 **합성 레이어 수를 같이 세지 않았다면 끝까지 몰랐을 것이다.**
> 측정값이 그럴듯했기 때문이다 (500 레이어에서 31.5ms — 이상할 게 없어 보였다).

## 1. 타일 메모리 가설은 산수로 이미 죽는다

[C2 에서 "A2 의 512MB 예산과 관련일 수 있다"](../c2-anomalies/RESULTS.md#판정)고 적어뒀다.
**측정하기 전에 계산부터 했어야 했다.**

[A2 의 `kTileRoundUp = 64`](../../track-a/a2-gpu-memory/RESULTS-source.md) 로 38×15 박스는 64×64 타일 = **16KB**.

| 레이어 | 타일 메모리 | [512MB 예산](../../track-a/a2-gpu-memory/RESULTS-source.md) 대비 |
|---:|---:|---:|
| 1,500 | 23.4 MB | 4.6% |
| **2,000** | **31.3 MB** | **6.1%** |
| 3,000 | 46.9 MB | 9.2% |

예산을 채우려면 **32,768개**가 필요하다. 2,000 은 근처도 못 간다.

**내가 C2 에 남긴 가설은 그럴듯해 보여서 적은 것이었고, 산수 한 줄로 죽는 것이었다.**
그래도 실측으로 한 번 더 확인한다 (§3).

## 2. 절벽은 없다

레이어 500~3,000 을 토글 120회 × 4회 반복으로 쟀다. 설정당 표본 **480개**
(C2 는 2,000 레이어에서 **49개**였다).

| 레이어 | p50 ms | 95% 구간 | 레이어당 µs | 앞 구간 대비 | 반복간 편차 |
|---:|---:|---|---:|---|---:|
| 500 | 32.40 | [32.0–35.3] | 64.80 | — | 1.11배 |
| 1,000 | 46.10 | [45.7–46.7] | 46.10 | 1.42배 / 레이어 2.00배 | 1.06배 |
| 1,500 | 51.10 | [47.8–53.6] | 34.07 | 1.11배 / 레이어 1.50배 | 1.17배 |
| 1,750 | 55.70 | [51.7–61.0] | 31.83 | 1.09배 / 레이어 1.17배 | 1.29배 |
| **2,000** | **55.50** | **[50.2–61.3]** | 27.75 | **1.00배** / 레이어 1.14배 | 1.43배 |
| 2,250 | 70.60 | [63.8–75.6] | 31.38 | 1.27배 / 레이어 1.13배 | 1.50배 |
| 2,500 | 96.90 | [86.4–104.9] | 38.76 | 1.37배 / 레이어 1.11배 | 1.35배 |
| 3,000 | 100.40 | [96.7–104.7] | 33.47 | 1.04배 / 레이어 1.20배 | 1.10배 |

**2,000 은 1,750 과 구별되지 않는다.** p50 이 55.70 → 55.50 으로 오히려 조금 낮고,
95% 구간이 [51.7–61.0] 과 [50.2–61.3] 으로 거의 포개진다.

### 구간별 기울기로 보면 더 분명하다

시간 배율 ÷ 레이어 배율. 1.0 이면 정확히 비례, 1.0 미만이면 레이어보다 느리게 는다.

| 구간 | 기울기 |
|---|---:|
| 500 → 1,000 | 0.71 |
| 1,000 → 1,500 | 0.74 |
| 1,500 → 1,750 | 0.93 |
| **1,750 → 2,000** | **0.87** ← 절벽이 있다면 여기가 튀어야 한다 |
| 2,000 → 2,250 | 1.13 |
| 2,250 → 2,500 | 1.24 |
| 2,500 → 3,000 | 0.86 |

**1,750 → 2,000 이 전 구간에서 가장 완만하다.** 절벽이 있어야 할 자리가 오히려 평평하다.

### 대신 2,000~2,500 에 완만한 굽이가 있다

2,000 [50.2–61.3] 과 2,500 [86.4–104.9] 은 구간이 안 겹친다 — **이건 진짜 차이다.**
다만 3,000 에서 기울기가 0.86 으로 되돌아오므로 **임계점이 아니라 굽이**다.

고정비 + 선형 모델 `p50 = 13.2ms + 27.8µs × 레이어` 의 R² 는 **0.871**.
잔차는 2,000 에서 −19%, 2,500 에서 +17% 로 양쪽으로 갈린다 — 직선이 살짝 안 맞을 뿐
어디에도 불연속은 없다.

### 도구가 달라지니 편차가 5배 → 1.1배

| 측정 방식 | 같은 설정 반복 간 p50 편차 |
|---|---:|
| C2 (자유 실행 애니메이션, 프레임 수가 표본 수) | **5.0배** (1,000 레이어에서 2.788 vs 0.557ms) |
| C3 (pump, 토글 수가 표본 수) | **1.06~1.50배** |

**C2 의 "절벽" 은 이 5배 편차 안에 들어간다.**

## 3. 타일 메모리는 원인이 아니다 — 실측으로도

레이어 **개수는 그대로** 두고 박스만 키워 타일 메모리를 늘렸다.

| 박스 | 타일 | 레이어당 실측 |
|---|---|---:|
| 38×15 | 64×64 | 18.8~31.1 KB |
| 100×100 | 128×128 | 66.9~79.2 KB |

예측한 16KB / 64KB 의 4배 관계가 실측 **2.5~3.6배**로 확인됐다 (그 외 타일이 섞여 절대값은 더 크다).

| 레이어 | 38×15 | 100×100 | 타일 메모리 | p50 변화 |
|---:|---:|---:|---|---|
| 500 | 37.7 ms | 29.8 ms | 15 → 39 MB (2.5배) | **0.79배 (오히려 빠름)** |
| 1,000 | 46.2 ms | 40.0 ms | 26 → 70 MB (2.7배) | 0.87배 (빠름) |
| 1,500 | 36.6 ms | 62.1 ms | 34 → 98 MB (2.8배) | 1.70배 |
| 2,000 | 42.1 ms | 89.8 ms | 37 → **133 MB** (3.6배) | 2.13배 |

**타일 메모리를 3.6배로 늘려도 절벽이 낮은 레이어 수로 내려오지 않는다.**
메모리가 원인이라면 500 레이어(39MB)에서 이미 뭔가 보여야 하는데, 거기서는 **오히려 더 빠르다.**

가장 메모리를 많이 쓴 설정이 **133MB — 512MB 예산의 26%** 다. 끝까지 예산 근처도 못 간다.

> 큰 박스가 1,500 이상에서 느려지는 건 사실이지만 **매끄럽게** 느려진다(1.70 → 2.13배).
> 타일이 4배 커지면 래스터·업로드 할 픽셀도 4배라 당연한 이야기고, 예산 초과와는 무관하다.

## 4. 덤으로 — C2 가 못 닫은 ③ 이 닫혔다

[C2 §4](../c2-anomalies/RESULTS.md#4--commit-선형성--판정-보류-대신-측정법이-틀렸다는-걸-찾았다) 에서
*"commit 이 레이어 수에 선형인가"* 를 **판정 보류**로 남겼다. 세 가지 방법 모두 R² < 0.95 였다.

토글 1회를 단계별로 쪼개보니 답이 나왔다 (토글 20회 × 3회, [probe-stages.mjs](probe-stages.mjs)).

| 레이어 | 토글당 ms | Style | **Commit** | Raster | **Commit 레이어당 µs** |
|---:|---:|---:|---:|---:|---:|
| 500 | 42.01 | 12.97 | **7.08** | 0.05 | **14.2** |
| 1,000 | 49.43 | 21.80 | **14.76** | 0.37 | **14.8** |
| 1,500 | 85.82 | 33.28 | **21.49** | 40.70 | **14.3** |
| 2,000 | 107.97 | 50.59 | **30.04** | 52.51 | **15.0** |
| 2,500 | 110.17 | 45.75 | **30.10** | 44.51 | 12.0 |
| 3,000 | 161.07 | 60.05 | **45.17** | 85.59 | **15.1** |

**Commit 은 레이어당 약 14.4µs 로 거의 일정하다.** 6배 구간에서 12.0~15.1µs.
독립적인 두 번째 실행([probe-buffer.mjs](probe-buffer.mjs))에서도 14.5 / 12.1 / 14.5 / 16.1µs 로 같았다.

> **H3 채택 — commit 은 레이어 수에 선형이다. 임계점은 없다.**

### C2 는 왜 못 봤나 — 개별 이벤트의 중앙값을 봤기 때문이다

같은 데이터에서 `Commit` **개별 이벤트의 중앙값**을 보면 이렇게 나온다.

| 레이어 | 500 | 1,000 | 1,500 | 2,000 | 2,500 | 3,000 |
|---|---:|---:|---:|---:|---:|---:|
| Commit 중앙값 ms | 1.401 | 1.881 | 2.061 | **6.314** | 7.357 | 7.733 |

**2,000 에서 3배로 뛴다.** C2 가 본 게 이것이다.

그런데 **토글 1회당 Commit 합계**는 같은 구간에서 매끄럽게 는다(21.49 → 30.04).
차이는 **토글 하나에 Commit 이 몇 번 찍히느냐**다. 그 횟수가 조건에 따라 달라지므로,
개별 이벤트의 중앙값은 레이어당 비용을 재는 지표가 못 된다.

> **정해진 작업 단위(토글 1회)로 합계를 내야 한다.**
> 개별 이벤트의 분위수는 이벤트 개수가 변하면 같이 흔들린다.
> C2 에서 세 가지 방법을 다 써도 R² 가 0.95 를 못 넘은 건 셋 다 이 함정에 걸려 있었기 때문이다.

### 비선형은 commit 이 아니라 Raster 에 있다

| 레이어 | 1,000 | **1,500** |
|---|---:|---:|
| Raster ms/토글 | 0.37 | **40.70** |

**110배 뛴다.** §2 에서 본 2,000~2,500 의 굽이도 여기서 온다.
Commit·Style 은 끝까지 선형이고, 휘는 건 Raster 다. (기전은 미확인 — [§6](#6-닫지-못한-것))

### 트레이스가 잘린 게 아닌지 확인했다

1,500·2,000·2,500 의 이벤트 수가 197K·196K·189K 로 평평해서 **버퍼가 차서 버려지는 줄 알았다.**
`Tracing.bufferUsage` 로 직접 봤더니 **최대 3%** 였다. 잘린 게 아니라 그냥 편차였다.

| 레이어 | 이벤트 수 | 버퍼 최대 사용률 |
|---:|---:|---:|
| 500 | 20,833 | 0% |
| 1,500 | 161,562 | 2% |
| 2,000 | 175,708 | 2% |
| 2,500 | 211,922 | **3%** |

## 6. 닫지 못한 것

- **Raster 가 1,000 → 1,500 에서 110배 뛰는 기전.** 타일 메모리는 23 → 28MB 로 거의 안 변했다.
  박스가 240px 움직일 때 새로 보이는 영역이 생기는 것과 관련일 수 있지만 **미검증**이다
- **2,000~2,500 의 굽이.** 3,000 에서 기울기가 되돌아오므로 임계점은 아니지만 왜 휘는지는 모른다
- **세션 간 편차.** pump 로 반복 간 편차는 1.1배로 잡았지만, A 와 B 의 같은 설정(38×15, 2,000 레이어)이
  55.5ms vs 42.1ms 로 **1.3배** 다르다. 95% 구간은 안 겹친다 — 실행 단위의 무언가가 남아 있다
- 박스가 320px 스테이지 안에서 심하게 겹친다. 겹치지 않는 배치에서도 같은지는 안 봤다

## 7. 한계

- 레이어가 전부 같은 크기·같은 내용이다. 실제 페이지의 레이어는 제각각이다
- `will-change:transform` 으로 승격했다. CSS 애니메이션 승격([A1](../../track-a/a1-pipeline-skip/RESULTS.md))과
  같은 경로인지는 확인하지 않았다
- 토글당 시간은 rAF 2회를 포함한다. vsync 를 껐어도 프레임 대기가 섞여 있다
- headless · GPU 가속 · Ganesh · Chrome 152 단일 엔진

## 8. 자가 평가

**통과**

- **"절벽" 은 없었고, 없다는 걸 보이려면 도구를 새로 만들어야 했다.** 기존 방식으로 몇 번 더 재는 걸로는
  못 닫았을 것이다 — 그 방식의 반복 간 편차(5배)가 찾으려는 신호(5배)와 같은 크기였기 때문이다
- **측정 전에 산수를 한 게 컸다.** C2 에서 "A2 의 512MB 예산과 관련일 수 있다"고 적어둔 가설이
  계산 한 줄로 죽었다. 그걸 먼저 했으면 C2 에 미검증 가설을 남기지도 않았을 것이다
- **덤으로 C2 의 ③ 을 닫았다.** 개별 이벤트의 분위수 대신 **정해진 작업 단위로 합계**를 내니
  commit 이 레이어당 14.4µs 로 깔끔하게 선형이었다
- **`will-change` 를 빼먹은 하네스 버그를 잡았다.** 레이어가 4개만 생겼는데 측정값은 그럴듯했다.
  매번 `LayerTree` 로 레이어 수를 같이 센 게 유일한 방어선이었고, 이후 자동 검사로 넣었다
- **버퍼가 찬 줄 알았던 것도 확인했다.** 3% 였다. 의심을 글로만 적지 않고 쟀다
