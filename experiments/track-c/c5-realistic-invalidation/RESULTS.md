# C5 결과 — "이득은 Style" 은 최악 조건에서만 참이었다

측정일 2026-09-18 · Chrome **152.0.7977.83** (headless=new, GPU 가속)
**엄격 격리**(이전 브라우저 완전 종료 + 3초) · **조건 순서 섞음** · 설정마다 4회 · N=500 / 4,000
사전 등록: [PREDICTION.md](PREDICTION.md) · 하네스 [index.html](index.html) · 측정 [measure.mjs](measure.mjs) · 집계 [analyze.mjs](analyze.mjs)

## 결론 먼저 — C2 의 문장은 뒤집힌다

[C2 §2](../c2-anomalies/RESULTS.md#2-예측-못-한-것--layout-패스-횟수가-늘어난다) 에 이렇게 썼다.

> **`content-visibility` 의 이득은 Layout 이 아니라 Style 에서 나온다.**

**현실적인 무효화에서는 정반대다.**

| 무효화 | 이득의 출처 | 전체 |
|---|---|---|
| **컨테이너 폭만** (가장 현실적) | **Layout** (165.8 → 57.3ms). Style 은 **오히려 늘어난다**(0.41 → 9.29) | 2.73배 이득 |
| 항목 스타일 + 레이아웃 | Layout·PrePaint. Style 은 +40% | 1.53배 이득 |
| **항목 스타일만** | 없음 — **4.5배 손해** | **0.22배** |
| `:root` 변수 (C2 가 쓴 방식) | **Style** (138.2 → 57.2ms) | 1.32배 이득 |

**C2 가 본 "Style 절감" 은 네 무효화 중 하나에서만 나타난다.**
그리고 그 하나가 하필 C2 가 쓴 유일한 방식이었다.

---

## 1. 왜 C2 의 조건이 문제였나

C2 의 세 무효화는 전부 **`:root` 의 CSS 커스텀 프로퍼티**였다.
커스텀 프로퍼티는 **상속**되므로 트리 전체의 스타일이 무효화된다 — 최악 경우다.

`plain` 의 Style 비용이 무효화 방식에 따라 이렇게 다르다 (N=4,000, 무효화 1회당).

| 무효화 | `plain` 의 Style |
|---|---:|
| 컨테이너 폭만 | **0.41 ms** |
| 항목 스타일만 | 22.95 ms |
| 항목 스타일 + 레이아웃 | 26.48 ms |
| **`:root` 변수** | **138.18 ms** |

**337배 차이다.** C2 는 이 중 가장 비싼 칸 하나만 보고 "Style 이 지배한다" 고 결론냈다.

당연한 이야기다 — **건너뛸 스타일 작업이 애초에 없으면 `content-visibility` 가 절감할 것도 없다.**

---

## 2. 무효화 범위별 전체 표 (N=4,000 · 무효화 1회당 ms)

| 무효화 | 모드 | Style | Layout | PrePaint | Paint | 합계 | `plain` 대비 |
|---|---|---:|---:|---:|---:|---:|---|
| 컨테이너 폭만 | `plain` | 0.41 | **165.77** | 70.33 | 5.42 | 241.93 | — |
| | `cv-auto` | **9.29** | **57.30** | 17.25 | 4.77 | 88.60 | **2.73배 이득** |
| 항목 스타일+레이아웃 | `plain` | 26.48 | 44.59 | 83.35 | 3.40 | 157.82 | — |
| | `cv-auto` | 37.04 | 36.95 | 24.01 | 5.30 | 103.30 | 1.53배 이득 |
| 항목 스타일만 | `plain` | 22.95 | **0.00** | 5.29 | 6.42 | 34.66 | — |
| | `cv-auto` | **70.96** | **68.19** | 12.99 | 6.05 | 158.20 | **0.22배 손해** |
| `:root` 변수 | `plain` | **138.18** | 0.00 | 4.94 | 7.28 | 150.41 | — |
| | `cv-auto` | **57.21** | 42.15 | 8.69 | 5.76 | 113.81 | 1.32배 이득 |

### 제일 중요한 칸 — 컨테이너 폭만 바꿀 때

현실에서 제일 흔한 변경(반응형 폭 변화, 사이드바 토글 등)이다.

```
plain    Style  0.41   Layout 165.77   ← 비용의 거의 전부가 Layout
cv-auto  Style  9.29   Layout  57.30   ← Layout 이 2.9배 싸진다
```

**이득은 Layout 에서 나온다.** Style 은 오히려 **22배 늘어난다**(0.41 → 9.29).
C2 의 문장과 **정확히 반대**다.

> ⚠️ 다만 `cv-auto` 의 Style 반복값이 0.52 · 6.19 · 14.21 · 16.24 로 **31배 흩어진다.**
> "Style 이 늘어난다" 는 방향은 맞지만 **배수는 못 믿는다.**
> `plain` 쪽은 0.26~0.54 로 촘촘하므로 **0.41ms 라는 값 자체는 믿을 만하다.**

### 제일 나쁜 칸 — 항목 스타일만 바뀔 때

색 테마 토글처럼 레이아웃은 그대로고 항목 스타일만 바뀌는 경우다.

```
plain    Style 22.95   Layout  0.00   합계  34.66
cv-auto  Style 70.96   Layout 68.19   합계 158.20   ← 4.5배 손해
```

`plain` 은 **레이아웃을 아예 안 한다**(0.00ms). `cv-auto` 는 **68ms 를 만들어낸다.**
[C2 §2 에서 본 "없던 Layout 이 생긴다"](../c2-anomalies/RESULTS.md#2-예측-못-한-것--layout-패스-횟수가-늘어난다)가
현실적인 무효화에서 훨씬 심각하게 나타난다.

## 3. 사전 등록 주장 판정

| # | 주장 | 판정 | 실측 |
|---|---|---|---|
| **P1** | `width-inline` 에서 Style 절감이 거의 없다 | ✅ **채택** (그 이상) | 절감이 없는 정도가 아니라 **늘어난다** |
| **P2** | 항목을 건드리는 무효화에서는 Style 절감이 ≥50% | ❌ **반증** | +40% · +209% — **양쪽 다 늘어난다** |
| **P3** | `root-var` 의 절감이 가장 크다 | ✅ **채택** | 유일하게 절감하는 칸(−59%) |
| **P4** | `plain` Style 이 `root-var` 에서 5배 이상 크다 | ✅ **채택** (그 이상) | **337배** |
| **P5** | 전체로는 cv 가 네 경우 모두 이긴다 | ❌ **반증** | 항목 스타일만에서 **4.5배 손해** |

**5개 중 2개 반증.** 특히 **P2 를 틀린 게 값지다** —
*"항목 스타일을 건드리면 cv 가 절감할 것이다"* 라고 예측했는데 **오히려 늘어났다.**
`content-visibility` 가 건너뛴 서브트리의 스타일을 아낀다는 내 모형 자체가 단순했다.

## 4. 그래서 C2 의 문장을 어떻게 고쳐야 하나

| | |
|---|---|
| **C2 가 쓴 것** | "이득은 Layout 이 아니라 Style 에서 나온다" |
| **실제** | "**무효화가 트리 전체의 스타일을 건드릴 때만** Style 에서 이득이 난다. 컨테이너만 바뀌는 흔한 경우에는 이득이 **Layout** 에서 나오고, 항목 스타일만 바뀌면 **손해**다" |

C2 의 결론은 **틀린 게 아니라 조건이 빠져 있었다.** 그런데 그 조건이 워낙 특수해서,
문장만 떼어놓고 읽으면 **반대로 안내한다.**

## 5. 측정 절차 — C4d 의 수정을 처음 적용했다

[C4d](../c4-raster-threshold/RESULTS.md#610-26배는-chromium-이-아니라-내-측정-절차였다) 에서 찾은 것을 이 실험부터 반영했다.

| | |
|---|---|
| 격리 | 이전 브라우저가 **완전히 종료될 때까지** 대기 + 3초 (기존 0.5초) |
| 순서 | 64건을 **섞어서** 실행 (seed 고정, 재현 가능) |
| 기록 | 시작 시점 chrome 프로세스 수 — 46~55개로 안정 |
| 판독 | **2배 미만 차이는 "차이 없음"** 으로 읽는다 |

효과가 보인다. `:root` 변수 · `cv-auto` 의 Style 반복값이
**53.51 · 56.76 · 59.10 · 59.46 — 흩어짐 1.1배**다.
[C4c 에서 같은 종류가 26배 흩어졌던 것](../c4-raster-threshold/RESULTS.md#69-겹침-10배도-잡음이었다--그리고-왜-계속-이랬는지-알아냈다)과 대조적이다.

다만 모든 칸이 그런 건 아니다 — `컨테이너 폭만 · cv-auto` 는 31배 흩어진다.
그래서 위에서 그 칸의 **배수는 못 믿는다**고 따로 적었다.

## 6. 한계

- 여전히 **합성 리스트 하나**다. 실제 페이지의 DOM 은 이것보다 복잡하고 선택자도 많다
- 무효화 네 가지가 현실의 전부는 아니다 (스크롤·삽입/삭제·미디어쿼리 등은 안 봤다)
- `cv-auto` 의 Style 이 왜 **늘어나는지** 기전은 확인하지 않았다.
  건너뛴 서브트리 대신 `content-visibility` 자체의 판정 비용이 드는 것으로 보이지만 미검증
- 세션 **사이**의 드리프트는 여전히 못 잡는다 (C4d §6.10)
- headless · GPU 가속 · Ganesh · Chrome 152 단일 엔진

## 7. 자가 평가

**통과**

- **이 저장소에서 제일 쓸모 있을 뻔한 결론이 조건부였다는 걸 잡았다.**
  C2 의 문장을 그대로 두면 *"content-visibility 는 Style 을 아낀다"* 로 읽히는데,
  가장 흔한 경우(컨테이너 폭 변경)에서는 **이득이 Layout 에서 나온다.** 정확히 반대로 안내할 뻔했다
- **한계에 적어두고 닫은 것을 실제로 검증했다.** C2 §7 에 *"커스텀 프로퍼티는 최악 경우"* 라고
  써놓고 넘어갔었다. 적어두는 것과 재보는 것은 다르다
- **P2 를 틀렸다.** "항목 스타일을 건드리면 cv 가 아낄 것" 이라는 내 모형이 단순했고,
  실측은 오히려 늘어났다. 사전 등록을 안 했으면 그냥 넘어갔을 것이다
- **C4d 의 수정을 바로 적용했다.** 덕분에 `:root`·`cv-auto` 칸이 1.1배로 촘촘하게 나왔고,
  반대로 31배 흩어지는 칸은 배수를 인용하지 않았다

**부족**

- `cv-auto` 의 Style 이 왜 늘어나는지까지는 못 갔다. 이번엔 **거기서 멈추는 게 맞다고 판단했다** —
  이 실험의 목적은 C2 의 결론 범위를 정하는 것이었고 그건 끝났다
