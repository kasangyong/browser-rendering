# C7 결과 — 초기 로드의 실제판

측정일 2026-09-18 · Chrome **152.0.7977.83** (headless=new, GPU 가속)
**엄격 격리 + 순서 섞기** · 사이트 3곳 × 모드 2종 × **6회** = 36회 측정 (실제 로드 72회)
사전 등록: [PREDICTION.md](PREDICTION.md) · 측정 [measure.mjs](measure.mjs) · 집계 [analyze.mjs](analyze.mjs)

> 공개 페이지를 **읽기만** 했다. 로그인·폼·쓰기 없음.

---

## 결론 먼저 — 렌더링 일은 어디서나 줄지만, 사용자가 느끼는 건 한 곳뿐이었다

| 사이트 | 문서 높이 | **초기 Layout** | **LCP** | 판정 |
|---|---:|---|---|---|
| Python 문서 | 37,059px | 108.7 → 17.4ms (**−84%**) | 652 → 1,019ms (1.56배) | **차이 없음** |
| WHATWG 스펙 | 64,120px | 161.2 → 16.7ms (**−90%**) | 728 → 427ms (1.70배) | **차이 없음** |
| **Wikipedia** | **152,571px** | **22,058 → 203ms (−99%)** | **24,049 → 2,169ms (11.1배)** | **빨라짐** |

**렌더링 일은 세 곳 모두 84~99% 줄었다. 그런데 LCP 가 유의미하게 움직인 건 한 곳뿐이다.**

판정 기준은 사전 등록한 대로 **2배 미만이면 "차이 없음"** 이다
([C4d 에서 잰 흩어짐이 그 정도](../c4-raster-threshold/RESULTS.md#610-26배는-chromium-이-아니라-내-측정-절차였다)).

## 1. 렌더링 일 — cv 는 약속한 대로 건너뛴다

로드 중 총 ms · 중앙값 (6회)

| 사이트 | 모드 | Style | **Layout** | PrePaint* | Paint* |
|---|---|---:|---:|---:|---:|
| Python 문서 | `plain` | 59.9 | **108.7** | 46.3 | 21.9 |
| | `cv-auto` | 28.5 (−52%) | **17.4 (−84%)** | 6.7 | 5.0 |
| WHATWG 스펙 | `plain` | 86.6 | **161.2** | 46.3 | 9.0 |
| | `cv-auto` | 21.0 (−76%) | **16.7 (−90%)** | 8.8 | 14.5 |
| Wikipedia | `plain` | 1,085.5 | **22,058.5** | 325.1 | 54.3 |
| | `cv-auto` | 141.9 (−87%) | **203.4 (−99%)** | 41.1 | 71.0 |

\* PrePaint·Paint·ParseHTML 은 아래 §5 의 사정으로 **대표값**이라 참고용이다. Style·Layout·FCP·LCP 는 36건 전부다.

**Wikipedia 의 `plain` 은 첫 페인트 전에 레이아웃에만 22초를 쓴다.**
152,571px 를 전부 배치해야 하기 때문이다. cv 를 걸면 203ms — **99% 가 사라진다.**

## 2. 그런데 사용자가 보는 건 다르다

FCP·LCP 중앙값 (ms)

| 사이트 | `plain` | `cv-auto` | 배율 | 판정 |
|---|---:|---:|---:|---|
| Python 문서 | 652 | 1,019 | 1.56배 느림 | 차이 없음 |
| WHATWG 스펙 | 728 | 427 | 1.70배 빠름 | 차이 없음 |
| **Wikipedia** | **24,049** | **2,169** | **11.1배 빠름** | **빨라짐** |

### 반복별로 펼치면 왜 그렇게 읽어야 하는지 보인다

| 사이트 | 모드 | 반복별 LCP (ms) | 흩어짐 |
|---|---|---|---:|
| Python 문서 | `plain` | 449 · 550 · 555 · 652 · 774 · 948 | 2.1배 |
| | `cv-auto` | 419 · 514 · 581 · 1019 · 1218 · 1244 | 3.0배 |
| WHATWG 스펙 | `plain` | 402 · 570 · 600 · 728 · 900 · 1752 | 4.4배 |
| | `cv-auto` | 197 · 318 · 335 · 427 · 514 · 568 | 2.9배 |
| **Wikipedia** | `plain` | 2,422 · 19,194 · 23,218 · 24,049 · 24,220 · 30,430 | 12.6배 |
| | `cv-auto` | 1,231 · 1,644 · 1,820 · 2,169 · 2,312 · 2,705 | 2.2배 |

앞의 두 사이트는 **두 분포가 완전히 겹친다.** 네트워크가 렌더링 차이를 덮는다.
Wikipedia 는 `cv-auto` 전체가 `plain` 아래에 있다 (한 이상치 2,422ms 만 겹친다).

> **cv 는 Wikipedia 의 흩어짐도 줄였다** — 12.6배 → 2.2배.
> 레이아웃이 병목일 때는 로드 시간이 그만큼 예측 불가능해진다는 뜻이기도 하다.

## 3. 합성(C1)과 대조 — 숫자가 아니라 **조건**이 틀렸다

| | 합성 C1 | 실제 C7 |
|---|---|---|
| 초기 Layout 절감 | 82% | **84% · 90% · 99%** (같은 방향, 더 큼) |
| LCP 변화 | **−36~39%** | **차이 없음 · 차이 없음 · −91%** |

[C1 은 "LCP 가 36~39% 빨라진다"](../c1-initial-load/RESULTS.md#3-lcp-도-실제로-빨라진다--내-예측이-틀렸다)고 했다.
실제 페이지 셋 중 **둘에서는 그런 일이 없고**, 하나에서는 **훨씬 크다.**

합성 리스트(항목 4,000개·436,074px)는 **레이아웃이 병목인 페이지**였다.
그런 페이지에서는 C1 의 결론이 맞는다 — Wikipedia 가 바로 그런 경우다.
그런데 **보통 크기의 페이지에서는 레이아웃이 병목이 아니다.**

## 4. 사전 등록 주장 판정

| # | 주장 | 판정 | 실측 |
|---|---|---|---|
| **R1** | 초기 Layout 이 세 곳 모두 ≥50% 준다 | ✅ **채택** | 84% · 90% · 99% |
| **R2** | LCP 개선이 있지만 **합성보다 작다** | ❌ **반증** | 두 곳은 **차이 없음**, 한 곳은 **훨씬 큼**(−91%) |
| **R3** | FCP 가 LCP 보다 덜 개선된다 | ⚪ **측정 불가** | 36건 중 대부분 **FCP = LCP** 였다 (§6) |
| **R4** | Wikipedia 에서 개선이 가장 크다 | ✅ **채택** | 압도적 (11.1배 vs 나머지는 차이 없음) |

**사전 등록에 적어둔 "가장 그럴듯한 반증" 이 절반 맞았다** —
*"네트워크·스크립트가 지배해서 LCP 가 안 움직이는 것"*.
두 사이트에서 정확히 그렇게 됐다. 나머지 한 곳에서는 레이아웃이 22초라 네트워크가 묻혔다.

그리고 **이번엔 내 예측이 cv 에 유리한 쪽으로 편향돼 있었다** —
[C6 에서 불리한 쪽으로 편향됐던 것](../c6-real-sites/RESULTS.md#4-사전-등록-주장-판정)과 반대다.
예측할 때 그 점을 적어뒀는데, 실제로 그쪽으로 틀렸다.

## 5. 측정 사고 — 락을 손으로 지웠다

36건을 다 재고도 `results.json` 에는 **12건만** 남았다. 두 프로세스가 번갈아 덮어썼다.

[C4d 에서 똑같이 당하고 PID 검사까지 넣어놨는데](../c4-raster-threshold/RESULTS.md#610-26배는-chromium-이-아니라-내-측정-절차였다),
이번엔 **내가 `rm -f .measure.lock` 으로 그 검사를 무력화했다.** 앞선 실행이 아직 살아 있었다.

사이트에 72회를 더 요청하는 대신 **stdout 로그에서 복구**했다 ([recover.mjs](recover.mjs)).
로그에는 36건의 site·mode·FCP·LCP·Layout·Style 이 전부 있다.
`ParseHTML`·`PrePaint`·`Paint`·문서 높이는 살아남은 12건의 **설정별 대표값**이라 참고용으로만 썼다.

> **락은 지우라고 있는 게 아니다.** PID 검사를 넣어놓고 그 앞단을 내 손으로 치웠다.
> 도구를 고쳐놓고 그 도구를 안 믿은 셈이다.

## 6. 한계

- **FCP 와 LCP 가 거의 항상 같았다.** 이 문서 사이트들은 첫 페인트에 나온 요소가 그대로 LCP 요소다.
  그래서 R3(둘을 분리해 보려던 것)을 검증할 수 없었다. 이미지가 LCP 인 페이지에서는 다를 것이다
- 세 곳 다 **문서 사이트**다 ([C6 와 같은 한계](../c6-real-sites/RESULTS.md#7-한계))
- **네트워크를 완전히 제거하지 못했다.** 캐시를 데우고 HTML 은 가로채 직접 넣었지만
  하위 리소스의 재검증은 남는다. 앞 두 사이트의 흩어짐(2~4배)이 그 몫이다
- Wikipedia `plain` 에 이상치 1건(2,422ms)이 있다. 나머지 5건은 19~30초다
- headless · Chrome 152 단일 엔진

## 7. 자가 평가

**통과**

- **이 저장소에서 제일 인용하기 좋은 숫자를 검증했고, 조건이 빠져 있었다는 게 나왔다.**
  "LCP 36~39% 단축" 은 **레이아웃이 병목인 페이지에 한한** 이야기였다.
  세 곳 중 둘에서는 아무 일도 일어나지 않는다
- **렌더링 일과 사용자 체감을 따로 잰 게 결정적이었다.** LCP 만 봤으면
  *"cv 는 초기 로드에 효과 없다"* 로 잘못 닫았을 것이고,
  Layout 만 봤으면 *"84~99% 빨라진다"* 로 과장했을 것이다. **둘이 갈리는 게 답이었다**
- 판정 기준(2배)을 **측정 전에** 정해둔 덕분에 WHATWG 의 −41% 를 "빨라졌다" 고 쓰지 않았다.
  흩어짐이 4.4배인 데이터였다
- `addScriptToEvaluateOnNewDocument` 가 실패하는 걸 **스모크에서 잡았다**(`documentElement` 가 아직 없다).
  그대로 갔으면 cv 가 안 걸린 채로 36건을 재고 "효과 없음" 이라 결론냈을 것이다

**부족**

- **락을 손으로 지워 데이터를 절반 넘게 날렸다.** 같은 실수를 두 번째로 했다 (§5)
- 이미지가 LCP 인 페이지를 안 골랐다. 그래서 FCP/LCP 분리를 못 봤다
