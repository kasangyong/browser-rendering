# C7 사전 등록 예측 — 초기 로드의 실제판

> **측정 전에 작성.** 2026-09-18.
> 이 저장소에서 제일 인용하기 좋은 숫자가 **제일 검증이 안 돼 있다.**

## 왜 이걸 하나

`content-visibility` 가 팔리는 문구는 **"초기 렌더가 빨라진다"** 한 줄이다.
이 저장소에서 그걸 잰 건 [C1](../c1-initial-load/RESULTS.md) 이고, **LCP 36~39% 단축**이 결과였다.

그런데 C1 은 **내가 만든 합성 리스트**에서 나왔고,
[C6 가 그 합성 하네스가 리레이아웃에서 **양쪽으로** 틀렸다는 걸 보여줬다](../c6-real-sites/RESULTS.md) —
성능은 과소평가, 정확성은 과소평가.

| | 합성 | 실제 |
|---|---|---|
| 리레이아웃 | C1~C5 | ✅ [C6](../c6-real-sites/RESULTS.md) 에서 검증 (양쪽으로 틀림) |
| **초기 로드** | **C1 (LCP −36~39%)** | ❌ **미검증** |

**같은 하네스에서 나온 LCP 숫자만 검증을 안 받고 남아 있다.**

## 설계의 핵심 문제 — 네트워크가 렌더링 차이를 덮는다

실제 사이트의 초기 로드는 네트워크가 수백 ms 를 먹는다.
`content-visibility` 가 아끼는 건 **레이아웃 시간**인데, 그게 네트워크에 묻히면 LCP 가 안 움직인다.

### 그래서 캐시를 데운 뒤에 잰다

| 단계 | |
|---|---|
| ① 첫 로드 | 그냥 로드해서 **HTTP 캐시를 채운다.** 측정 안 함 |
| ② `addScriptToEvaluateOnNewDocument` 등록 | 문서 시작 시점에 스타일을 넣어 **첫 페인트 전에** cv 가 걸리게 |
| ③ 두 번째 로드 | **이걸 측정한다.** 캐시가 따뜻하므로 네트워크 몫이 최소 |

브라우저는 설정마다 새로 띄우고(격리), 두 로드는 그 안에서 한다.
cv 를 페이지 로드 **후에** 거는 건 의미가 없다 — 첫 페인트는 이미 끝났다.

### 그래도 남는 변동

캐시 재검증·폰트·스크립트는 남는다. 그래서:
- 설정마다 **6회** 반복, **순서를 섞는다** (네트워크 드리프트가 양쪽 팔에 똑같이 걸리게)
- **LCP 만 보지 않는다.** 로드 중 `Layout`·`Style` 총량을 같이 재서
  *"렌더링 일은 줄었는데 LCP 가 안 움직였다"* 와 *"아무것도 안 줄었다"* 를 구분한다

## 측정 대상

[C6 와 같은 3곳](../c6-real-sites/PREDICTION.md) — 선택자·intrinsic 값도 그대로.

| 사이트 | 블록 | DOM | 문서 높이 |
|---|---:|---:|---:|
| Wikipedia (Unicode 목록) | 698 | 47,925 | 152,571px |
| WHATWG HTML Standard | 410 | 9,320 | 64,120px |
| Python 문서 | 77 | 7,011 | 37,059px |

측정: **FCP · LCP** (C1 과 같은 트레이스 이벤트) + 로드 중 `ParseHTML`·`Style`·`Layout`·`PrePaint`·`Paint`

## 예측

| # | 주장 | 내 예측 |
|---|---|---|
| **R1** | 초기 `Layout` 이 세 곳 모두 **크게 준다** (≥50%) | ✅ C6 의 리레이아웃과 같은 방향일 것 |
| **R2** | LCP 개선이 있지만 **합성의 36~39% 보다 작다** | ✅ 실제 페이지는 레이아웃 말고도 할 일이 많다 |
| **R3** | FCP 는 LCP 보다 **덜** 개선된다 | ✅ 첫 페인트는 화면 위쪽만 필요하다 |
| **R4** | DOM 이 큰 **Wikipedia 에서 개선이 가장 크다** | ✅ 건너뛸 일이 제일 많다 |

### 틀릴 수 있는 지점

**가장 그럴듯한 반증**: 네트워크·스크립트·폰트가 지배해서 **LCP 가 아예 안 움직이는** 것.
그러면 R1(렌더링 일은 줄었다)은 맞고 R2(LCP 개선)는 틀린다.
그 경우 **"content-visibility 는 초기 렌더를 빠르게 한다" 는 문구 자체가 실제 페이지에서는 과장**이 된다.

[C6 에서 내 예측이 전부 "실제가 cv 에 불리할 것" 쪽으로 편향돼 있었다](../c6-real-sites/RESULTS.md#4-사전-등록-주장-판정).
이번엔 반대로 **cv 에 유리한 쪽으로 예측**하고 있다는 걸 적어둔다 — 그 편향도 의심한다.
