# A2 결과 — 합성 레이어의 GPU 메모리 비용

측정일 2026-09-17 · Chrome **152.0.7977.83** (headless=new, **GPU 가속 켜짐**) · RTX 4050 Laptop / Intel Iris Xe
격리: **설정당 Chrome 새로 기동** · 지표: `gpu/shared_images` (memory-infra 덤프)
설계·사전검증: [README.md](README.md) · 원자료: `isolated-results-*.json`

---

> ⚠️ **정정됨** — 아래 "2의 거듭제곱" 규칙은 **틀렸다.** 실제로는 **64의 배수로 올림**(`kTileRoundUp = 64`)이며,
> 이 문서의 세 표본(38×15 / 100×100 / 200×200)이 하필 두 규칙의 답이 같은 값이라 구분되지 않았을 뿐이다.
> 소스 확인과 판별 실험: **[RESULTS-source.md](RESULTS-source.md)** · 실측 수치 자체는 그대로 유효하다.

## 결론 먼저

**레이어의 텍스처는 실제 크기가 아니라 2의 거듭제곱 정사각 타일로 올림된다.** 최소 64×64.

| 박스 크기 | 실제 픽셀 메모리 | **예측 타일** | **실측 KB/레이어** | 오버헤드 |
|---|---:|---|---:|---:|
| 38×15 | 2.23 KB | 64×64 → **16 KB** | **15.4 ~ 16.4** | **7.2×** |
| 100×100 | 39.1 KB | 128×128 → **64 KB** | **64.5** | **1.64×** |
| 200×200 | 156.3 KB | 256×256 → **256 KB** | **250.0 ~ 253.7** | **1.64×** |

세 크기 모두 예측과 **오차 2% 이내**로 맞는다.

그리고 **타일 메모리에는 약 500MB 상한이 있다.** 그 위로는 레이어를 계속 승격하면서도 메모리를 더 주지 않는다.

---

## 1. 개수에 대한 선형성 — 38×15 박스

기준선 = `none` 모드(레이어 5개) 전체 측정 36회 평균 **48.3MB** (범위 17.5~58.4, 워밍업 이상치 포함)

| 레이어 | `gpu/shared_images` | 기준선 대비 | KB/레이어 |
|---:|---:|---:|---:|
| 1 | 51.82MB | +3.5MB | (3566) |
| 205 | 49.73MB | +1.4MB | (7.2) |
| 1005 | 59.87MB | +11.5MB | 11.8 |
| 2005 | 78.33MB | +30.0MB | 15.4 |
| 4006 | 105.98MB | +57.6MB | 14.8 |
| 8005 | 176.29MB | +128.0MB | **16.4** |

**괄호 친 값은 믿으면 안 된다.** 기준선 노이즈가 ±8MB인데 델타가 그보다 작기 때문이다.
레이어 1000개 이상부터 신호가 노이즈를 넘고, 8000개에서 16.4 KB/레이어로 수렴한다.

최소제곱 적합 (1005 / 2005 / 4006 / 8005):
```
gpu/shared_images(MB) ≈ 50.0 + 0.0157 × 레이어수
                         └ 기준선     └ 16.1 KB/레이어
```
적합에서 나온 절편 50.0MB가 실측 기준선(48.3MB)과 일치한다 — 모델이 자기 정합적이다.

> 📌 **16.1 KB = 64 × 64 × 4 bytes 와 정확히 같다.** 여기서 "최소 타일 64×64" 가설이 나왔고, 아래에서 검증했다.

---

## 2. 크기에 대한 검증 — 가설을 예측으로 바꿔 시험

레이어 4000개 고정, 박스 크기만 변경:

| 크기 | 실측 총량 | 기준선 대비 | KB/레이어 | 예측(2ⁿ 정사각) | 일치 |
|---|---:|---:|---:|---|---|
| 38×15 | 105.98MB | +57.6MB | 14.8 | 64×64 = 16 KB | ✅ 92% |
| 100×100 | 300.46MB | +252.1MB | **64.5** | 128×128 = 64 KB | ✅ **101%** |
| 200×200 | 549.37MB | +501.0MB | 128.3 | 256×256 = 256 KB | ❌ 50% ← §3 |

100×100 이 예측 64KB에 **64.5KB로 적중**한 게 결정적이다. 실제 픽셀(39.1KB)도, 단순 비례도 아닌 **다음 2의 거듭제곱**이라는 게 확인됐다.

200×200 만 절반으로 어긋나는데, 이유는 개수를 줄여보면 드러난다.

---

## 3. 타일 메모리 상한 ≈ 500MB

200×200 박스로 개수를 바꿔가며:

| 레이어 | `gpu/shared_images` | 기준선 대비 | KB/레이어 |
|---:|---:|---:|---:|
| 255 | 115.50MB | +67.2MB | 275.1 |
| 505 | 170.43MB | +122.1MB | 250.0 |
| 1005 | 294.03MB | +245.7MB | 251.6 |
| 2006 | 543.90MB | +495.6MB | **253.7** |
| 4006 | 549.37MB | +501.0MB | **128.3 ← 절반** |

```
메모리
501MB  ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄╭━━━━━━━  상한
                      ╱
245MB              ╱
122MB          ╱
 67MB      ╱
        255   505  1005  2006   4006 (레이어)
```

255~2006 구간에서 **250~254 KB/레이어로 일정**하다. 예측한 256KB와 일치한다.
4006에서 KB/레이어가 절반으로 떨어지는 건 레이어가 싸진 게 아니라 **총량이 501MB에서 멈췄기** 때문이다.

**즉 Chromium은 레이어 승격은 무제한으로 하면서, 타일 메모리는 예산으로 막는다.**
레이어 4006개는 전부 만들어지지만(LayerTree 확인), 그중 상당수는 타일을 못 받는다.

---

## 4. `left` 는 개수와 무관하게 평탄

`left` 와 `none` 은 박스가 1개든 8000개든 레이어가 **5~6개**로 고정이고, GPU 메모리도 기준선(≈50MB) 근처에서 움직이지 않는다.

합성 레이어를 안 만드는 대신 **매 프레임 Layout·Paint·Raster를 다시 돈다** ([A1 결과](../a1-pipeline-skip/RESULTS.md)).
`transform` 은 그 작업을 GPU 메모리와 맞바꾼 것이다.

---

## 5. 실무로 옮기면

[강의 §6 보강](../../../docs/lecture/01-rendering-pipeline.md#6-layer-슬라이드--)에 적은 *"레이어는 공짜가 아니다"* 의 값이 이것이다.

| 상황 | 추가 GPU 메모리 |
|---|---:|
| 작은 아이콘(38×15) 100개에 `will-change: transform` | 1.6 MB |
| 카드(200×200) 100개 | **25 MB** |
| 카드(200×200) 1,000개 | **250 MB** |
| 카드(200×200) 2,000개 | **~500 MB (상한 도달)** |

- **작은 요소일수록 낭비 비율이 크다** — 38×15는 실제 필요량의 7.2배를 쓴다. `will-change` 를 작은 요소에 뿌리는 게 특히 나쁜 이유
- **상한에 닿으면 조용히 나빠진다.** 에러도 경고도 없고, 타일을 못 받은 레이어가 다시 래스터되면서 스크롤이 끊긴다
- 데스크톱 상한이 500MB면 **모바일은 훨씬 낮다**

## 6. 폐기한 방법 (기록용)

**① 한 브라우저에서 설정만 바꿔 측정 → 오염**
GPU 리소스 풀이 설정 사이에 이월된다. 증상:
- `left` 값이 n=1000/2000/4000 에서 소수점까지 동일 (45.15 / 66.22 / 78.44)
- 레이어 6개인 `none` 이 레이어 4006개인 `transform` 보다 메모리가 많음

→ 설정마다 Chrome 을 새로 띄워야 한다. 느리지만 이월이 불가능해진다.

**② rep 0 을 그대로 쓰기 → 워밍업 이상치**
각 그룹의 첫 반복이 일관되게 낮다 (200 none → **22.31** / 54.31 / 47.93). reps 1·2 는 소수점까지 재현된다.

## 7. 남은 한계

- 2의 거듭제곱 정사각 타일은 **실측에서 유도한 경험칙**이다. Chromium 소스에서 타일 크기 결정 로직을 확인하지 않았다 (`cc/tiles/tile_manager.cc` 계열)
- 500MB 상한값도 이 기기·이 뷰포트(1280×900) 기준이다. 예산 산정식은 확인 못 함
- 박스가 전부 같은 크기·같은 애니메이션이다
- Skia **Graphite 가 아니라 Ganesh** 경로다 (`skia_graphite: disabled_off`). [Graphite](../../../docs/01-landscape-2026.md#31-skia-graphite-chrome의-차세대-래스터-백엔드) 에서는 메모리 특성이 달라질 수 있다

## 8. 자가 평가

**통과**

잘한 것
- **계측기를 먼저 검증했다** (A1 교훈 #2). P1~P3 통과 전에는 본 실험을 시작하지 않았고, 그 과정에서 A1b에 잘못 적은 "headless는 GPU 없음"도 바로잡았다
- 1차 측정을 **의심하고 폐기**했다. `left` 값이 소수점까지 같은 걸 그냥 넘겼으면 전부 틀린 결론이 나왔다
- **가설 → 예측 → 검증** 순서로 갔다. 16.1KB에서 "64×64 타일"을 추론하고, 100×100/200×200으로 예측을 시험해 101% 적중을 얻었다. 우연의 일치가 아님을 보인 것

못한 것
- **본 스윕의 성공 기준을 사전에 문서로 못 박지 않았다.** A1 교훈 #3을 지키지 않았다. 사전 검증(P1~P3)만 문서화했고 본 실험은 탐색적으로 진행했다 — 결과가 깨끗해서 문제가 안 드러났을 뿐, 프로세스 회귀다
- 다음 실험에서는 측정 전에 기준표를 파일로 먼저 쓴다
