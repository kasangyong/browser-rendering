## 결론 먼저

**`yield` 만 하면 INP는 거의 완벽해지지만, 사용자는 여전히 210ms를 기다린다.**

INP는 "입력 → **다음 프레임**"을 잰다. 그 프레임에 **내 작업 결과가 들어있는지는 보지 않는다.**
핸들러가 아무것도 안 바꾸고 양보하면, 브라우저는 빈 프레임을 내고 INP는 16ms 미만이 된다. 지표는 초록불인데 화면은 그대로다.

**화면부터 갱신하고(`paint-first`) + 작업을 쪼개 양보해야(`yield`)** 지표와 체감이 같이 좋아진다.

## 1. 전체 결과 (작업량 200ms 고정)

| 전략 | INP p75 | INP 기록 건수¹ | 화면 갱신 p75 | LoAF blocking 합 |
|---|---:|---:|---:|---:|
| `sync` | **208ms** | 12 / 12 | 201.6ms | **1,805ms** |
| `yield` | **<16ms**² | 0~2 / 12 | **210.4ms** | **0ms** |
| `paint-first` | **16ms** | 6~10 / 12 | 207.1ms ⚠️³ | 1,801ms |
| **`paint-first+yield`** | **16ms** | 9~10 / 12 | **17.6ms** | **0ms** |
| `worker` | **16ms** | 8~12 / 12 | **15.3ms** | **0ms** |

¹ Event Timing 은 16ms 미만 상호작용을 기록하지 않는다. 건수가 적다 = 대부분 16ms 안에 끝났다는 뜻.
² 12번 중 10~12번이 기록조차 안 됐다 → INP < 16ms.
³ **이 값은 무효다.** §3 참조.

## 2. 핵심 발견 — INP는 "결과가 보이는 시점"이 아니다

`yield` 는 5ms씩 쪼개며 양보하고, 화면 갱신(`repaint()`)은 **작업이 다 끝난 뒤**에 한다.

```js
'yield': async () => {
  let left = 200;
  while (left > 0) { busy(5); left -= 5; await yieldToMain(); }
  repaint();          // ← 200ms 뒤
}
```

결과:
- **INP: 16ms 미만** (12번 중 10~12번이 임계값 미달로 기록조차 안 됨)
- **실제 화면 갱신: 210ms**

핸들러가 첫 5ms만 쓰고 양보하니 브라우저는 곧바로 프레임을 낸다. 그 프레임에는 **아무 변화도 없다.**
Event Timing 은 그걸 "다음 페인트"로 세고 상호작용을 종료 처리한다.

> **INP 200ms 기준을 통과했다고 사용자가 빠르다고 느끼는 건 아니다.**
> 반대로 말하면, INP는 양보만으로 쉽게 좋아 보이게 만들 수 있다.

## 3. 측정 함정 — `paint-first` 의 화면 갱신 값은 무효

`paint-first` 는 화면부터 바꾸고 작업을 뒤로 미룬다.

```js
'paint-first': async () => {
  repaint();
  await yieldToMain();
  busy(200);          // ← 여기서 메인 스레드가 200ms 막힌다
}
```

내 화면 갱신 측정은 `requestAnimationFrame` 2회로 시점을 찍는데, **그 콜백도 메인 스레드에서 돈다.**
`busy(200)` 이 메인을 잡고 있으니 콜백이 200ms 뒤에야 실행된다 → 207ms 라는 **거짓 값**이 나온다.

진짜 값은 브라우저 자신이 잰 **INP 16ms** 다. 픽셀은 16ms에 나왔고, 내 계측기만 늦게 깨어났다.

**교차 검증**: 같은 `repaint()` 를 앞에 두되 작업도 쪼갠 `paint-first+yield` 는 메인이 막히지 않으므로 측정이 유효하다 → **17.6ms**. INP(16ms)와 일치한다.
→ `paint-first` 의 실제 화면 갱신도 ~16ms 였다는 뜻이다.

> [A1에서 배운 것](../a1-pipeline-skip/RESULTS.md#5-도중에-버린-방법-두-가지-기록용)이 그대로 반복됐다: **관찰 도구가 메인 스레드에 걸리면 관찰이 망가진다.**

## 4. 사전 등록 주장 판정

| # | 주장 | 판정 | 실측 |
|---|---|---|---|
| **F1** | `sync` INP p75 ≥ 200ms | ✅ | 208ms |
| **F2** | `worker` INP p75 ≤ 50ms | ✅ | 16ms |
| **F3** | `paint-first` INP p75 ≤ 50ms | ✅ | 16ms |
| **F4** | `yield` INP < `sync` | ✅ | <16ms vs 208ms |
| **F5** | `sync` 의 LoAF blocking 이 다른 전략보다 큼 | ⚠️ **부분** | sync 1,805 ≈ **paint-first 1,801** (사실상 동률) |

F4에 대해 예측할 때 *"성립하되 폭이 작을 것(150~210ms)"* 이라 적었는데 **틀렸다.** `yield` 는 INP를 16ms 미만으로 만들었다.
다만 예측의 배경이던 가설 — *"repaint 가 끝에 있으면 사용자는 여전히 기다린다"* — 은 맞았다. **INP가 그걸 반영하지 않을 뿐이었다.**

F5가 부분 성립인 이유: `paint-first` 도 작업을 통째로 돌려 메인을 1,801ms 막는다. INP만 좋고 **후속 상호작용은 여전히 막힌다.**

## 5. 정리 — 네 가지 축으로 봐야 한다

| 전략 | 첫 반응(INP) | 결과가 보이는 시점 | 후속 상호작용 | 총 처리량 |
|---|---|---|---|---|
| `sync` | ❌ 208ms | ❌ 201ms | ❌ 막힘 | ✅ 최고 |
| `yield` | ✅ <16ms | ❌ **210ms** | ✅ 안 막힘 | ⚠️ 양보 오버헤드 |
| `paint-first` | ✅ 16ms | ✅ 16ms | ❌ **1,801ms 막힘** | ✅ 좋음 |
| **`paint-first+yield`** | ✅ 16ms | ✅ **17.6ms** | ✅ **안 막힘** | ⚠️ 오버헤드 |
| `worker` | ✅ 16ms | ✅ 15.3ms | ✅ 안 막힘 | ✅ 최고 |

**권장 순서**
1. **워커로 보낼 수 있으면 워커** — 모든 축에서 최고. 단 DOM 접근 불가
2. 못 옮기면 **`paint-first` + 시간 분할 양보** — 화면부터 바꾸고 작업을 쪼갠다
3. 양보만 하는 건 **지표만 고치고 체감은 그대로**다

[강의 02](../../../docs/lecture/02-javascript-and-rendering.md)의 네 대응 중 **"화면부터 갱신한다"가 빠져 있었다.** 그게 INP와 체감을 갈라놓는 조각이다.

## 6. 한계

- 작업량 200ms 한 값만 시험했다. 50ms·1000ms 에서 양상이 다를 수 있다
- 클릭 간격을 550ms 로 두어 상호작용이 겹치지 않는다. 실제 연타 상황은 다르다
- headless 라 실제 입력 지연(하드웨어 → 브라우저)이 빠져 있다. `inputDelay` 가 0.2~1ms 로 비현실적으로 작다
- INP는 세션 전체의 상위 백분위 하나를 쓰는 지표인데, 여기서는 클릭 12회의 p75로 근사했다
- `scheduler.yield()` 지원 환경(Chrome)에서만 쟀다. Safari 폴백(`setTimeout`) 경로는 미측정
