## 결론 먼저

**가설은 증명됐다.** `transform` 애니메이션은 Layout·Paint·Raster를 건너뛰고, 메인 스레드가 완전히 막혀도 컴포지터가 프레임을 계속 만든다.

단, **사전에 정한 성공 기준 4개 중 2개는 실패했다.** 가설이 틀려서가 아니라 **내가 고른 지표(rAF 프레임 시간)가 나쁜 계측기**였기 때문이다. 아래 §4에 그대로 기록한다.

## 1. 핵심 측정 — 박스 5개, 모드당 4초

박스를 5개로 줄이자 세 모드 모두 **정확히 같은 프레임 수(482)** 를 냈다. 프레임 수가 같으니 이벤트 수를 그대로 비교할 수 있다.

| 파이프라인 단계 | `left` | `transform` | 감소 배율 |
|---|---:|---:|---:|
| `UpdateLayoutTree` (style) | 482회 / 90.2ms | 482회 / 92.0ms | **1.0× (동일)** |
| `Layout` | 482회 / 63.4ms | **15회** / 5.8ms | **32×** |
| `PrePaint` | 482회 / 78.0ms | 482회 / 60.8ms | 1.0× (동일) |
| `Paint` | 2,832회 / 194.1ms | **30회** / 6.8ms | **94×** |
| `Commit` | 483회 / 60.1ms | 482회 / 95.7ms | 1.0× |
| `RasterTask` | 979회 / 45.8ms | **15회** / 1.5ms | **65×** |
| **`InvalidateLayout`** | **497회** | **0회** | **∞** |

`transform + will-change` 는 `transform` 과 사실상 동일했다 (Layout 16 / Paint 32 / Raster 16).

### 읽는 법

**`InvalidateLayout` 497 → 0 이 가장 깨끗한 증거다.**
[Life of a Pixel의 invalidation 슬라이드](../../../docs/video/01-life-of-a-pixel-2020.md#invalidation-1720--강의에-없던-좋은-슬라이드)에 나온 `LayoutObject::SetNeedsLayout()` 이 바로 이 이벤트다.
`left`는 매 프레임 레이아웃을 무효화하고, `transform`은 **단 한 번도 하지 않는다.**

`Layout`/`Paint`/`RasterTask`가 15~30회씩 남는 건 0이 아니라 **애니메이션과 무관한 잔여 작업**이다 (4초 동안 15회 ≈ 0.25초에 1회, 프레임과 무관한 주기).

### 예상과 달랐던 것 — style과 prepaint는 안 줄어든다

`UpdateLayoutTree`(style recalc)와 `PrePaint`는 **양쪽 모두 482회, 즉 매 프레임 실행**된다.

- [RenderingNG 13단계](../../../docs/01-landscape-2026.md#12-13단계-파이프라인)는 "animations ... can skip layout, pre-paint and paint"라고 쓰지만,
- 실측에서는 **Layout / Paint / Raster만** 스킵되고 **Style / PrePaint는 매 프레임 돈다**.

다만 비용은 무시할 만하다 (style 0.19ms/프레임, prepaint 0.13ms/프레임 — 두 모드 동일).
문서의 "skip"은 **비용이 드는 작업을 건너뛴다**는 뜻이지 라이프사이클 단계 자체를 호출하지 않는다는 뜻이 아니다. 단계는 매 프레임 호출되고, **할 일이 없어서 즉시 반환**한다.

## 2. 부하 상황 — 박스 600개

| 단계 | `left` | `transform` |
|---|---:|---:|
| 프레임 수 | 91 | 134 |
| `Layout` | 91회 / 176.6ms | 15회 / 13.2ms |
| `Paint` | **44,507회** / 1,355.7ms | 30회 / 21.7ms |
| `RasterTask` | 274회 / 186.1ms | 15회 / 2.6ms |
| rAF 실측 FPS | **22.9** | **36.1** |
| p95 프레임 시간 | 58.2ms | 41.7ms |

`Paint` 44,507회는 박스 600개 × 프레임 91회 × display item 여러 개. **박스마다 매 프레임 다시 그린다**는 게 숫자로 드러난다.

### ⚠️ 미해결 이상치

600개에서 `transform`의 style recalc **총 시간이 오히려 더 길다** (1,453ms vs 623ms).
프레임당으로 봐도 10.9ms vs 6.9ms로 `transform`이 비싸다. 5개에서는 완전히 동일했는데(0.19ms) 600개에서 역전된다.

가설: 애니메이션 600개의 **컴포지터 승격 자격 검사**가 매 프레임 반복되는 비용. 확인 못 함 — [열린 질문](#5-열린-질문)으로 남긴다.

## 3. S4 — 메인 스레드를 막아도 움직이는가

**박스 1개, 메인 스레드 1,500ms 완전 점유** 중 컴포지터 스레드 활동:

| 모드 | Compositor 이벤트 | `MainFrame.Draw` | **`Swap`(화면 제출)** |
|---|---:|---:|---:|
| `left` | 4,512 | **0** | **0** |
| `transform` | 17,948 | 536 | **360** |
| `transform + will-change` | 17,941 | 536 | **360** |

**메인 스레드가 죽어 있는 1.5초 동안 `transform`은 360프레임을 화면에 제출했다. `left`는 0이다.**

`left`에서도 Compositor 이벤트가 4,512개 있지만 전부 내부 관리 작업이고 **새 프레임은 한 장도 나오지 않았다**.

이게 [강의 §6](../../../docs/lecture/01-rendering-pipeline.md#6-layer-슬라이드--)의 "움직이는 부분과 움직이지 않는 부분 분리"와 [강의 02](../../../docs/lecture/02-javascript-and-rendering.md)의 "메인 스레드 경쟁"이 만나는 지점이다.

## 4. 성공 기준 판정 (사전 정의한 그대로)

| # | 기준 | 판정 | 근거 |
|---|---|---|---|
| S1 | `transform` p95가 `left`의 **절반 이하** | ❌ **실패** | 58.2ms → 41.7ms = 1.40배. 2배 못 미침 |
| S2 | `left`만 지연 프레임 발생, `transform`은 ~0 | ❌ **실패** | left 6/216 vs transform 3/222. 분리 안 됨 |
| S3 | style+layout 구간이 `left`에서만 유의미 | ⚠️ **대체 충족** | LoAF 대신 트레이스로 측정. Layout 482→15, InvalidateLayout 497→0 |
| S4 | 메인 블록 중 `transform`만 계속 움직임 | ✅ **통과** | Swap 360 vs 0 |

### S1·S2가 실패한 이유 — 계측기를 잘못 골랐다

`rAF` 콜백 간격은 **애니메이션 비용만 재는 게 아니다.** 내 측정 루프 자체, 브라우저의 프레임 스케줄링, headless의 프레임 상한이 전부 섞인다. `left`가 레이아웃을 600번 더 돌아도 프레임 시간은 1.4배밖에 안 벌어진다.

**"프레임 시간"은 결과이고, "어느 단계가 돌았나"가 원인이다.** 원인을 직접 세는 트레이스로 바꾸자 32~94배 차이가 나왔다. 처음부터 트레이스로 설계했어야 했다.

## 5. 도중에 버린 방법 두 가지 (기록용)

재현하려는 사람이 같은 함정에 빠지지 않도록 남긴다.

**① 브라우저 패널에서 rAF 측정 → 무효**
`document.hidden === true` 일 때 rAF가 **완전히 멈춘다**. Claude 브라우저 패널이 가려져 있으면 측정 구간이 통째로 비고, 그걸 모르면 빈 배열을 정상 측정으로 착각한다.
→ 하네스에 **커버리지 검사**(실제 프레임 / 기대 프레임 < 0.5 면 무효 표시)를 넣어 방어했다.

**② `Page.captureScreenshot` 으로 S4 관찰 → 무효**
[`s4-probe.mjs`](s4-probe.mjs) 로 확인한 사실:

| 항목 | 결과 |
|---|---|
| busy loop 2,000ms 중 `Runtime.evaluate` 응답 | 1,846ms → **메인 스레드는 확실히 막힌다** |
| busy loop 2,000ms 중 `captureScreenshot` 응답 | 1,936ms → **스크린샷도 메인 스레드에 걸린다** |

즉 블록 중에는 스크린샷을 찍을 수 없다. 첫 시도에서 "3개 모드 전부 움직였다"는 결과가 나왔는데, 그건 **4장이 전부 블록이 끝난 뒤 찍힌 것**이었다. 하마터면 `left`도 컴포지터에서 돈다고 보고할 뻔했다.

## 7. 자가 평가

**보통**

- 가설은 결정적으로 증명됐다 (S3 대체·S4 통과). `InvalidateLayout 497 → 0` 과 `Swap 360 vs 0` 은 반박하기 어려운 증거다.
- 그러나 **사전 정의한 4개 기준 중 2개가 실패**했고, 측정 방법을 **두 번 갈아엎었다**. 실험 설계가 처음부터 옳지 않았다.
- A2(레이어 승격 관찰)로 넘어가기 전에 고칠 것:
  1. rAF 프레임 시간을 **1차 지표로 쓰지 않는다**. 트레이스 이벤트 카운트가 기본
  2. 관찰 도구가 메인 스레드에 걸리는지 **먼저 검증**한 뒤 쓴다
  3. 성공 기준은 "몇 배 빠른가"가 아니라 **"어떤 이벤트가 몇 번 도는가"** 로 쓴다
