# A4 결과 — `content-visibility: auto`

측정일 2026-09-17 · Chrome **152.0.7977.83** (headless=new, GPU 가속) · 설정마다 Chrome 새로 기동 · 3회 반복
강제 리레이아웃 8회 구간만 트레이싱 (DOM 생성 비용 제외)
사전 등록 예측: [PREDICTION.md](PREDICTION.md) · 하네스: [index.html](index.html) · 원자료: [results.json](results.json)

---

## 결론 먼저 — 내 예측이 틀렸다

**`content-visibility: auto` 는 비용을 "콘텐츠 양과 무관"하게 만들지 않는다.** 여전히 **O(N)** 이다.

| | 예측 | 실측 |
|---|---:|---:|
| `plain` 의 Layout, N=100 → 8000 | ≥40배 | **78.1배** ✅ |
| `cv-auto` 의 Layout, N=100 → 8000 | **<5배** | **21.4배** ❌ |

바뀌는 건 **기울기**지 차수가 아니다. 항목당 비용이 **9.8µs → 1.25µs (7.8배)** 로 줄 뿐, 항목 수에는 그대로 비례한다.

**이유**: `content-visibility: auto` 는 각 요소의 **서브트리**를 건너뛴다. **요소 상자 자체는 여전히 레이아웃된다.**
8000개를 배치하고 위치를 정하는 일은 그대로 해야 한다. — 그래서 `contain-intrinsic-size` 가 필요한 것이기도 하다.

## 1. 단계별 비용 (리레이아웃 1회당 ms)

| N | 모드 | Style | Layout | PrePaint | Paint | **합계** |
|---:|---|---:|---:|---:|---:|---:|
| 100 | `plain` | 1.37 | 1.01 | 0.53 | 0.65 | 3.56 |
| | `cv-auto` | 0.76 | 0.47 | 0.34 | 0.55 | **2.12** |
| 500 | `plain` | 7.52 | 4.89 | 2.57 | 0.80 | 15.78 |
| | `cv-auto` | 1.38 | 0.78 | 0.81 | 0.53 | **3.50** |
| 2000 | `plain` | 19.87 | 18.55 | 9.39 | 1.36 | 49.17 |
| | `cv-auto` | 4.48 | 2.58 | 2.57 | 0.90 | **10.53** |
| 8000 | `plain` | 82.42 | 78.50 | 40.39 | 3.53 | 204.84 |
| | `cv-auto` | 14.95 | 10.00 | 10.64 | 3.02 | **38.61** |

N=8000에서 **전체 81% 절감**. 단계별로는:

| 단계 | 절감 |
|---|---:|
| Layout | **87%** |
| Style (`UpdateLayoutTree`) | **82%** |
| PrePaint | **74%** |
| **Paint** | **14%** ← §3 |

## 2. 스케일링 — 차수는 그대로, 기울기만 바뀐다

N=8000 / N=100 배율:

| 모드 | Layout | Style | Paint |
|---|---:|---:|---:|
| `plain` | **78.1배** | 60.1배 | 5.4배 |
| `cv-auto` | **21.4배** | 19.7배 | 5.5배 |
| `cv-nosize` | 20.6배 | 17.9배 | 5.0배 |

`plain` 의 78.1배는 N 증가폭(80배)과 거의 같다 — **완전한 선형**.
`cv-auto` 는 21.4배로 완만해졌지만 **평탄과는 거리가 멀다**.

### 절감률은 N이 커질수록 좋아지다 수렴한다

| N | `plain` Layout | `cv-auto` Layout | 절감 | 배율 |
|---:|---:|---:|---:|---:|
| 100 | 1.01ms | 0.47ms | 54% | 2.2배 |
| 500 | 4.89ms | 0.78ms | 84% | 6.2배 |
| 2000 | 18.55ms | 2.58ms | 86% | 7.2배 |
| 8000 | 78.50ms | 10.00ms | **87%** | **7.8배** |

작은 리스트(100개)에서는 2.2배밖에 안 된다. 고정 비용이 상대적으로 크기 때문이다.
**`content-visibility` 는 리스트가 클수록 유리하고, 작으면 쓸 이유가 별로 없다.**

### 항목당 비용으로 보면 모델이 선명하다

```
항목 1개당 Layout 비용 (N=8000 기준)
  plain    78.50ms / 8000 = 9.80 µs   ← 상자 + 서브트리(h3 + p + span×3)
  cv-auto  10.00ms / 8000 = 1.25 µs   ← 상자만
                            ─────
  서브트리가 항목당 비용의 87%
```

**절감률은 "항목의 서브트리가 얼마나 무거운가"로 결정된다.**
내 항목은 요소 5개짜리라 87%가 나왔다. 테이블·중첩 플렉스처럼 무거우면 더, 단순 텍스트 한 줄이면 훨씬 적다.

## 3. 가장 뜻밖이었던 것 — Paint 는 원래도 안 하고 있었다

| N | `plain` Paint | `cv-auto` Paint |
|---:|---:|---:|
| 100 | 0.65ms | 0.55ms |
| 8000 | 3.53ms | 3.02ms |
| **N 배율** | **5.4배** | **5.5배** |

**`plain` 조차 Paint 비용이 N에 거의 비례하지 않는다** (80배 늘었는데 5.4배).
Chromium은 `content-visibility` 없이도 **화면 밖 콘텐츠의 페인트를 이미 컬링한다.**

→ 예측 C3(Paint 90% 이상 감소)는 **반증**. 실측 14%다.
→ `content-visibility` 의 실질 이득은 **Style·Layout·PrePaint** 에 있지, Paint 에 있지 않다.

"layout **and paint** 를 건너뛴다"는 흔한 설명은 이 조건에서는 절반만 맞다.

---

## 4. `contain-intrinsic-size` 는 속도가 아니라 정확성을 위한 것

| 모드 | Layout (N=8000) | `scrollHeight` |
|---|---:|---:|
| `plain` (진짜 높이) | 78.50ms | **872,328px** |
| `cv-auto` (118px 지정) | 10.00ms | 1,231,608px (**+41%**) |
| `cv-nosize` (미지정) | 10.88ms | 291,832px (**−67%**) |

**CPU 비용은 둘이 사실상 같다** (10.00 vs 10.88ms). 차이는 전부 스크롤 길이에 있다.

- 미지정 → 건너뛴 항목의 높이를 0으로 잡아 문서가 **1/3로 쪼그라든다**. 스크롤바가 엉망이 되고 스크롤 중 계속 튄다
- 지정했어도 **값이 틀리면 그만큼 틀어진다**

### 값을 어떻게 잡아야 하나 — 실측으로 확인한 함정

내가 쓴 값은 `contain-intrinsic-size: auto 118px` 인데 41% 과대평가가 났다. 계산해보면:

```
실제 항목 높이 = 872,328 / 8000 = 109.0px
  = content 73px + padding 24px + border 2px + margin 10px

cv-auto 추정   = 1,231,608 / 8000 = 153.95px
  = 지정값 118px + padding 24px + border 2px + margin 10px = 154px  ✓
```

**`contain-intrinsic-size` 는 content-box 크기다.** padding·border·margin 은 그 위에 더해진다.
"항목 높이가 대충 118px 이니까 118을 넣자"가 틀린 이유다. 넣어야 했던 값은 **73px**.

## 6. 실무로 옮기면

| 통용되는 말 | 실측 |
|---|---|
| "화면 밖 콘텐츠가 공짜가 된다" | ❌ 여전히 **O(N)**. 항목당 비용이 7.8배 싸질 뿐 |
| "layout 과 paint 를 건너뛴다" | ⚠️ layout·style 은 맞다(82~87%). **paint 는 원래도 컬링되고 있었다**(14%) |
| "30~60% 절감" | 조건 의존. 내 케이스는 **81%**. 항목 서브트리가 무거울수록 커진다 |
| "`contain-intrinsic-size` 는 성능용" | ❌ **정확성용**. CPU 비용은 없어도 거의 같고, 없으면 스크롤바가 망가진다 |

**쓸 만한 판단 기준**
- 항목이 **많고**(≥500) 항목마다 **서브트리가 무거울 때** 가장 이득
- 항목 100개짜리엔 별 의미 없다 (2.2배)
- `contain-intrinsic-size` 는 **content-box 기준**으로, padding·border 를 뺀 값을 넣는다
- 근본적으로 O(N)이므로, 항목이 수만 개라면 **가상 스크롤을 대체하지 못한다**

## 7. 한계

- 항목 구조가 한 종류(`h3` + `p` + `span`×3)다. 절감률은 이 구조에 의존한다
- **스크롤을 하지 않았다.** 스크롤 시 항목이 뷰포트에 들어오며 발생하는 비용(`cv-auto` 의 대가)은 측정 안 함 — 이게 이 기능의 진짜 트레이드오프인데 빠졌다
- 강제 리레이아웃(폭 변경)이라는 인위적 무효화다. 실제 페이지의 무효화 패턴과 다를 수 있다
- 초기 로드(파싱 + 첫 렌더) 비용은 제외했다. `content-visibility` 의 주요 홍보 지점이 초기 로드인데 여기선 안 쟀다

## 8. 자가 평가

**통과**

- **예측을 등록했고, 그 예측이 반증됐다.** C1을 미리 "5배 미만"이라고 못 박아두지 않았다면, 21.4배를 보고도 "그래도 7.8배 빨라졌네"로 넘어갔을 것이다. 사전 등록의 값어치가 이번에 드러났다
- **N 스윕 설계가 결정적이었다.** 단일 N에서 "87% 빨라짐"만 쟀으면 통용되는 홍보 문구를 그대로 재확인하고 끝났다. 여러 N을 봐야 *"차수는 그대로고 기울기만 바뀐다"* 가 보인다
- 뜻밖의 발견(Paint 는 원래도 컬링됨)은 **대조군의 스케일링까지 같이 쟀기 때문에** 나왔다. `plain` 의 Paint 가 5.4배밖에 안 는 걸 보지 않았다면 알 수 없었다
- `contain-intrinsic-size` 가 content-box 기준이라는 것도 **숫자가 안 맞아서** 파고들다 나왔다 (154 = 118 + 26 + 10)

미흡한 것
- §7의 **스크롤 비용 미측정**이 가장 아프다. `content-visibility` 의 대가가 거기 있는데 빠졌다. 후속 실험 후보
